# perf

Performance harnesses of the engine and its services (run by Node; `explorer-ui-20k-browser` and `grid-100k` also drive a real Chromium): budgets measured on synthetic data and printed for the S-13 and S-14 records.

Tags: `type:test`, `runtime:node`.

## Public API

- None: `src/index.ts` exports nothing. A harness is a file `src/<name>/<name>.perf.ts` with its own Nx target; it is run by `vitest.perf.config.mts` and never by `nx test` (a loaded machine would make a timing assertion flaky in the unit run).

## Harnesses

- `explorer-20k` (`pnpm nx run perf:explorer-20k`, M0-48 AC-24): the `inventory.query` action of `svc-explorer` over the real index and sweeper, fed by the scripted broker of `svc-explorer`'s fakes. A sweep loop keeps installing new index versions while 1,000 window queries (mixed filters, sorts, offsets and limits, a fixed random sequence) run, with `monitorEventLoopDelay` sampling every millisecond. At 20,000 queues it asserts engine time per window p95 at most 100 ms and event-loop delay p99 at most 20 ms; at 100,000 queues (`PERF_EXPLORER_LARGE=0` skips it) the same run is measured and printed, never asserted (OQ-665).
  - The figures are **synthetic**: the broker answers from memory (one turn of the event loop per request, standing in for a socket), so they are the engine's own CPU and not a lab run. The lab run is `pnpm nx run svc-explorer:it`.
  - The harness prints the idle event-loop delay it measured first. On Windows that floor is about 16 ms (the operating system's timer tick, whatever the sampling resolution), so a loop-delay figure there is conservative; on Linux the floor is about 1 ms.
  - Where it runs in CI (pull request, nightly) is not decided (OQ-544, OQ-671): no workflow runs it yet.

- `metrics-100k` (`pnpm nx run perf:metrics-100k`, M1-26 AC-19): a Prometheus page of 400,000 series (100,000 queues, four families, 29 MiB, generated while it is read) through the parser of `adapter-prometheus`, then through the real reader into the collector of `svc-metrics` with 100,000 queues of demand, then 400,000 queue series pushed at the hot store. It asserts **counts**, not clocks: the parser takes a turn at least every 64 KiB and 2,000 lines and holds nothing (heap growth under 96 MiB for 29 MiB of text); the demand is capped at 50 queues and only those are stored; queues nobody asked for are skipped by the parser, not stored and not lost; the store admits at most twice its queue-series cap during a round, ends it at the cap, and every series is accounted for (stored or refused, then evicted); a series is a ring of 720 points. Wall times, the event-loop delay and the heap are printed.
  - **Synthetic**: the page is generated and the scrape port is a function, so the figures are the engine's own work. The store part admits every queue on purpose (the real collector admits only the demanded ones), which is why its heap figure is large. The run against a real 100,000-queue broker is a maintainer task.

- `capture-ingest` (`pnpm nx run perf:capture-ingest`, M1-09 AC-1): 50,000 saved messages of about 1 KiB of JSON (`PERF_CAPTURE_MESSAGES` changes the count) through the real capture store of `svc-messages`, the real AES-256-GCM field cipher and the real capture worker thread (the built `workers/capture.mjs`, so the target builds `engine` first), then 60 full-text filters (words, a prefix, a rare word, several words together). It asserts every message accepted is stored (none refused, none lost), the **p95 of the worker's transaction time is at most 5 ms and the p99 under 25 ms** (measured next to the database, OQ-994), the main loop's delay p99 at most 20 ms above what the sampler reads on an idle loop (the explorer harness's rule), and the **p95 of a filter over the 50,000 within 1 s**. It prints the machine, the throughput, the percentiles and the counters.
  - **Synthetic and one machine's**: one writer, no broker, no UI; the maintainer's and CI's figures differ (OQ-990). The transaction max is printed and not asserted: on a desktop operating system a single transaction can take several times its median for reasons outside the batch.
- `explorer-ui-20k` (`pnpm nx run perf:explorer-ui-20k`, M0-54 AC-26): the real window source of `@app/explorer-model` (the one the explorer page uses) reading through a data port that runs the real `inventory.query` action over a 20,000-queue index, while sweeps keep installing versions. 1,000 interactions (scroll jumps, text filters, facet changes, sorts; a fixed random sequence) are each timed from the call to the rows of the first block. It asserts every request has a limit of 200 or less, no window failed and the p95 per interaction is at most 300 ms, and prints the resubscribe, refresh and version-change counts of the sources; the 100,000-queue run (`PERF_EXPLORER_UI_LARGE=0` skips it) is printed, never asserted.
  - It measures **engine plus adapter in Node** and says so in its output: no transport, no rendering and no browser. Its data port has no live topic, so the resubscribe count is the source's reaction to the rows it was told were on screen. The time from input to painted rows in a browser is AC-27 (`explorer-ui-20k-browser`, below).

- `explorer-ui-20k-browser` (`pnpm nx run perf:explorer-ui-20k-browser`, M0-54 AC-27, #280): the explorer's queue page **in a real Chromium** at 1280x720. It builds `web` and `engine`, starts the engine bundle in local mode (it serves the production web build under the real Content-Security-Policy, the way `web-csp-check` does), opens `/c/perf/explorer/queues` and drives a fixed sequence of scroll jumps (the scrollbar's jump, by `scrollTop`), text filters, facet changes (queue types, vhosts) and sorts (real mouse clicks on the header) with a CDP driver written for it (`cdp.ts`, no new dependency). 500 interactions are timed after 12 warm-up ones (`PERF_EXPLORER_UI_BROWSER_INTERACTIONS` changes the count). Each is timed from the input (`event.timeStamp` of the click or Enter, `performance.now()` before a scroll jump) to the end of the first frame whose DOM holds the new rows, **checked by content** against an oracle (the names of the eight rows at the top of the viewport, the matched count, the sort mark and the scroll position), so a screen that merely changed does not count. The filter's 200 ms pause is excluded by construction (the text is entered and Enter pressed in one task, which applies the filter at once and cancels the pause). It asserts: p95 under 300 ms, every request has a limit of 200 or less, no long task above 50 ms (`PerformanceObserver` `longtask`, from the first timed interaction to the last), and zero CSP or Trusted Types reports (`securitypolicyviolation` events, `Audits` issues, console and exception text) over the whole life of the page, boot included.
  - **What stands in for the engine.** The engine bundle has registered the explorer module since issue #278 (`apps/engine/src/modules/index.ts`: the actions, the `explorer.window` source and a drain phase), but the engine this run serves has no broker and no connection `perf`, so `inventory.query` is answered by the harness from a 20,000-queue `createFakeExplorerData` through the DevTools `Fetch` domain (and `profile.get` with the explorer fakes' sample profile, because the page reads the profile before the inventory and shows its "has not been checked yet" prompt, not a list, for a connection without one; no connection `perf` exists in the engine): the page's `EngineApi`, `HttpClient`, window source, AG Grid, filter bar and router are the real ones; the engine's `svc-explorer` is not on the path (`explorer-ui-20k` has it, in Node). The live socket of the page is replaced in the page by a stand-in that speaks the live protocol minimally (hello, sub, a snapshot that holds only the version marker, ping), because the engine would end the `explorer.window` subscription with "no such connection" and put the page in its "live updates ended" state; the topic's own cost is not measured here.
  - **What the figure is.** One machine, headless Chromium (`--headless=new`, software compositing), the answer from memory over the DevTools protocol (the figure prints the data port's own time and the interception round trip so they can be subtracted). "Painted" is the end of the main-thread work of the frame that holds the rows (a message posted from that frame's animation-frame callback), not light on a screen, and a figure is a multiple of the 16.7 ms frame. The output names the machine, the browser and the budgets; it is not a promise for any other hardware.
  - **Flake policy.** The two timing budgets (p95, long tasks) depend on the machine's load: a failing attempt is repeated, up to `PERF_EXPLORER_UI_BROWSER_ATTEMPTS` (3) attempts in all, and the run passes when one attempt meets them; every attempt is printed. A CSP or Trusted Types report, a request over a block, rows that never appear or fewer timed interactions than planned fail at once and are never retried. Before anything is timed the page proves that its two detectors are alive (a 90 ms busy loop must be reported as a long task, an inline script as a CSP report); `PERF_EXPLORER_UI_BROWSER_ANSWER_DELAY_MS=400` slows the data port and makes the run fail on the p95, which is how the gate was shown to bite.
  - **No browser, no proof.** The browser is taken from `CSP_CHECK_BROWSER`, `PERF_BROWSER`, `CSP_SPIKE_BROWSER`, then Chrome or Edge in their default locations (Windows, macOS) or on `PATH` (Linux). Without one the test is **skipped, loudly** (a message on stderr and a skipped test, never a pass), and nothing is proved; `PERF_REQUIRE_BROWSER` makes that a failure (CI sets it). The unit specs of the judgement, the plan, the browser search and the page script run in `pnpm nx test perf` and need no browser.
- `charts-50` (`pnpm nx run perf:charts-50`, M1-54 AC-24): 50 live charts of three series at 1 Hz for 300 ticks, each tick a point into a session (`metrics-model`), then the draw maths of `ui-charts` (downsample to the pixel width, axis, paths). It asserts **counts**: a path never has more than four vertices per pixel column, a ring holds at most 1,000 points (16,000 bytes) and every point it pushed out is counted. The time per tick and the heap are printed, not asserted. It is the work handed to the renderer, **not** the renderer CPU of the issue (under 20 %), which needs a browser profile (OQ-930).
- `grid-100k` (`pnpm nx run perf:grid-100k`, M0-53 AC-1, AC-4, AC-16, #49; spike S-14): the real `<app-data-grid>` of `ui-grid` **in a real Chromium** at 1280x720, reading 100,000 rows through the engine-windowed infinite row model (block 200, at most 25 blocks resident) from a fake engine window (`createFakeWindowSource`, 15 ms an answer, in the page). It builds the harness page (`perf-grid-page:build`, a bare Angular app, see `apps/perf-grid-page/README.md`) and serves it from a small static server (`src/grid-100k/server.ts`) that sends the engine's own Content-Security-Policy (`contentSecurityPolicy` of `@app/transport`: Trusted Types enforced, `style-src 'self' 'nonce-N'`, no `unsafe-eval`) with a fresh nonce in every `index.html`. The driver is `src/explorer-ui-20k/cdp.ts` (shared with the explorer harness, no new dependency); the page script (`page-script.ts`) records frames, long tasks and policy reports from the first script of the page. Three tests, one per AC:
  - **AC-1** "scrolls 100k rows at 55 fps or better with no task above 50 ms": real wheel input (`Input.synthesizeScrollGesture`, the browser's own wheel gesture, 40,000 px/s for 6 s) over the grid, in **both densities** (32 px and 24 px rows), a fresh page each. It asserts at least 55 frames per second (one `requestAnimationFrame` timestamp per frame, `(n - 1)` intervals over the window), no main-thread task above 50 ms (the Long Tasks API, which reports only tasks over 50 ms, so the longest task under that is not known), and, as counts, that the scroll asked for more than 25 distinct blocks (37 at 32 px, 50 at 24 px), every request had a limit of 200 or less and started on a multiple of 200, and the viewport moved more than 25 x 200 rows.
  - **AC-4** "memory stays flat across 100k rows": 300 seeded jumps (mulberry32, seed 53) over all 100,000 rows, each checked by content (the names of the first and last rows on screen, against an oracle), with a header click (sort ascending, descending, none) before every 30th jump from the 15th on. It asserts, as counts, that the grid never held more than 25 blocks (`getCacheBlockState()` sampled after every model update and every answer), no request asked for more than 200 rows or off a block boundary, and 300 jumps were made; and that the JS heap after a forced collection (`HeapProfiler.collectGarbage`, then `Runtime.getHeapUsage`) at the end of the run is at most **1.15 times the heap at the middle of the run**, where the cache holds a comparable number of blocks (at least 15 at both points, asserted). The literal reading of the spec, against the heap after the **first five windows**, is printed and **not asserted**: it measures 1.30 on the reference machine because the cache is allowed to grow from about a third of its 25 blocks to all of them (OQ-940).
  - **AC-16** "the grid runs under the enforced S-04 policy with zero violations": mount, scroll (a jump and wheel input), a real right click that opens the app menu (`role="menu"`, focus on the first item, Escape closes it), then a theme change (to the other of light and dark) and a density change. It asserts zero CSP or Trusted Types reports from three channels over the whole life of the page, boot included (`securitypolicyviolation` events, the DevTools `Audits` issues, console and exception text), that the policy sent holds the S-04 rules and no `unsafe-eval`, that the nonce is set and every `<style>` element carries it (19 on the reference run: AG Grid's and Angular's), that the grid background and the row height followed the theme and the density, and that the grid root has no `style` attribute. It runs twice: under the engine's policy as it is, and under the same policy **without** `style-src-attr 'unsafe-inline'`, where no markup may carry a style attribute (both pass).
  - **What it does not measure.** A real engine (the window is a function in the page: no network, no JSON), a GPU or a physical display (headless, software compositing, one machine), a user's hardware. "Frames" are animation-frame callbacks, not light on a screen. The spec words AC-1 as "the CDP trace shows"; the harness uses the page's own frame and long-task records instead of a trace (OQ-941). The figures are that machine's, printed with it.
  - **Flake policy** (the same as `explorer-ui-20k-browser`): the timing and memory budgets (fps, a long task, the heap ratio) are repeated up to `PERF_GRID_100K_ATTEMPTS` (3) attempts in all and pass when one attempt meets them; every attempt is printed. A CSP or Trusted Types report, a request over a block or off a boundary, more than 25 blocks resident, a scroll that did not pass 25 blocks, a missing jump or a dead detector fail at once and are never retried. Before anything is measured the page proves that its two detectors are alive (a 90 ms busy loop must be reported as a long task, an inline script as a CSP report) and that its row count is the driver's.
  - **Self-checks of the gates.** `PERF_GRID_100K_BREAK=jank` makes every answer a 60 ms task (AC-1 fails on fps and long tasks), `=leak` keeps every answer for good (AC-4 fails on the heap ratio), `=violate` writes an inline script at boot (AC-16 fails on the report). `PERF_GRID_100K_JUMPS` and `PERF_GRID_100K_SCROLL_SPEED` change the length of the runs.
  - **No browser, no proof.** As for `explorer-ui-20k-browser`: the browser is taken from `CSP_CHECK_BROWSER`, `PERF_BROWSER`, `CSP_SPIKE_BROWSER`, then Chrome or Edge in their default locations; without one the tests are **skipped, loudly**, and `PERF_REQUIRE_BROWSER` (CI sets it) makes that a failure. The unit specs of the judgement, the plan, the page server and the page script (`grid-100k-run.spec.ts`) run in `pnpm nx test perf` and need no browser.

## Invariants

- Dependencies follow the type:test row of blueprint 2.2; `pnpm nx lint perf` enforces them.
- A harness prints what it measured and labels the data it measured on (synthetic or lab). A budget is asserted only where its spec says so.

## Proof commands

```sh
pnpm nx run-many -t lint typecheck test -p perf
pnpm nx run perf:explorer-20k
pnpm nx run perf:explorer-ui-20k
pnpm nx run perf:explorer-ui-20k-browser   # needs Chrome or Edge; skips loudly without one
pnpm nx run perf:charts-50                 # M1-54: the draw work of 50 live charts, counted
pnpm nx run perf:grid-100k                 # builds the harness page; needs Chrome or Edge; skips loudly without one
```
