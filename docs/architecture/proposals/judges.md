# Judge panel

Two independent judges scored the three proposals (weights: correctness & message safety 25%, agent-buildability 20%, security 15%, delivery-mode fit 15%, performance 10%, testability 10%, maintainability 5%).

## Judge A (correctness, maintainability)

**Winner:** simplicity-first

| Proposal | Weighted total |
| --- | --- |
| simplicity-first | 8.025 |
| safety-first | 7.925 |
| scale-first | 7.725 |

| simplicity-first | correctness & message safety (25%) | 7.5 | Strengths: - Peek follows the b.8 algorithm precisely: exact era rules and guard thresholds, an HTTP-only preflight, one nack(multiple,requeue) then a qos barrier then close, a watchdog, and a write-ahead peek_started record that becomes a W-CRASH receipt on restart. - The HTTP request lifecycle never controls a hold. - Every DC is traced. - It adds an isolated 'source' connection role for replay consumers, a genuine refinement of DC-12.  Deductions: 1. DC-09 is mis-modelled. 'stop' is a fourth policy and the default, and only let-broker-handle is refused for AI or unattended actors. Replay nack-requeues prefetched sources on cancel or shutdown. On 4.3 QQ DLQs carrying DC=21, any return drops them (b.4). 4. The port types constrain nack but not ack/accept. 5. ### Gaps in all proposals

- Replay and move source consumers have no doomed-return guard:
- Simplicity-first and scale-first nack-requeue unprocessed or unconfirmed sources on cancel and drain.
- Safety-first parks sources only when a publish fails.
- None gates replay sources with W-OVERLIMIT or W-BUDGET.

On 4.3, a QQ DLQ at default limits receives messages carrying DC=21, and any return drops them (b.4). On 4.0-4.2, every return burns AC budget.

Required:
- prefetch 1 for finite-L QQ sources;
- park by confirm-then-ack instead of nacking when DC>L (4.3) or AC>=L (4.0-4.2);
- a refusal or one-click fix before replaying from an over-limit DLQ;
- a DC-04 drain rule that never blindly nack-flushes these sources.
- The AMQP 1.0 credit+drain peek path on 4.3, offered by all three, acquires the whole credit window before the guard sees any message. 'Stop at the first doomed message' cannot apply, and released on a doomed delivery drops it. One of the following is needed:
- rescue each doomed delivery in the batch individually;
- grant credit 1 per step;
- offer the path only when the disposition is quarantine or raise-limit.
- The rescue target is never preflighted, and the rescue has no failure path. None of the proposals does the following for the quarantine queue:
- simulate its policy matches (Amazon MQ's '.*' default policies set max-length with reject-publish);
- declare x-queue-type=classic explicitly under a quorum default queue type (classic can be disabled on 4.2+);
- check permissions;
- handle alarms or connection.blocked on the publish connection.

If the confirm is nacked, returned or blocked mid-hold, the doomed message is returned and dropped anyway. The plan should preflight the rescue path as it does for taps, and should state what happens when the rescue fails.
- Docker local-web mode is unspecified. Inside a container the engine must bind 0.0.0.0 to receive traffic from a published port, but all three refuse non-loopback binds without OIDC or basic auth plus TLS (DC-36 as written). Host and Origin allow-lists keyed to the internal port also reject remaps such as -p 127.0.0.1:9000:8765. A container mode is needed: an explicit bind exception with a mandatory token, a --public-origin or allowed-hosts setting, a healthcheck, and documented -p 127.0.0.1 usage.
- The pin policy has no expedited path for security patches:
- DC-49 pins fastify 5.12.5, which is now behind security release 5.12.6 (GHSA-389g-gv7q-r4x8 / CVE-2026-107832, 2026-10-13, low severity).
- The two Nest-based proposals inherit @nestjs/platform-fastify@12.1.3's exact 5.12.5 pin.
- The minimumReleaseAge gates (3-7 days) would also block that fix, the pinned Spartan 1.7.0 (published 2026-10-14) and Electron 45.0.0 at its GA.

M0 needs a reviewed exclusion list and an override procedure: pnpm overrides, an ADR and CODEOWNERS sign-off.
- The post-acquire guard trusts the x-delivery-count header, but QQs stamp it only on messages already returned at least once (b.1), so a client-copied header survives:
- A copied high count gives a false 'doomed' verdict, and 'rescue' then acks a healthy message out of its production queue.
- On 4.3, a carried DC also arrives with redelivered=false, so a forged value and a carried value cannot be told apart by flags.

Receipts and the UX must mark such counters as unverified and ask before rescuing a non-redelivered message. Add a lab cell for this.
- Plans, approval requests and replay or undo journals can carry message bodies and edited payloads (publish, replay-edit and undo copies). No proposal specifies:
- encryption at rest for plan records (DC-45 coverage stops at secrets and captures);
- masking in the four-eyes approval view;
- purging plan payloads when their TTL expires.

On the team server this leaks PII through the plans table and the approvals inbox.
- No proposal limits the metadata-store write cost of short-lived queues on 4.3 (Khepri only): tap queues, quarantine and parked queues, and replay staging queues. There is no creation-rate limit, no reuse of a tap queue when its bindings change, and no team-wide churn budget, even though the stack research flagged Khepri writes for tap create/delete.

### Gaps in all proposals

- No patch lane for exact pins. DC-49's fastify 5.12.5 is pinned directly by simplicity-first, and @nestjs/platform-fastify 12.1.3 hard-pins it for the other two. It is affected by GHSA-389g-gv7q-r4x8 (header validation bypass), fixed in 5.12.6 on 2026-10-13; latest is 5.12.7. I verified this in the npm registry and the GitHub advisory.
- None defines a security lane: OSV/Renovate alert, then pnpm override, then a minimumReleaseAge exception, then a rebuild of every esbuild-bundled artefact (bundling bakes the vulnerable code in).
- Their 3-7 day minimumReleaseAge would currently block the fact-sheet pin @spartan-ng/brain 1.7.0, published 2026-10-14.
- THIRD_PARTY_NOTICES and the SBOM should be generated from the esbuild metafile, not from the lockfile.
- Docker local-web mode is contradictory.
- Inside a container the engine must listen on 0.0.0.0, which conflicts with the 'refuse non-loopback bind without OIDC/password + TLS' rule all three state.
- Host allow-lists keyed to the internal PORT break when the host port differs: -p 127.0.0.1:HOSTPORT:PORT.
- It needs an explicit container mode: token always required; Host limited to loopback names on any port, or to a configured external origin; docs that forbid 0.0.0.0 publishes and --network host.
- Replay and move source consumers on budget-limited QQ DLQs are unsafe in all three.
- On 4.3, any return of a prefetched source re-checks the carried DC > L and drops the message. That includes a nack on cancel, shutdown or publish failure, and the DOWN after a crash. On 4.0-4.2, each return spends AC budget.
- simplicity-first and scale-first nack-requeue sources on cancel.
- safety-first states 'never return a source to a budget-limited QQ DLQ' but defines no drain path and has no job drain hook.
- Required: apply the DC-07/DC-08 gates to replay and move sources; prefetch 1 on QQ DLQs; drain by finishing confirm-then-ack or parking by confirm, never by nack; conformance cells for cancel, shutdown and crash mid-replay.
- Replay crash-resume identity is undefined.
- CQ/QQ deliveries carry no stable broker ID, so matching a redelivered source message to its journal row is ambiguous.
- scale-first keys rows by content fingerprint. Identical messages then collapse, one is acked without being republished, and it is lost. The other two leave the rule unspecified.
- Define it as at-least-once: when in doubt, republish rather than skip; count per fingerprint as a multiset; prefer framework logical IDs; stamp the replay id on copies so downstream dedupe works.
- Executor failure paths have no conformance cells. All three test the happy-path settle matrix and the nack-vs-DOWN race. None covers the tool closing its own channel while holding deliveries:
- 406 'unknown delivery tag', for example from nack(multiple) using the tag of a delivery the rescue path just acked (only scale-first says lastUnackedTag);
- 405 RESOURCE_LOCKED;
- 403 on a passive declare;
- 404 when the queue is deleted mid-peek;
- the quarantine publish being nacked or returned while the original is still held;
- the watchdog firing during a rescue publish.

On 4.3 each of these turns every held delivery into a failed delivery. It needs an executor state machine with model tests, plus fault-injection cells.
- The registry and its tests are circular, which matters for agent-built code.
- The semantics registry is both the specification and the expected value. scale-first's tests read their expectations from the cell, and all three generate receipts and warnings from it.
- An agent can therefore turn a red conformance run green by editing the cell.
- None requires a lab evidence artefact (raw before/after counter traces per broker version) to flip a status.
- None keeps golden observations recorded independently of the registry.
- None requires human sign-off on registry and expectation diffs.
- None mutation-tests the suite, for example swapping nack for reject or dropping the qos barrier and requiring failures.
- No runtime policy covers brokers newer than the last conformance-verified version, such as 4.3.7 (alpha draft notes exist) or 4.4 alphas.
- Era resolution simply classifies them as 4.3 or 4.4 and applies verified cells, while DC-60 says support is claimed only after re-verification.
- Needed: an 'unverified version' state (banner, lower receipt confidence, conservative caps with extra consent, MCP mutations off) and a way to ship registry data updates.
- safety-first fails closed only for missing cells.
- The tool has no controls on its own blast radius.
- There is no per-broker emergency action that revokes all of the tool's leases at once: taps, firehose, in-flight peeks, and running replays or moves, across all users.
- There is no broker maintenance freeze that forces read-only and pauses pollers during incidents or upgrades.
- Both matter for a team server holding delegated sessions against production brokers.
- Backup, restore and key custody are not designed. Missing:
- Postgres point-in-time recovery and SQLite backup;
- restore drills;
- KEK escrow and rotation runbooks ('lost KEK = lost secrets');
- re-verifying the audit hash chain after a restore and across retention deletes;
- anchoring chain heads outside the database (WORM storage or a SIEM), so a schema owner cannot rewrite history.

simplicity-first and scale-first even let the migrating app role own the audit table.
- UI/engine skew in team and local-web modes is only half handled.
- Long-lived tabs keep the old Angular build after an engine upgrade, and its hashed lazy chunks then 404 (ChunkLoadError).
- None keeps the previous build's chunks or forces a controlled reload when a chunk fails to load.
- simplicity-first claims there is no skew at all.
- Local IPC authentication is one-way.
- All three authenticate the CLI and the stdio MCP shim to the engine, but none has the client verify that it is talking to the real engine before it sends its capability token.
- On Windows the default named-pipe DACL grants Everyone read. Fixes: check GetNamedPipeServerProcessId and the owner SID; on Unix, check the socket directory's uid and mode; or require a nonce proof keyed from the user-only token file.
- Without this, an impostor engine could also feed injected content to an AI agent.
