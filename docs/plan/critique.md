# Final consistency critique (design phase)

All blocker and major findings are resolved as binding amendments in [amendments.md](amendments.md).

## Verdict

The package is close but not ready to execute as written: it needs fixes before M0-W1. Product, blueprint and plan agree closely and respect every binding decision. The stack is TypeScript end to end, with a Node 24 engine and an Angular 22.2.3 UI, and no React anywhere. One engine bundle and one UI build run in Electron, in npx or Docker on loopback, and in the Helm team server. The project is fully Apache-2.0 with free team features and no SaaS. There is no browser-to-broker path, and no CQ or QQ read is called non-destructive. The DC-49 deviation (no NestJS, no Orval, fastify 5.12.7) is backed by evidence I verified. There is 1 blocker: the ADR-028 / §5.6 counter-trust rule makes the post-acquire guard fail open, contradicts DC-09, and requires a human confirmation while messages are held, which DC-05 forbids. There are 24 majors, in four groups. The first is cross-document contradictions: replay failure semantics, and the 'zero duplicates' exit criterion. The second is safety gaps in trust:critical paths: a new policy silently replacing the existing one, a garbled quarantine spec, firehose disk risk, incomplete DLX-source analysis, the HTTP fallback, and settlement proofs that can be forged. The third is gaps against DC-12, DC-36 and DC-59: the connection budget, container-mode PUBLIC_ORIGIN, and the Electron spellchecker download. The fourth is execution-model problems: licence-gate scope, lab-evidence provenance, agent identity versus code-owner review, public identifiers created before the name is cleared, RabbitMQ 4.4 arriving during M0, MSIX virtualization, data-directory ownership, audit partitions under a DML-only role, cross-OS test infrastructure, and the platform upgrade lane. Fix the blocker and the majors that touch M0 (licence gate, evidence workflow, agent identity, naming gate, proofs, 4.4 plan, spellchecker, PUBLIC_ORIGIN, desktop authz) before M0-W1. Fix the rest before the work packages they touch start.

| blocker | Peek safety: architecture §5.6 / ADR-028 counter trust vs DC-09 and DC-05 (encoded in plan M1-15 AC) | The counter-trust rule makes the DC-09 post-acquire guard fail open in three ways. (1) On 4.3, a delivery with redelivered=false and an x-delivery-count header is classed 'unverified-copied', treated as not doomed, and returned normally whenever the routing simulator finds no finite-L DLX source. Current topology does not prove history: the source may have been deleted or re-policied, policies may be unreadable without policymaker, operator policies can return 405, and stats-off below 4.2.5 hides policy fields. A genuinely carried-over message with DC=21 in an L=20 DLQ is then nacked and dropped by the broker. That is exactly the fact-sheet b.4 loss the product exists to prevent. (2) The rule requires that 'any rescue of a message whose counter is unverified or redelivered=false' get per-message human confirmation, and that AI or unattended runs 'stop and return'. On 4.3 every carried-over doomed message arrives with redelivered=false, so AI and unattended runs let RabbitMQ handle doomed messages, which DC-09 explicitly forbids. M1-15's AC encodes this. (3) A per-message human confirmation can only happen while deliveries are held. That violates DC-05 and I-4 (no hold across user think-time) and the 5 s target / 30 s hard-abort budget. | Rewrite ADR-028, §5.6 and the M1-15 AC so the guard applies DC-09 literally. A message is doomed exactly when the era rule holds on the observed header, whatever its provenance: - 4.3+: x-delivery-count > L - 4.0-4.2: x-delivery-count ≥ L - 3.13 with a limit: ≥ L Keep counterSource only as a label in the receipt and UI. Resolve ambiguity at plan time: the plan states that messages whose counters cannot be verified are treated as doomed, and the pre-chosen disposition applies (default quarantine). A false positive then lands recoverably in quarantine instead of being lost. Allow no prompts during a hold. Reject AI and unattended plans unless a quarantine or raise-limit disposition passed rescue preflight within the last 60 s. Add CF cells for: - a carried-over message whose source queue was deleted - a source whose policy is invisible to the principal - a client-copied header, which ends quarantined, not lost Add the mutant 'unverified counter treated as not doomed' to the nightly kill list. |

M1-37's AC only hides the fallback for 4.3 DLQs at over-limit risk, so an agent will reasonably offer it, with W-BUDGET consent, for any finite-L QQ on 4.0-4.2. That is a loss path. | major | Rescue quarantine queue spec (§5.5 rescue preflight, steps 1-2) | The text contradicts itself. Step 1 says arguments set x-overflow explicitly to beat Amazon MQ's '.*' max-length + reject-publish policy. Step 2 then reads 'x-overflow=drop-head… — not drop-head. It uses reject-publish-dlx: false, i.e. no overflow argument, and no max-length'. Both readings are unsafe. With drop-head, a full quarantine silently discards earlier rescued messages. With no overflow argument, the inherited reject-publish applies and nothing checks headroom. This is a trust:critical path, and an agent will implement whichever sentence it reads last. | Define a literal QuarantineQueueSpec in the core interfaces: durable, x-queue-type=classic, x-overflow=reject-publish, never drop-head, and no x-max-length argument. A full quarantine then nacks the copy and the receipt says rescue-failed. Add a preflight headroom check against any matching policy max-length (classic queues take min(policy, arg)). Refuse the disposition when headroom is below the planned count. Add a CF-EXEC 'quarantine full' cell. Keep the QQ fallback (x-delivery-limit=-1, 4.0+ only). |
| major | DLQ replay/move failure semantics: product DLQ-03/MSG-12 vs architecture §5.8/ADR-010 vs plan M1-34 | The three documents disagree about the source message when a publish is nacked or returned: - Product DLQ-03 and MSG-12 ACs: 'the source is not acked'. - §5.8: park it, i.e. confirm a copy to <product>.parked, then ackWithProof. - Plan M1-34 AC: both at once ('the source is not acked and the message is parked by confirm-then-ack'). | major | M2 exit criterion / M2-06 AC: 'zero lost and zero duplicate messages across 10k replays' | ADR-010 is at-least-once by design: 'when in doubt, republish', with an uncertain-duplicate state. | major | Settlement proofs (ADR-009, core interfaces, M0-27) | ConfirmedCopyProof, DestructiveConsentProof and SafeReturnProof are structural interfaces with string brands. ## Consistency notes

The product definition, blueprint and plan are consistent with one another and with every binding user decision:
- **Stack:** TypeScript throughout, with a Node 24 ESM engine and an Angular 22.2.3 UI. React appears nowhere; the Astro Starlight docs site is not product UI.
- **Delivery:** one engine bundle and one Angular build, served three ways: the Electron utilityProcess over MessagePort, npx/Docker on loopback over HTTP and WebSocket, and the Helm team server.
- **Licensing:** Apache-2.0, with OIDC, RBAC, audit, approvals and masking all free. No SaaS.
- **Broker access:** all broker I/O happens in the engine, with CSP connect-src 'self', no CORS, and static web utilities that run client-side only. There is no browser-to-broker path.
- **Wording:** no CQ or QQ read is called non-destructive. That word is kept for anonymous stream browsing and the M6 node agent, and an honest-wording lint enforces it.

Plan §0 reconciles the stale product text: NestJS, Orval, Amqp10Port in M0, the PLAT-16 dependency, and signed NSIS. Every blueprint WP is mapped to plan WPs, all M0/M1 features are covered, all 26 uncertainties are scheduled, and the 46 M2-M6 epics cover the remaining features.
