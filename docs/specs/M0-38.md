## Goal

Write the lab scenarios, the projections and the harness wiring for the six conformance ids the registry already names for the "return" family: `CF-SETTLE-01..06` (AMQP 0-9-1 `basic.nack` and `basic.reject` with requeue, AMQP 1.0 `released`, `modified` with delivery-failed true and false, and the management API `/get` with `ack_requeue_true`). Once CI records evidence for them (never this WP), the three-way assertion can show, on the five pinned lab brokers (3.13.7, 4.0.9, 4.1.8, 4.2.9, 4.3.6), whether the registry's 40 `CF-SETTLE` cells are right: which counter moves (`x-delivery-count` is the acquired count on 4.0 to 4.2, get and consume paths), where the returned message lands (TAIL on 3.13 with no limit and on 4.0 to 4.2 with a limit of -1, HEAD otherwise), whether the return counts toward the delivery limit, and the 3.13 `x-delivery-limit` -1 drop on the first return.

Serves: U-01 priorities (2), (3) and (5) (`docs/research/uncertainties.md`; tracking issue #72), invariant I-14 (lab truth outranks registry text), amendment A-20 (evidence is recorded only by CI), blueprint 5.2, DC-16 (treat the 3.13 `x-delivery-limit` -1 as "drop on first return") and fact sheet b.1 and b.2.

**This WP produces no evidence and changes no registry cell.** It makes the 40 cells *recordable and comparable*. Each stays `code-derived` with empty `evidence` until a maintainer has CI record the evidence and approves it (section "What a maintainer and CI must do"). This session writes a spec only.

The issue title also says "CQ" (classic queues). The registry has no classic-queue cells (OQ-394), so there is nothing to compare a classic result with; classic queues are out of scope (Q-8).

### Three findings that shape the plan

1. **The landed projections read the counter headers the same way in every era (a defect in M0-40 slices A to C).** `projections-stamp.ts`, `projections-carry.ts` and `projections-dr.ts` take `deltaAC` from `x-acquired-count` and `deltaDC` from `x-delivery-count` for every era. The fact sheet (b.1) says that on 4.0 to 4.2 `x-delivery-count` **is** the acquired count and no `x-acquired-count` is sent, and on 3.13 there is no acquired-count header. `projections-down.ts` (M0-39) reads them per era correctly. `testing/era-broker.ts` emits `x-acquired-count` on 4.0 to 4.2 and nothing in `x-delivery-count`, so the unit tests pass without seeing it. On a real 4.2.9 the `CF-STAMP-01` projection would give `deltaAC 0, deltaDC 1` against the registry's `deltaAC 1, deltaDC 0`: a false `fail` that reads as the lab contradicting the registry (I-14: a negative result changes the registry, never the test, so a harness bug must be fixed before any evidence is recorded). U-01 priority (3) is exactly this fact, so M0-38 cannot start with the cells before the reading is one shared, era-aware function (slice A, Q-2).
2. **40 cells, but only 30 depend on `CF-SETTLE-*` alone.** The coverage gate confirms a cell only when every id it names is confirmed on every lab version of its era. Ten cells also name `CF-STAMP-01` (7 nack cells; the 3 `minus1` ones are unspoken by `CF-STAMP-01`, OQ-557) or `CF-CARRY-03` (3 cells whose AMQP 1.0 or HTTP leg `CF-CARRY-03` does not have, OQ-600). Q-3.
3. **AMQP 1.0 on the 3.13.7 lab broker needs a plugin.** `testing/broker-lab/enabled_plugins` is one file for every version and does not list `rabbitmq_amqp1_0`, which 3.13 needs and 4.x must not list (OQ-84 says a conformance cell that needs it adds a per-version file or build argument). Seven of the 40 cells are AMQP 1.0 on 3.13 (released and modified df=true at three limits each, plus the modified df=false drop). Without the lab change their 3.13 leg cannot run (Q-5, slice E).

## The scenarios

One scenario per id, the same for all five versions; the evidence differs by version, the scenario does not. All queues are quorum queues, declared with the arguments below, published with message ids only (`m1` and `t`, a short fixed id as body, no headers) and deleted at the end of the run. `t` is the "tail marker": after the return, `m1` ahead of `t` is HEAD and behind it is TAIL.

### CF-SETTLE-01, -02 (0-9-1) and CF-SETTLE-05 (HTTP), built by `settleReturnScenario`

| Dimension | Values |
| --------- | ------ |
| Delivery limit | `unset` (no argument; the 3.13 cells; on 4.x it is the default 20, recorded but not projected, OQ-394), `fin` (`x-delivery-limit` 2), `minus1` (`x-delivery-limit` -1) |
| Path | `get` (`basic.get`, then the return) and `consume` (consumer with prefetch 1, cancelled after the delivery arrives so the returned message is not handed straight back to it, then the return). CF-SETTLE-05 has only the HTTP path |
| Return | `nack` (requeue true) for 01, `reject` (requeue true) for 02, `POST /get` with `ackmode` `ack_requeue_true` for 05 |
| Rounds | one return per queue (counters, position, survival), plus crossing queues: `unset` returned 21 times (the version default plus one, as `CF-CARRY-03` does) and `fin` returned 3 times (L+1) |

Per single-return queue (6 queues): declare, publish `m1`, publish `t`, take `m1`, return it, `awaitReady`, `observe` (drain: position, survival, `redelivered`, both counter headers). Per crossing queue (2 queues, `get` path): the same publish, then each round takes the message at the head (`get`, return), then `awaitReady` and `observe`; the round's `get` result says which message came back. About 8 queues and 100 recorded steps per scenario (about 80 for the HTTP one). The scenarios hold deliveries on lab brokers only: I-4 governs the product's engine, and the lab driver's job is to do what a product must not and report what the broker answers.

### CF-SETTLE-03, -04, -06 (AMQP 1.0; slice F)

Same queues and rounds as above; the message is published and drained with 0-9-1 (`publish`, `observe`), and **taken and returned with AMQP 1.0**: `openReceiver`, `grantCredit` (one), `receive`, `settleAmqp10` with `release` (03), `modify` delivery-failed true, undeliverable-here false (04) or `modify` delivery-failed false, undeliverable-here false (06). The 1.0 settle is asynchronous (OQ-425: a released message was back within seconds on 4.3.6), so `awaitReady` follows every settle. The `consume` path is replaced by a second receiver attach (`get` and `consume` are 0-9-1 names; the 1.0 path has one shape). The artefact's `protocol` is `amqp10`: the protocol of the action under test, not of the publish and the drain.

## The projection (`projectSettle`)

What an artefact shows, by the key of the cell asking (`era`, `limit`, `action`; `delayedRetry` must be absent or `disabled`, otherwise null, OQ-392). It speaks only for the effect fields the scenario measures and returns null (the cell stays `unverified`) when it cannot tell, never a default (OQ-518).

- **Counters** (`deltaAC`, `deltaDC`): `counterDeltas(cell.key.era, ...)` on the headers of the first delivery and of `m1` in the drain. 4.0 to 4.2 never projects `deltaDC`; 3.13 never projects `deltaAC`.
- **Position**: from the single-return queue: `m1` before `t` is `head`, after is `tail`. `original` is not distinguishable from `head` with `m1` first in the queue and no cell claims it (Q-10).
- **Survival**: `m1` gone after the single return is `destructive true`, `position dlx-or-drop` (the queues bind no dead-letter exchange, so a drop and a dead-letter cannot be told apart, OQ-611), and `countsTowardLimit yes` (3.13 with a limit of -1: DC-16). The counters of a message that no longer exists are not projected.
- **`countsTowardLimit`** from rounds: `fin`: `m1` held in rounds 1 to 3 and gone after round 3 is `yes`; held in all three and still there is `no`, **except** for the 4.3 cells of the actions that never raise the delivery count (nack, released, HTTP `ack_requeue_true`, modified df=false; chosen by the cell's key, never by its claimed value), where the field is left out: no number of such returns tells `no` from `if-dc-gt-limit`, and `CF-CARRY-03` is the scenario that does (Q-6). 4.3 `reject` and modified df=true raise the delivery count, so survival decides there. Gone earlier than round 3, or a different message held in a round, is null. `minus1`: `m1` survives the first return is `no`. `unset`: survives 21 returns is `no` (3.13 only).
- **Paths**: the `get` and `consume` queues of one limit must agree on survival, position and counters; if not, null, and `settlePathDivergence` names the queue and field (U-01 priority 3 says "both get and consume paths": the paths are compared, not assumed equal).
- **The 3.13 `amqp10.modified_df_false` cell** (`dlx-carryover.data.ts`) has no `limit` in its key (the plugin maps it to `basic.reject(requeue=false)`, so a drop whatever the limit). The projection reads the `unset` queue and requires the `fin` and `minus1` queues to show the same, otherwise null.
- A recorded value outside the registry's type (a delta of 2) is kept as it is and shows up as a field-level mismatch (the same rule as `projections-stamp.ts`).
