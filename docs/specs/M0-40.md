# M0-40 Lab cells: DLX carry-over, delayed retry, header stamping (U-01 priority 4, U-05)

**Issue:** #36 · **Milestone:** M0 · **Wave:** M0-W2 · **Size:** M by label, about 2,000 to 2,300 changed lines by estimate (over the 800 limit; four slices proposed, see Slices and question Q-1) · **Owner area:** conformance (lane: evidence) · **trust:critical:** yes

## Goal

Write the lab scenarios, the projections and the harness wiring for the six conformance ids the registry already names for the dead-letter, delayed-retry and header-stamping facts: `CF-CARRY-01..03`, `CF-DR-01..02` and `CF-STAMP-01`. Once CI records evidence for them (never this WP), the three-way assertion can show whether 4.3 dead-lettering carries the delivery count into a quorum-queue dead-letter queue (and what a first return then does to it), whether delayed retry hides a returned message and how the management stats show it, and whether a client-copied `x-delivery-count` survives.

Serves: U-01 (priority 4) and U-05 (`docs/research/uncertainties.md`), invariant I-14 (lab truth outranks registry text), amendment A-20 (evidence is recorded only by CI), blueprint 5.2 and 5.6, DC-16 and the fact sheet sections b.1, b.4 and b.5.

**This WP produces no evidence and changes no registry cell.** It makes the six cells *recordable and comparable*. Every cell that names these ids stays `code-derived` with empty `evidence` until a maintainer has CI record the evidence and approves it (section "How the cells become lab-verified").

### Scenario shapes (proposals; a lab surprise is evidence, not a spec error)

The docs define these ids only through the registry cells that name them, so the meaning below is read from those cells and the fact sheet; the maintainer confirms it (Q-4). All shapes run on all five lab versions (3.13.7, 4.0.9, 4.1.8, 4.2.9, 4.3.6) unless stated. Counters are read from the `x-delivery-count` and `x-acquired-count` headers and `redelivered` that `get` and `consume` already record. No scenario records a message body, a header other than the two counters, a URL or a login (the recorder rule, `findSecrets`).

- **`CF-STAMP-01`** (cells: the `amqp091.nack_requeue` cells of `settle-matrix.data.ts`). A quorum queue; publish `m1` with a copied `x-delivery-count: 99` and a control `m2` without; `get` both; record the headers and `redelivered` as delivered; `nack(requeue=true)` both; `get` both again; record. Shows whether the copied value survives the first delivery and the return (fact sheet b.1: "stamped only on messages already returned at least once"). The projection takes the counter deltas and the position from the control message only, so the copied value cannot distort a cell's `deltaAC` / `deltaDC`.
- **`CF-CARRY-01`** (cells: `amqp091.no_requeue`, quorum; 3.13, 4.0-4.2, 4.3). A direct exchange `dlx`, a quorum dead-letter queue `dlq` (no delivery limit argument, so the version default), and sources that dead-letter into it on `nack(requeue=false)` after one earlier return so the counters are non-zero: a quorum source with `x-dead-letter-strategy` at-most-once, a quorum source with at-least-once (with its required overflow setting), and a classic source. Read the dead letter from `dlq` and record its counters and `redelivered`. Shows the carry-over of fact sheet b.4: on 4.3 the target seeds its delivery count from the source; on 4.0-4.2 the limit counter (AC) is not carried; on 3.13 nothing is carried.
- **`CF-CARRY-03`** (cells whose `countsTowardLimit` is `if-dc-gt-limit`, 4.3). The issue's first criterion. A quorum source with `x-delivery-limit` 20 and a dead-letter exchange; a quorum `dlq` with no limit argument (so 20 on 4.x and none on 3.13). Return the message 21 times with `reject(requeue=true)` (not `nack`: on 4.3 only reject and modified-with-delivery-failed raise DC, fact sheet b.2) so it is dead-lettered for `delivery_limit` carrying DC 21; read it from `dlq`; `nack(requeue=true)` once; drain `dlq`. 4.3.6 is expected to show the message gone (dropped), or present in a second dead-letter target if `dlq` has its own exchange (a second variant); 4.2.9 is expected to show it present with a fresh budget (`x-delivery-count` 1 after the return). Expectations come from b.4 and are what the lab tests, not facts.
- **`CF-DR-01`** (non-failed returns: `nack`, `released`, HTTP nack-and-requeue read, `modified(df=false)`; cells `delayedRetry` `all` / `failed` / `returned`). Four quorum queues, `x-delayed-retry-type` `all`, `failed`, `returned` and `disabled` (the control), each with `x-delayed-retry-min` 5000 (and `x-delayed-retry-max` unset, which defaults to min). On each: publish, `get`, `nack(requeue=true)`; then, on a second set, the management API nack-and-requeue read (`mgmtGet` with `ack_requeue_true`, the issue's "nack peek"). Immediately after each return: `get` (empty or not), `mgmtQueue` (see Q-9 for the fields). Then `wait` 2500, `get`; `wait` 3500 more (total about 6 s), `get`. The artefact brackets the invisibility window between the two waits and records `messages_delayed` and the class of `next_delayed_at`. The AMQP 1.0 `released` and `modified` legs wait for slice D.
- **`CF-DR-02`** (failed returns: `reject(requeue=true)`, `modified(df=true)`): the same four queues, `reject(requeue=true)` instead of `nack`, then a second `reject` to see the delay grow with DC and stop at max (b.5: `min(min x max(1, DC), max)`).
- **`CF-CARRY-02`** (slice D): `CF-CARRY-01` with the AMQP 1.0 `rejected` outcome.

`wait` makes the delayed-retry scenarios last about 10 to 20 seconds per version; the `describeThreeWay` timeout is 120 s, which is enough (Q-9).

## How the cells become lab-verified (maintainer and CI; no agent does this)

1. Land the slice(s) on `main`.
2. Dispatch `.github/workflows/conformance-record.yml` (manual; default is a dry run) with `cells` = `CF-STAMP-01,CF-CARRY-01,CF-CARRY-03,CF-DR-01,CF-DR-02` (add `CF-CARRY-02` after slice D), `versions` = `3.13.7,4.0.9,4.1.8,4.2.9,4.3.6`, and `dry_run` off. CI stamps the artefacts `ci` and opens a bot PR labelled `lab-evidence`.
3. A maintainer reviews the bot PR (CODEOWNERS covers `testing/lab-evidence/**`) and merges it. Recorded evidence alone changes no cell.
4. Re-run `pnpm nx run conformance:test --versions=<each>`: results are now `pass` or `fail` per cell. A `fail` means the registry or the design is wrong; it is never fixed by weakening a scenario or a projection.
5. For each confirmed cell, a **separate human-reviewed change** lists the evidence path(s) in the cell's `evidence[]` and sets `status: 'lab-verified'`; for a refuted one, a registry fix and `lab-contradicted`. `semantics-evidence:check` then requires valid CI-stamped evidence (and checks the run through the GitHub API). A cell is confirmed only when **every** conformance id it names is confirmed on **every** lab version of its era (`coverage.ts`): a cell such as `...nack_requeue-limit-finite-delayed-all` needs `CF-DR-01` and `CF-CARRY-03`, and a `counters.data.ts` cell needs `CF-DOWN-*` (M0-39) as well. So no cell reaches `lab-verified` until the other WPs' ids are recorded too.
6. Any "lab-verified" wording elsewhere and the `SEMANTICS_VERSION` bump (OQ-398) follow the release process, not this WP.

## Risks / questions

Nothing here is decided by the spec; the "proposed" values are what it assumes until the maintainer answers. The implementer adds these as rows in `docs/open-questions.md` (numbers assigned then).

- **Q-1. Size and slicing.** About 2,000 to 2,300 lines against 800. Proposed: the four slices above, as four commits under #36 with `oversize-approved`, or four new issues. Slice D depends on Q-5.
- **Q-2. Paths in the issue are stale.** The issue and the design entry say `apps/conformance/src/cells/{carryover,delayed-retry,stamping}/*.cell.ts`. The repository uses flat `cells/cf-*.cell.spec.ts` stubs made by the generator, and OQ-396 says M0-38 to M0-40 settle the layout. This spec keeps the flat layout and puts scenarios in `scenarios/`, as `cf-smoke-01` does.
- **Q-3. The issue's verification command is refused by the launcher** (`|` in `--grep`). The spec uses three runs. Confirm, or change the launcher's grep rule (M0-37-owned).
- **Q-4. What exactly does each id measure?** No document defines `CF-CARRY-01..03`, `CF-DR-01..02` or `CF-STAMP-01` except through the cells that name them (`cells.data.spec.ts` oracle, `dlx-carryover.data.ts`, `delayed-retry.data.ts`). The shapes above are read from those cells and from fact sheet b.1, b.2, b.4, b.5. The blueprint (5.6) names two other lab cells, `CF-43-QQ-COPIED-HEADER-01` and `CF-43-QQ-DLX-CARRY-01`, that match `CF-STAMP-01` and `CF-CARRY-01` in intent but not in id. Confirm the mapping, and whether OQ-396's granularity should be revisited (for example one id per strategy and source type).
- **Q-5. AMQP 1.0 (and who widens the DSL).** `LabScenario.protocol` is the literal `'amqp091'` and `ScenarioHost` has no 1.0 methods, although `driver/amqp10-raw.ts` exists and the evidence schema already allows `amqp10` and `http`. `CF-CARRY-02` and the 1.0 legs of `CF-DR-*` and `CF-CARRY-03` need that widening, as do M0-38's `CF-SETTLE-03/04/06`. Two WPs writing it twice would collide. Proposed: one of them (whichever starts first, a maintainer picks) lands the widening as its own small commit; slice D waits for it. The management API legs need no widening (`mgmtGet` exists).
- **Q-6. Classic-queue sources and the other uncovered keys.** The issue asks for CQ and QQ sources, but the registry has no classic-queue cells (OQ-394, b.3), so a classic source is recorded as evidence and compared with nothing (`unverified`). Proposed: do not add cells here; ask whether classic cells should come with this WP or with the b.3 work. Similarly there is no cell for a dead letter from an at-least-once versus at-most-once source (the cells are strategy-agnostic); the projection must hold for both, which is a real check.
- **Q-7. Carry-over has no field in the schema (OQ-390).** A cell cannot say "the target seeds its delivery count" or "a fresh budget"; so the facts the issue cares about most (DC arrives as L+1; first return drops it; a fresh budget on 4.2.9) are recorded in the artefact but projected only as the fields the schema has (`countsTowardLimit`, `position`, `destructive`, the deltas). Until the maintainer answers OQ-390, those facts are evidence for people and the planner (M1-12), not a machine-compared cell field.
- **Q-8. Cells that name several ids, owned by several WPs.** The coverage gate confirms a cell only when every id it names is confirmed on every lab version of its era. `CF-STAMP-01` and `CF-CARRY-03` are named by `settle-matrix.data.ts` cells that M0-38 also tests with `CF-SETTLE-01..06`, and `CF-CARRY-03` by `counters.data.ts` cells that M0-39 tests with `CF-DOWN-*`. If a projection returns null for such a cell, the cell can never be lab-verified. Proposed: this WP's projections speak for the effect fields the scenario really measures (stamping: deltas and position of the control message; carry-over: `countsTowardLimit`) and return null otherwise; M0-38 and M0-39 do the same for theirs. Confirm the division; agree it on the M0-38 and M0-39 issues.
- **Q-9. Time, stats and what `messages_delayed` / `next_delayed_at` are.** (a) The fact sheet says a delayed message shows in `messages_delayed` and `next_delayed_at`, but not where (management queue JSON or Prometheus) or in which format; U-05 asks both. The lab endpoint exposes the AMQP and management ports only, so the proposal records the management queue JSON and defers Prometheus. (b) The management API refreshes queue stats on `collect_statistics_interval` (5 s by default; the lab configuration sets none), so a stat read right after a return may not show the delay yet; the scenario must read it again after a wait, or the lab sets a shorter interval (a lab-wide change, not made here). (c) A live replay must equal the recorded evidence field by field, so no clock value may be recorded: the window is bracketed by fixed waits (0, 2.5 s, about 6 s) and `next_delayed_at` is reduced to a class. The bracket is coarse and can flake on a loaded runner; the tolerance and the `min` of 5000 ms (the issue's value) are the maintainer's call.
- **Q-10. Policy keys.** U-05 says "x-delayed-retry-* arguments and 4.3.1+ policy keys". The issue's criteria use arguments only. Proposed: out of scope; adding the policy variant needs `PUT /api/policies` (the host's `management()` is POST-only today; slice A widens it anyway) and a precedence cell that does not exist.
- **Q-11. Old versions.** The issue's verification runs delayed retry on 3.13.7 to 4.2.9, where the registry has no delayed-retry cell. Proposed: record them as negative controls (the feature is absent) and show them `unverified`, as the issue's command implies. A declaration the broker *refuses* (for example an at-least-once source on a classic queue, or an argument an old version rejects) closes the channel and aborts the whole scenario today; such a variant is left out unless the DSL learns to record a refusal.
- **Q-12. The era broker can mislead.** It encodes the registry's claims so the plumbing can be tested without Docker; a test that passes against it must not be read as evidence. AC-13 and the recorded evidence are the only broker truth. Confirm that a fake of this kind is acceptable, or require the plumbing tests to run on the lab only.
- **Q-13. Test titles and the generator.** `describeThreeWay` titles every test `AC-2 <id> on <version>: ...` (M0-37's numbering), which clashes with this spec's AC ids; the project rule is that test names quote the AC id. Proposed: leave it, map by file and CF id; or parametrise the title in `assert/cell-spec.ts` (an M0-37 file). Also OQ-459 says the `conformance-cell` generator's template should emit `describeThreeWay` instead of `it.todo` once the lab-cell WPs land; whoever lands first updates it (a generator change, `tools/generators`).
- **Q-14. Trust-critical WIP cap.** M0-39, M0-40 and M0-42 are open now; the cap is 2. Confirm the order before an implementation session starts.
- **Uncertainties:** U-01 (priority 4) and U-05 are what this WP exists to measure. U-19 and U-06 are not touched. Related open questions: OQ-390, OQ-391, OQ-392, OQ-393, OQ-394, OQ-396, OQ-398, OQ-459.
