# M0-41 Lab cells: operational hazards: SAC, exclusive, stream get, passive declare, vhost PUT, machine version (U-02, U-09)

**Issue:** #37 · **Milestone:** M0 · **Wave:** M0-W2 · **Size:** L by label, about 3,800 changed lines by estimate (eight slices of at most 600, each proposed as a child issue; see Slices and question Q-2) · **Owner area:** conformance (lane: evidence) · **trust:critical:** yes

## Goal

Make the gating facts that the probe, the peek planner and the admin writes rely on **recordable and comparable** in the conformance harness: a quorum queue with single active consumer (SAC) refuses `basic.get` with 405 and a classic queue with SAC lets it bypass the consumer, an exclusive queue refuses another connection, a stream refuses `basic.get` with a connection-level 540, a passive declare needs (or needs no) permission per version, a vhost `PUT` without `default_queue_type` resets it, the quorum-queue status reports a Machine Version per member, and a 3-node rolling upgrade 4.2.9 to 4.3.6 with the `rabbitmq_4.3.0` flag off and then on leaves the resolved era at 4.0-4.2 until the flag is enabled.

Serves: U-02 and U-09 (`docs/research/uncertainties.md`), invariant I-14 (lab truth outranks registry text), amendment A-20 (evidence is recorded only by CI), blueprint 5.2, DC-21 (GET-merge-PUT for vhosts), DC-32 and fact sheet sections 0.1, 0.8, 0.13, a (hazard table), b.6, b.7 and b.8.

**This WP produces no evidence and changes no registry data.** It makes the eight ids below recordable and comparable. Nothing here, and nothing a human does with the evidence, can turn a registry *cell* to `lab-verified`, because **no registry cell names a `CF-OPS-*` id** (checked: `grep CF-OPS libs/shared/semantics` finds nothing). The facts live in hazard rules, warnings and fact-sheet prose, which carry no status or evidence field. Section "How the facts become lab-verified" and question Q-1 say what a maintainer decides.

## Files & interfaces

Nx project `conformance` (`apps/conformance`, tags `type:test`, `runtime:node`; trust-critical by path and label; CODEOWNERS covers `/apps/conformance/`). The DSL, drivers, recorder and scenarios import no `@app/*` package (`checkRecorderIndependence`, ADR-007); only `assert/` reads the registry. No new dependency (`amqplib` is already confined to this project).

```ts
// apps/conformance/src/dsl.ts  (names are proposals; the capabilities are the requirement)

/** A broker's reply to a request that failed: never its text, which carries run-unique names. */
export interface Refusal { readonly level: 'channel' | 'connection'; readonly code: number | null; readonly reply: string } // 'unparsed' when no name could be read
export type Attempt<T> =
  | { readonly refused: false; readonly value: T }
  | { readonly refused: true; readonly refusal: Refusal };

// slice A
export const tryGet: (as: string, queue: string, options?: { noAck?: boolean; channel?: string }) => LabStep;
//   result: { outcome: 'empty' } | { outcome: 'delivery', ...same fields as get } | { outcome: 'refused', level, code, reply }
//   declareQueue gains `exclusive` (classic and non-durable only: a mistake is an error at definition time)
// ScenarioHost gains: tryGet(channel, queue, noAck): Promise<Attempt<RawDelivery | null>>

// slice D
export const labUser: (alias: string, grants: { read?: true; write?: true; configure?: true }) => LabStep;
//   the host maps each grant to a regex that matches only this run's queue names; a scenario cannot ask for '.*'
export const openConnection: (name: string, options?: { user?: string }) => LabStep;   // user = a labUser alias
export const tryPassiveDeclare: (as: string, queue: string, options?: { channel?: string }) => LabStep;
// ScenarioHost gains: createLabUser(alias, grants), deleteLabUser(alias), openConnection(name, user?),
//   tryPassiveDeclare(channel, queue): Promise<Attempt<{ messageCount: number }>>; RecordHost gains secrets(): string[]

// slices E, F, H: one step, a closed table of operations, each with its own allow-listed result
export type MgmtOp =
  | 'vhost.put' | 'vhost.get' | 'vhost.delete' | 'vhostQueue.put' | 'vhostQueue.get'   // E
  | 'qqStatus.get' | 'featureFlag.get'                                                  // F
  | 'featureFlag.enable';                                                               // H
export const mgmt: (as: string, op: MgmtOp, params?: MgmtParams) => LabStep;
//   results (fields only): vhost.get { status, defaultQueueType, description, tags, tracing };
//   vhostQueue.get { status, type }; qqStatus.get { status, members, machineVersions: number[] sorted };
//   featureFlag.get { status, state }. A vhost, queue or user is created under a run-unique name, only
//   ever one the run created (the vhost "/" and the lab login are refused at definition time), and
//   deleted in `finally` even when the run failed.
```

## How the facts become lab-verified (maintainer and CI; no agent does this)

1. Land the slices on `main`. Slice G also needs CODEOWNERS lines for `/testing/broker-lab/` and `/libs/testkit/` (proposed in OQ-86, not applied: `CODEOWNERS` is a protected path), and the maintainer's answers to Q-5 and Q-6.
2. Dispatch `.github/workflows/conformance-record.yml` (manual; default is a dry run) with `cells` = `CF-OPS-SAC-01,CF-OPS-SAC-02,CF-OPS-EXCL-01,CF-OPS-STREAM-01,CF-OPS-PASSIVE-01,CF-OPS-VHOST-01,CF-OPS-QQVER-01`, `versions` = `3.13.7,4.0.9,4.1.8,4.2.9,4.3.6` and `dry_run` off. CI stamps the artefacts `ci` and opens a bot PR labelled `lab-evidence`. `CF-OPS-UPGRADE-01` is **not** in that run: the workflow starts one single-node broker per version. It is recorded after the maintainer chooses how the workflow starts the upgrade cluster (Q-5; the 120-minute job limit and the cost are part of that decision, Q-20).
3. A maintainer reviews the bot PR (CODEOWNERS covers `testing/lab-evidence/**`) and merges it. Recorded evidence alone changes no registry data.
4. Re-run `pnpm nx run conformance:test --grep=CF-OPS --versions=<each>`: each fact is now `pass` or `fail`. A `fail` means the fact sheet, the hazard rule or the design is wrong; it is never fixed by weakening a scenario or a check. Examples a human would act on: the lab shows the quorum-queue `get` on a SAC queue is not refused on 3.13.7 (the fact becomes version-dependent, so it needs registry data, I-3); the vhost reset starts at a version other than 4.1.4 (the hazard's range is corrected); status and canary disagree after the upgrade (U-02 negative: keep the conservative rule, canary opt-in).
5. **There is no registry cell to flip.** The three hazard rules, the warnings and `resolveEra` have no `status`, `conformance[]` or `evidence[]`, so `semantics-evidence:check` has nothing to require and nothing becomes `lab-verified`. The maintainer decides (Q-1) between leaving the recorded evidence as the proof behind the fact sheet, or opening a follow-up issue that extends the schema in `libs/shared/semantics` (a CODEOWNERS-reviewed change) so that a hazard, capability or warning can name `conformance[]` and carry a status, and teaching `semantics-evidence` about it. Corrections to the fact sheet or to hazard ranges are separate, human-reviewed changes that cite the evidence path.
6. Any "lab-verified" wording elsewhere, and the `SEMANTICS_VERSION` bump (OQ-398), follow the release process, not this WP.
