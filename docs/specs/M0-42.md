# M0-42 Conformance CI workflows

**Issue:** #38 · **Milestone:** M0 · **Wave:** M0-W2 · **Size:** M by label, about 1,500 changed lines by estimate (over the 800 limit; see Risks, question Q-10) · **Owner area:** ci, conformance, semantics (lane: evidence) · **trust:critical:** yes

## Goal

Run the conformance matrix on every change that can affect it (five lab brokers, sharded, on the pinned Node, with a required check named `conformance`), run it nightly across Node 26.12, the Electron runtime and non-release broker builds, and prove nightly that the suite notices a broken registry by killing a listed set of mutants. This serves invariant I-14, amendments A-1, A-20 and A-23, DC-47 and DC-60, blueprint 5.2 ("Mutation testing of the suite") and section 14 (conformance row), and ADR-028.

The workflows only **run** the harness and the mutants. They never record evidence (that stays in `conformance-record.yml`, M0-71, A-20), never write to `testing/lab-evidence/**`, hold no write token and no secret.

## Slices

The scope is three independently landable slices. They share the project and the interfaces below; each can be one commit under #38 if the maintainer approves the size (Q-10).

## Files & interfaces

New Nx project `conformance-ci` in `tools/conformance-ci`, tags `type:test`, `runtime:node`, `trust:critical`. Make it with the generator, then run `pnpm install`:

```sh
pnpm nx g @app/generators:library conformance-ci --type=test --runtime=node --directory=tools --trustCritical --description="Plans, gates and reports of the conformance CI workflows, and the targeted-mutant runner (M0-42)."
```

The modules read the repository with Node built-ins only (like `apps/conformance/src/record/bundle-cli.ts`), so a workflow step can run them with `node` and no build. The one dev dependency of the project is `vitest`, already in the catalog.

**Create**

- `.github/workflows/conformance-pr.yml`: workflow `conformance-pr`. Triggers `pull_request`, `push` to `main` (the maintainer lands on `main` without pull requests) and `workflow_dispatch`. Top-level `permissions: {}`; every job `contents: read` only. Jobs:
  - `plan`: full-history checkout, `./.github/actions/setup`, then `node tools/conformance-ci/src/plan-cli.ts` with the base and head as environment variables; outputs `affected` and `matrix`.
  - `lab`: `needs: plan`, `if: needs.plan.outputs.affected == 'true'`, matrix from `fromJSON(needs.plan.outputs.matrix)`, `fail-fast: false`, `runs-on: ubuntu-24.04`, `timeout-minutes` set, Node from `.nvmrc` (24.22.0) through the unchanged `setup` action. Runs `pnpm nx run conformance:test --versions="$VERSION" --shard="$SHARD"` with both values passed as environment variables, never interpolated into `run:`.
  - `conformance`: the required check. `name: conformance`, `needs: [plan, lab]`, `if: always()`. It runs `node tools/conformance-ci/src/verdict-cli.ts` with the three results as environment variables and installs nothing.
- `.github/workflows/conformance-nightly.yml`: workflow `conformance-nightly`. Triggers `schedule` and `workflow_dispatch`. Jobs `plan`, `release` (every lab version on Node 24.22.0 and on Node 26.12.0, blocking), `alpha` (job-level `continue-on-error: true`, versions from the plan; empty until Q-5 is settled), the Electron-runtime leg (Q-6) and `report` (`if: always()`, writes the step summary and uploads the report artifact).
- `.github/workflows/mutation-nightly.yml`: workflow `mutation-nightly`. Triggers `schedule` and `workflow_dispatch`. Jobs `mutants` (the targeted mutants; blocking) and `stryker` (matrix `semantics`, `conformance`; uploads the Stryker reports).
- `tools/conformance-ci/src/plan.ts`, `plan-cli.ts`: the plan (below).
- `tools/conformance-ci/src/verdict.ts`, `verdict-cli.ts`: the aggregate decision of the required check.
- `tools/conformance-ci/src/nightly.ts`, `report-cli.ts`: the nightly legs and their report.
- `tools/conformance-ci/src/mutants.ts`, `run-mutants.ts`, `mutant.vitest.config.mts`: the listed mutants and the runner. A mutant is applied **in memory**, by a Vite `transform` hook that rewrites the module text while vitest loads it, so no file on disk changes and a parallel `nx affected -t test` cannot see a mutated file. The hook fails the run if the `from` text does not occur exactly once.
- `libs/shared/semantics/stryker.config.json`, `apps/conformance/stryker.config.json`: Stryker configs (below).
- `tools/conformance-ci/README.md`, `project.json`, `vitest.config.mts`, tsconfigs: from the generator (README filled in: purpose, public API, invariants, proof commands).
- `tools/supply-chain/conformance-workflows.ts`, `conformance-workflows-selftest.ts`: the hardening check of the three workflows and its self-test with planted violations (same method as `workflow-hardening.ts`).

**Modify**

- `.github/actions/setup/action.yml`: an optional input `node-version` (default empty). When set it is passed as `node-version` and `node-version-file` is left empty; when empty the action behaves as today (`.nvmrc`). Both are chosen by an expression in `with:` so the two never reach `setup-node` together. Nothing else changes; the record workflow's hardening check still passes.
- `.github/workflows/ci.yml`: add `conformance-workflows-selftest` to the "Gates self-tests" step.
- `tools/supply-chain/project.json`: target `conformance-workflows-selftest` (inputs: the three workflow files, the setup action, `conformance-workflows.ts`).
- `libs/shared/semantics/project.json` and `apps/conformance/project.json`: target `mutation` (`stryker run <config>`; not cached; reports to `dist/mutation/<project>`).
- `AGENTS.md` section 7, `apps/conformance/README.md`, `libs/shared/semantics/README.md`: the new commands. `docs/open-questions.md`: a section "Conformance CI workflows (M0-42)" with the questions below.

**Interfaces**

```ts
// tools/conformance-ci/src/plan.ts
export const CONFORMANCE_PROJECTS: readonly string[]; // semantics, conformance, adapter-amqp091, adapter-mgmt-http, broker-lab, testkit
export interface PlanInput {
  /** `nx show projects --affected` output, or null when it could not be computed. */
  readonly affectedProjects: readonly string[] | null;
  /** Files changed against the base, or null when unknown. */
  readonly changedFiles: readonly string[] | null;
  /** Versions pinned in testing/broker-lab/versions.json. */
  readonly versions: readonly string[];
  readonly shards: number;
}
export interface MatrixEntry {
  readonly version: string;
  readonly shard: string; // 'i/n', the form `conformance:test --shard` takes
}
export interface Plan {
  readonly affected: boolean;
  readonly reasons: readonly string[];
  readonly matrix: { readonly include: readonly MatrixEntry[] };
}
export function planConformance(input: PlanInput): Plan;

// tools/conformance-ci/src/verdict.ts
export type JobResult = 'success' | 'failure' | 'cancelled' | 'skipped';
export function verdict(input: {
  readonly affected: boolean | undefined; // undefined when the plan job did not finish
  readonly plan: JobResult;
  readonly lab: JobResult;
}): { readonly pass: boolean; readonly reason: string };

// tools/conformance-ci/src/nightly.ts
export type Runtime = 'node-24.22.0' | 'node-26.12.0' | 'electron-node';
export interface NightlyLeg {
  readonly runtime: Runtime;
  readonly channel: 'release' | 'alpha';
  readonly broker: string;
  readonly result: JobResult | 'not-available';
}
export function nightlyReport(legs: readonly NightlyLeg[]): {
  readonly markdown: string; // the step summary: one row per leg, never a green cell for a leg that did not run
  readonly exitCode: 0 | 1;  // 1 when a blocking leg did not succeed
};

// tools/conformance-ci/src/mutants.ts
export interface Mutant {
  readonly id: string;
  readonly project: 'semantics' | 'conformance';
  readonly file: string; // repository-relative
  readonly from: string; // must occur exactly once in the file
  readonly to: string;
  readonly why: string;
}
export const MUTANTS: readonly Mutant[];
export type MutantOutcome =
  | { readonly id: string; readonly status: 'killed'; readonly failingTests: readonly string[] }
  | { readonly id: string; readonly status: 'survived' }
  | { readonly id: string; readonly status: 'invalid'; readonly reason: string };
export function runMutant(mutant: Mutant, runTests: (m: Mutant) => { failed: readonly string[] }): MutantOutcome;
```

## Risks / questions

Nothing here is decided by the spec; the "proposed" values are what the spec assumes until the maintainer answers. The implementer adds these as rows in `docs/open-questions.md` (numbers assigned then).

- **Q-1. Five brokers on every PR, or the smoke from the plan?** The issue (system of record) and the execution plan (conformance matrix row: "affected PRs; full run nightly") say five versions on every affected PR. `docs/plan/plan.md` (CI gates) says that while the repository is private a 2-version smoke (4.2.9 and 4.3.6) runs on a self-hosted runner and the full matrix runs nightly. This spec follows the issue on hosted `ubuntu-24.04` runners (as `ci.yml`'s `amqp091-contract` job already does). Hosted minutes and anonymous image pulls from Docker Hub across ten parallel jobs are the cost.
- **Q-2. "Block the merge" without pull requests.** The maintainer lands on `main` directly (same conflict as OQ-430 and OQ-460). The workflow therefore also runs on push to `main`, and fails red there. A blocking required check exists only if a maintainer sets `conformance` as a required status check in the repository settings, which matters for outside contributors' pull requests.
- **Q-3. Shards and time limits.** Proposed: 2 shards (21 lab-cell spec files today, most still `it.todo`), so 10 jobs; `timeout-minutes` 45 for the lab job (the value the AMQP contract job uses). No run has been measured. A shard that selects no spec file must not fail a job (to be confirmed against the Vitest 5 behaviour in the implementation).
- **Q-4. What blocks.** `conformance:test` reports a cell with no recorded evidence as `unverified`: shown and skipped, never green, never failing. No evidence is recorded yet, so today the PR gate can only fail on a recorded disagreement or a broken harness. `--strict` (the release gate) is not used on PRs or nightly. Confirm; also whether the nightly should print the strict result as a non-blocking report.
- **Q-5. Alpha builds (OQ-81) and "feed the unverified state".** `versions.json` has no alpha entry, and the alpha packages are not Docker Hub tags. Until OQ-81 settles a source and a pinning rule, the `alpha` job takes an empty list and reports `not-available`. The spec reads "feed the 'unverified' state" as: the nightly report and artifact tell maintainers (and the new-broker-release runbook) which non-release builds ran and how; nothing automatic changes `profile.verification`, which is `unverified-minor` for any version without a green run by rule (blueprint 5.2). Confirm this reading, and which file (`versions.json`, owned by the pins in OQ-458, or a new file) holds the alpha list.
- **Q-6. Electron's Node.** The test-fused Electron binary (DC-46) does not exist before M2 (`apps/desktop` is absent). The spec proposes no stub: the leg is declared in the nightly and reported `not-available` with that reason, and a later WP (M2 packaging) wires `ELECTRON_RUN_AS_NODE=1 <binary>`. Confirm, or name the WP that owns the leg.
- **Q-7. Node 26.12.0.** Proposed: a failure on Node 26 turns the nightly red (only alphas "may fail"), and the `setup` action gets the optional `node-version` input. Unconfirmed: that every install and native add-on works on Node 26.12.0 (the platform lane, OQ-131, has not run the upgrade), and that the hosted runners provide that exact version.
- **Q-8. Which mutants, exactly.** "Drop a W-* gate" is not defined anywhere; the spec proposes M-3 (a `block` warning downgraded to `warn`). Other readings: a `GateRule` removed from the capability gates, or a W-* entry deleted. M-1 as written is killed largely by load-time data validation (ten suites fail to load), which proves the registry is checked but not that a behavioural test notices a swapped settle action; a mutant that keeps the registry valid would be stronger. M-4 is added because A-1 and ADR-028 ask for it; confirm. The other five blueprint mutants wait for the peek planner and executor.
- **Q-9. Stryker.** (a) Stryker 10.0.0 declares `vitest >=2.0.0` as a peer, but a run against Vitest 5.0.5 is unproven here; if it fails the targeted mutants still stand as the gate and slice C reports Stryker as not run. (b) No mutation-score threshold is invented; propose to set `break` after the first nightly baseline. (c) Transitive packages may need an ADR-027 exclusion (maintainer).
- **Q-10. Size.** Estimated changed lines (excluding the lockfile and generated project files): workflows about 380, `tools/conformance-ci` sources about 550, its tests about 450, `tools/supply-chain` check and self-test about 300, docs and configs about 100, so about 1,500, against the 800 limit. Options: land as the three slices (about 650, 450 and 450 lines) as three commits, each still `Closes`-free until the last, with `oversize-approved` on #38; or split into three new issues (ADR-033: no work without an issue). Slice C also cannot finish before the maintainer applies the dependency change.
- **Q-11. A new project.** The runner and the plan are not harness code (the recorder must not depend on the registry, `checkRecorderIndependence`), so the spec puts them in a new `tools/conformance-ci` project. Alternative: extend `tools/supply-chain`. Also a CODEOWNERS line for the new path (protected; proposed above).
