# M0-46 svc-capabilities: gates, hazards, era and verification (CON-03 part 2, MSG-01 integration)

**Issue:** #42 · **Milestone:** M0 · **Wave:** M0-W3 · **Size:** M · **Owner area:** engine, semantics, ci · **trust:critical:** no (see "Risks / questions": it becomes yes if the gate rules are added to `libs/shared/semantics`)

## Goal

Every feature gate in `BrokerProfile.gates` carries a why-disabled reason with a source, and every profile carries its era and verification state with the reasons shown. The engine also computes the per-principal `allowedActions` that `profile.get` sends, so the UI renders gates and never computes authorisation.

Serves: CON-03 (capability probe and BrokerProfile, part 2), MSG-01 (era resolver integration), DC-31 (every gate shows a why-disabled reason with a source), DC-32 (gate on version, flags and stats mode), DC-01 and DC-02 (conservative era, unknown builds fall back to 4.0-4.2), DC-60 (verification state). Blueprint 5.1 steps 4 and 5, 5.2, 7 (UI never computes authorisation). Invariants I-3 (version-dependent behaviour is registry data), I-10 (no secret or broker text in a profile), I-14 (nothing here sets a cell status or writes evidence).

## Files & interfaces

**Feature catalogue** (the ids are `FeatureId`s, a branded non-empty string; the set below is the proposal this WP implements, Q-3 asks the maintainer to confirm it):

| Feature id | Closed when (otherwise open) | Source of the reason |
| --- | --- | --- |
| `streams.browse` | product is not RabbitMQ family, or `streams.supported` is false (stream plugin not seen, or the provider preset blocks streams) | provider preset citations (fact sheet j.1) |
| `tap.firehose` | `firehose.available` is not `tracing-plugin` (`runbook-only` and `none` are closed; the reason says which) | provider preset citations, or the probe step (`10-exchanges`, node plugin list) |
| `audit.event-exchange` | the preset's `eventExchange` is `blocked`, or the `rabbitmq_event_exchange` plugin is not listed on any node, or the plugin list is unknown (statistics off lists no plugins, OQ-431) | provider preset citations, or the probe step |
| `policies.operator-edit` | `restrictions.operatorPolicyChanges` is `disabled` or `unknown` | the overview flag `is_op_policy_updating_enabled` or the provider preset; Amazon MQ adds the remediation text |
| `amqp.peek`, `amqp.tap`, `amqp.publish`, `amqp.replay` | the AMQP handshake (probe step 12) did not succeed | the probe step, reason from the failure class only (never the broker's text, I-10) |

**Interfaces**

```ts
// Introduced in libs/engine/svc-capabilities/src/gates/index.ts
import type { FeatureId, GateDecision } from '@app/contracts';
import type { BrokerProfile } from '@app/domain-model';
import type { BrokerSemanticsRegistry } from '@app/semantics';
import type { Facts } from '../probe/types';

/** The features this package decides, in a stable order. */
export const FEATURES: readonly FeatureId[];

export interface GateInput {
  /** The profile without gates: what the builder has so far. */
  readonly profile: Omit<BrokerProfile, 'gates' | 'fingerprint' | 'probedAt'>;
  readonly facts: Facts; // only for the AMQP handshake outcome; no free text of it is copied
  readonly registry: BrokerSemanticsRegistry; // providerPreset(...) and capability(...)
}

/** Every id of FEATURES is in the result. A decision that cannot be reached is closed with a reason. */
export function computeGates(input: GateInput): Record<FeatureId, GateDecision>;

// Introduced in libs/engine/svc-capabilities/src/gates/allowed-actions.ts
import type { ActionId, EngineMode, EnvClass, Permission } from '@app/contracts';
import type { Authorizer } from '@app/kernel';
import type { Principal } from '@app/ports';

export type ActionFeatures = Readonly<Record<string, readonly FeatureId[]>>;

export interface AllowedActionsInput {
  readonly profile: BrokerProfile; // with gates
  readonly principal: Principal;
  readonly mode: EngineMode;
  readonly env: EnvClass;
  readonly authorizer: Authorizer;
  readonly actions: readonly { id: ActionId; permission: Permission }[]; // from the contract registry
  readonly featuresOf: ActionFeatures; // an action not listed needs no feature
}
/** Actions the principal holds the permission for AND whose every feature is open. Sorted by id. */
export function computeAllowedActions(input: AllowedActionsInput): Promise<ActionId[]>;

// Introduced in libs/engine/svc-capabilities/src/era.ts
export function eraOf(input: {
  nodeVersions: readonly (SemVer | null)[];
  ff43: 'enabled' | 'disabled' | 'unknown';
  build: Build;
  family: boolean;
  product: Product;
  lastVerified: readonly string[];
  registry: BrokerSemanticsRegistry;
}): Pick<BrokerProfile, 'era' | 'verification'>;

// Consumed (unchanged)
// @app/contracts:      GateDecision { enabled; mode?: 'full' | 'degraded'; reason?; source?; fix? }, FeatureId, ActionId, registry
// @app/domain-model:   BrokerProfile (gates, era, verification, allowedActions?), BrokerProfileSchema
// @app/semantics:      registry.providerPreset(target, version), registry.resolveEra(...), registry.capability(...), registry.gate(...)
// @app/kernel:         Authorizer, AuthorizationRequest, denyAllAuthorizer
// Probe facts (M0-45): Facts.amqp (AmqpHandshakeResult), BrokerProfile.{streams, firehose, restrictions, nodes[].enabledPlugins}
```

Rules the implementation follows (each is also covered by an AC):

- **Fail closed.** A feature the code cannot decide, or whose evidence is unknown, is `enabled: false` with a reason that says what is not proven. A missing catalogue id is a bug: `computeGates` returns every id of `FEATURES`.
- **Reason and source on every closed gate.** Both are non-empty; `source` names the provider preset citation, the fact sheet row or the probe step. Open gates carry `mode: 'full'` and, when a preset is the reason a feature is only `partial`, `mode: 'degraded'` with the reason.
- **No version comparison here (I-3).** Version-dependent answers come from `registry.capability`, `registry.providerPreset(target, versions.min)` or `registry.gate` (which may be a `SemanticsGapError` for an id with no rule: handled by closing the gate, never by a default that opens it).
- **No broker text, no URL, no credential in a reason or source (I-10).** Reasons are fixed strings and registry text; a failed handshake contributes its failure class only.
- **The profile stays deterministic.** Same facts give the same `gates` (same key order, same text), so the fingerprint is stable and a plan is not marked stale without cause.
- **`allowedActions` is per principal and never stored or fingerprinted.** It is `[]` unless the authorizer says yes for the action (deny by default) and every feature the action needs is open.

## Risks / questions

Open questions for the human; this spec does not decide them. Each has a default that the spec uses so it can be implemented, and the default is recorded in `docs/open-questions.md` in the new section. The ids are proposed; take the next free range when writing them.

- **Q-1 Where do the gate rules live (I-3)?** `GateRuleSchema` (`libs/shared/semantics/src/gates.ts`) can test versions, products, feature flags and statistics mode but not a provider preset's support level or a profile field (`firehose.available`, `restrictions.operatorPolicyChanges`, plugin lists), and the shipped table is empty. Default used here: the decision functions live in `svc-capabilities/src/gates/features.ts` and read `registry.providerPreset`, `registry.capability` and the profile; `registry.gate` is consulted only if a rule exists for the id (a gap closes it). Alternative: extend `GateRuleSchema` with a preset-support condition and ship the rows as data. That changes `libs/shared/semantics` (`trust:critical`, `@RafaelJCamara` in CODEOWNERS), would need the adversarial review, and about +150 lines; the WP would then become `trust:critical: yes`.
- **Q-2 Where does the 405 remediation text live?** `GateDecision` has `reason`, `source` and a `fix` that must be an `ActionId`; no action exists to fix an operator-policy restriction, and UI strings are i18n keys while engine reasons are English strings (as in the registry). Default: the remediation is part of `reason`, `fix` is absent. Alternatives: a `remediation` or `reasonKey` field in `GateDecisionSchema` (a contracts change, regenerates the OpenAPI document) or an i18n key convention.
- **Q-3 Is the catalogue right and complete?** The issue names streams, firehose, event audit and operator-policy edits; the id spelling (`streams.browse`, `tap.firehose`, `audit.event-exchange`, `policies.operator-edit`; the `amqp.*` four from OQ-445) is mine, taken from the `FeatureId` comment in the architecture proposals ('streams.browse', 'tap.firehose', ...). Not included: Prometheus, definitions export, quorum replica operations, shovels, OAuth2. The maintainer confirms or extends the list; a feature added later is one function and one AC.
- **Q-4 What does "firehose disabled" mean?** The Amazon MQ preset marks firehose `probe` (unknown until probed), not `blocked`, and the fact sheet row reads "U to P (admin; node-local behind the NLB; no tracing plugin)". Default: the gate is open only on positive evidence (`firehose.available === 'tracing-plugin'`); `runbook-only` (the tool can only show instructions) is closed with a reason that says so. Related uncertainty for M0-45's builder: the `4.2.9` recording lists the trace exchange together with the tracing plugin, and the builder reads the exchange as evidence; whether that exchange exists without the plugin is not established by anything in this repository. If it does, the builder's `firehose` field is too generous and is a separate issue.
- **Q-5 Do hazards close gates?** The title says "hazards", but M0-45 already fills `profile.hazards` (`registry.hazards(slice)`), and `HazardRule` carries no link to a feature. This spec changes nothing about hazards. If a hazard should close or degrade a gate (for example `channels-400-stats-off` for a channel list), the rule needs a `gates: FeatureId[]` link in the registry (a semantics change, as Q-1), and the list of features that depend on it.
- **Q-6 Which features does an action depend on, and where is that written?** `ActionDef` has no feature link, and no registered action needs a gate today, so the default table (`ActionFeatures`) is empty and AC-10 supplies its own. Alternative that fits ADR-003 better: an optional `requires: FeatureId[]` on `defineAction` (contracts change, OpenAPI drift gate). Until then `allowedActions` equals the permitted actions.
- **Q-7 Era and verification are already built by M0-45** (`registry.resolveEra`, tested in `capabilities.spec.ts` and `era.spec.ts` of `semantics`). The issue's second criterion therefore adds profile-level regression tests plus the extraction into `era.ts`, not new behaviour. Confirm that this is the intended reading of "era.ts" in the scope line, or drop the extraction and keep only the tests.
- **Q-8 `allowedActions` needs the principal, mode and environment class**, taken from `ActionContext` (`principal`, `mode`, `env`). The module gains an optional `authorizer` dependency; the composition root (OQ-472) must pass the one the executor uses, or the field stays `[]`. Confirm that `profile.get` (not a new action) is the place.
- Related decisions that stay open and are not decided here: OQ-478 (`lastVerified` source), OQ-472 (module registration), OQ-445 (the `amqp.*` stand-ins), OQ-431 (no plugin list with statistics off, which is why event audit closes there), OQ-476 (provider rules).
- **Protected paths:** none needed. No dependency, no `testing/lab-evidence/**`, no CODEOWNERS or workflow change.
- **Size:** about 700 changed lines excluding fixtures (about 330 source: gates 220, allowed actions 70, era 40, builder and action edits 30; about 380 tests; README and open-question text about 70 on top). Under the 800 limit, with little margin. If it grows, split `allowed-actions.ts` and AC-10 and AC-11 into a follow-up work package; the gates and era part stands alone.
- **trust:critical:** no, as long as Q-1 keeps the rules in the service. The gates feed the `ProfileResolver` that refuses actions (blueprint 5.1 step 5), so the review should still check that no code path opens a gate on missing evidence.
