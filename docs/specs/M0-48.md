# M0-48 svc-explorer: inventory windows, overview, explorer.window topic (EXP-02/03 engine, S-13)

**Issue:** #44 · **Milestone:** M0 · **Wave:** M0-W3 · **Size:** L by label, about 3,200 changed lines by estimate (eight slices, each with a hard budget of at most 600 and each proposed as a child issue; see "Slices" and Q-2) · **Owner area:** engine, desktop-win, conformance · **trust:critical:** yes by the issue label (see Q-1: the blueprint list and CODEOWNERS do not name this module)

## Goal

A new engine service, `svc-explorer`, that answers the explorer from an engine-resident, bounded inventory instead of from the broker: windowed `inventory.query`, a cheap `overview.get`, and the `explorer.window` live topic (snapshot-delta, deltas only for the keys the UI shows). It stays correct with management statistics off and keeps the broker load small at 20k to 100k queues, and the S-13 measurements (management API cost at 100k queues) are recorded in an ADR-024 addendum.

Serves: EXP-02 (inventory grids) and EXP-03 (cluster overview), the engine side only (the UI is M0-54). DC-32 (stats-off requests: `disable_stats` with `enable_queue_totals`, never trust a field that stats-off drops), DC-48 (always page, 500 at most), DC-31 (the overview names a degraded resource). Invariants I-6 (bounded index and rings, counted drops), I-7 (windowed queries only, no "list all"), I-8 (one background request per broker, interactive pre-empts background, via the `BrokerScheduler`), I-13 (no silent loss: partial, stale, truncated and dropped are in every answer), I-10 (no broker text or secret in an answer), I-3 (no version comparison here), I-5 (event-loop budget, measured, see Q-13). ADR-003, ADR-005, ADR-024. Blueprint 3.2 (resource map, `explorer.window`), 8 (BrokerScheduler), scale-first 8.1 (inventory sweeps, index structures) and 10 (grid live updates).

How the pieces behave (each rule is covered by an AC):

- **Windows come from the index, not from the broker.** `inventory.query` does no management request on a warm index. Filter, sort and window are computed in the engine: the filter is a substring of the name (case-insensitive) plus exact facets; a sort is a cached permutation per (version, kind, column, direction), bounded to a small number of entries (Q-13). Rows keep their key (`encodeObjectKey(vhost, name)`; a connection with no vhost uses the empty vhost).
- **The sweeper is the only code that lists the broker, and it lists in the `background` lane.** Per sweep: `GET /api/vhosts` (a bare array, not paged), then for each vhost and each kind a paged list (`/api/queues/{vhost}`, `/api/exchanges/{vhost}`, `/api/connections` for connections) with `page_size: 500`, `disable_stats: true`, `enable_queue_totals: true` on the queue list, and the row columns the adapter adds. The service passes only what it needs and relies on the adapter for `columns`, clamping and dropping unsupported flags. A sweep builds into a staging area and installs one kind at a time as a new version, so a half-read kind is never visible as complete. A failed or partial sweep never replaces a good version: the old rows stay and the answer is `stale` (AC-4).
- **Cadence.** The next sweep starts `clamp(30 s, 15 min, 50 x the server time of the last sweep)` after the last one ended; the first sweep starts at once on demand; no demand for `idleStopMs` stops it; `stop()` ends every sweep and aborts the request in flight. The server time is the sum of the request durations the sweeper measured with the injected `Clock`.
- **Cold start.** Until the first sweep has installed a kind, `inventory.query` answers from what has been installed (possibly nothing) with `freshness.state: 'loading'`, `complete: false`, `loaded` and `expected` (from the profile's last overview or the sweep's own count): it never blocks on the sweep and never claims the loaded subset is the whole inventory (AC-8). Filters and sorts then apply to the loaded rows only, and the answer says so (Q-4).
- **Stats off.** The rows are what the broker sent: a field that stats-off drops (policy fields below 4.2.5, static connection information below 4.2.6) is absent, never defaulted or guessed, and the registry hazard ids from `profile.hazards` that concern the kind are copied into `freshness.hazards` so the UI can say why a column is empty (AC-9, Q-22). Message counts come from `enable_queue_totals`; per-queue rates are never offered by this module.
- **Visible-key deltas.** `explorer.window` follows installs: for each install it publishes only the upserts whose key is in the subscription's `keys` (the source compares the new version with the previous one per key) and removes a visible key that has left the inventory; a version marker item (`key: '~version'`) is published when membership changed so the grid can refresh its cache (Q-6). Coalescing, pacing (2 Hz), bounds and overflow are the hub's (`latest` outbox, `maxHz`, `gap` then `snapshot`).
- **Errors are Problems.** An unknown or invisible connection is `NOT_FOUND` (the same answer for both, so existence is not leaked); a connection with no cached profile is `NOT_FOUND` ("run the probe first", as `profile.get`); a request over a cap is `VALIDATION_FAILED`; a refused scheduler slot is `BUDGET_EXCEEDED`; a sweep failure is data (`freshness`), not a thrown error, when an older index exists.

## Risks / questions

Every question below is also a row in `docs/open-questions.md`, section "Spec questions: M0-48" (Q-n is OQ-(652+n) as of this commit). None is decided here: each has a default that this spec uses so it can be implemented, and the row says what the maintainer must answer.

- **Q-1 `trust:critical` and CODEOWNERS.** The issue carries the label, but blueprint 2.1 and `CODEOWNERS` do not name `svc-explorer`. Default: follow the label (the module is generated with `--trustCritical`, the review includes the adversarial pass, no change lands without the maintainer's approval) and propose the CODEOWNERS line `/libs/engine/svc-explorer/ @RafaelJCamara`. CODEOWNERS is a protected path, so a maintainer applies it, or removes the label.
- **Q-2 Size.** About 3,200 changed lines by estimate against 800 (AGENTS.md section 5). Default: eight child issues with the hard budgets and cuts of "Slices"; `oversize-approved` is not asked for. Same family as OQ-545 and OQ-634.
- **Q-3 Window shape (OQ-546).** Default: `offset` and `limit` (at most 500, default 200) plus an optional pinned `version`, defined here in `@app/contracts` so `ui-grid` (M0-53) adapts to it; a cursor is the alternative, but the grid's infinite model asks by row range. The type lives in `@app/contracts`, not in `ui-grid` or `ui-data`.
- **Q-4 Serving model and cold start.** Default: windows come from the resident index; the first query starts the sweep and is answered from what is loaded, labelled `loading` and `complete: false`. Alternative: an interactive-lane passthrough page (server-side name filter and sort) until the first sweep is complete, which costs one broker request per window and re-sorts the full list on the broker for every page (scale-first 8.1).
- **Q-5 Visible keys.** Default: `params.keys` (at most 500) and a resubscribe (`unsub` then `sub`) when the visible set changes, debounced by the client at 100 ms; no protocol change. Alternative: a new client frame that replaces the params of a subscription, or an action that sets them, which changes `live-frames.ts` and the hub.
- **Q-6 Version marker.** Default: the reserved key `~version` in the same topic (an item without `row`). Alternative: a separate `status` use or a second topic.
- **Q-7 What "overview totals from `enable_queue_totals`" means.** The 4.2.9 stats-off overview has no message totals at all, and the adapter drops `enable_queue_totals` on `/api/overview`. Default: message totals are the sum over the queue-list sweep (`source: 'queue-sweep'`, with `asOf` and `complete`), as old as the last sweep. Confirm, or name another source.
- **Q-8 Alarm source and shape.** No recording holds an alarm and stats-off `/api/nodes` drops resource information. Default sources: the per-node alarm flags of `/api/nodes` (`mem_alarm`, `disk_free_alarm`, named from the broker's HTTP API and not from anything in this repository) when present, then `/api/health/checks/alarms`; an alarm that cannot be attributed to a node and a resource is reported as `unknown`, never as none or as a guess (AC-14). The AC-13 shape is assumed. Needed: a recorded alarm (a lab broker with a raised memory or disk alarm, replayed by `record-golden`), or the Prometheus alarm gauges once a reader exists. Not recorded here: `testing/broker-lab` and `testing/lab-evidence/**` are not touched.
- **Q-9 Rates.** Default: stats on, rates from the broker overview (`available`, `source: 'broker-overview'`); stats off, `unavailable` with `reason: 'statistics-off'`; per-queue rates never. Prometheus-derived rates arrive with the metrics work packages.
- **Q-10 Sweep strategy and S-13.** Default: per vhost, paged at 500, `disable_stats` and `enable_queue_totals`, as scale-first 8.1. S-13 measures per-vhost against global, page sizes 100, 200 and 500, and an unpaged request made by the lab script outside the engine. The adapter cannot send an unpaged list (DC-48), so adopting "unpaged" is a decision for the adapter and not for this WP.
- **Q-11 Cadence, demand and warm start.** Default: the formula of blueprint 8 (`clamp(30 s, 15 min, 50 x last sweep server time)`), first sweep on first demand, idle stop at 10 minutes (the "hot" definition of scale-first 9), no persisted snapshot. Confirm the numbers.
- **Q-12 Limits.** Defaults: 250,000 rows and 128 MiB per connection (the blueprint's 1M rows is the team total), 5,000 vhosts per sweep, topic ring 1,000 items and 1 MiB, `maxHz` 2, window 200 default and 500 maximum, search 50 results. Confirm.
- **Q-13 In-process index and the event loop.** The blueprint puts the index in a worker (I-5, p99 at most 20 ms under sweep and tap load); the issue names `internal/index.ts`, with no worker. Default: in-process, with sort permutations cached per (version, kind, column, direction) and at most a few kept, and AC-24 asserts p99 at most 20 ms at 20,000 and only prints 100,000. A sort of 100,000 rows may exceed the budget; if S-13 shows it does, a worker or a chunked sort becomes a new issue.
- **Q-14 Regex filter.** Default: no regex in the engine. The filter is substring plus facets. A regex over 100,000 names on the event loop is a denial-of-service risk, and a safe engine for it (a linear-time matcher) is not in the catalog; adding one is a dependency decision (AGENTS.md section 4).
- **Q-15 Kinds.** Default: `queues`, `exchanges`, `connections` (slices A to C), `bindings` as slice H (a vhost is required, on demand, with a resident cap of 500,000 rows per scale-first), nothing else.
- **Q-16 Names, permission and exposure.** Default: `inventory.query` (`POST /connections/{cid}/inventory/queries`), `overview.get` (`GET /connections/{cid}/overview`), `search.query` (`POST /connections/{cid}/search`), topic `explorer.window`, all with permission `broker.read` (blueprint 7.3), no MCP and no CLI.
