# M0-48l Bounded streaming reader for bare-array management lists (bindings)

**Issue:** #272 · **Parent:** #44 (M0-48), follow-up of #269 (bindings kind) · **Milestone:** M0 · **Wave:** M0-W3 · **Size:** M by label, about 1,100 changed lines by estimate (four slices, each a proposed child issue; see "Slices" and Q-13) · **Owner area:** engine, adapters · **trust:critical:** no for the new project and the adapter spec (Q-9); the `svc-explorer` part is covered by its existing CODEOWNERS line

Checked against the worktree at `ba9e103` (5d8a9fd, the OQ-688 correction, is on `main`). The spec changes no code in `libs/engine/ports` or in the adapter's behaviour: Q-3 writes down the optional change a maintainer may still want there.

## Goal

Read the bindings of one vhost as a stream, parse it incrementally and stop at `ExplorerLimits.maxBindingsResident`, so that the bytes held at any moment are one chunk plus one item (not the whole answer), a vhost with more than about 75,000 bindings can be read, a vhost with more bindings than the cap is cut at the cap instead of being read to its end, and every failure (truncated JSON, a bad item, too many bytes, too slow) fails closed with a fixed-text Problem.

Serves: EXP-02 (the bindings kind of the explorer, engine side), I-6 (a buffer bounded by items and bytes, a drop that is counted), I-7 (a windowed answer from a bounded set), I-8 (the stream holds one `interactive` slot and gives it back), I-5 (the parse is chunked and yields to the event loop), I-10 (no broker text in any error), I-13 (what was left out is said, and when the number is not known, that is said too). DC-48 (always page), OQ-433, OQ-686, OQ-688. Blueprint 8 (BrokerScheduler), scale-first 8.1.

// Introduced in libs/shared/json-stream/src/errors.ts (slice A)
export type JsonStreamReason =
  | 'not-an-array' // array() on a body whose first significant byte is not `[`
  | 'malformed' // not JSON where the array requires it (bad item, bad separator, bad UTF-8)
  | 'truncated' // the source ended before the closing bracket
  | 'too-large' // maxBytes, maxItemBytes or a value() ceiling passed
  | 'too-deep' // nesting inside one item deeper than maxDepth
  | 'trailing-data' // a non-blank byte after the closing bracket
  | 'aborted'; // the signal fired
export class JsonStreamError extends Error {
  readonly reason: JsonStreamReason;
  /** Bytes taken from the source when the fault was found. A position, never content. */
  readonly offset: number;
  /** Items delivered before the fault. */
  readonly delivered: number;
  // `message` is one fixed text per reason; it never contains input bytes.
}

// Introduced in libs/shared/json-stream/src/reader.ts (slices A and B)
export interface ArrayLimits {
  /** Items delivered. Must be at least 1. */
  readonly maxItems: number;
  /** Bytes taken from the source, whatever they are. */
  readonly maxBytes: number;
  /** Bytes of one item. */
  readonly maxItemBytes: number;
  /** Nesting inside one item. Default 64. */
  readonly maxDepth?: number;
}
export type ArrayEnd =
  /** The closing bracket was seen: `items` is the exact length of the array. */
  | { readonly kind: 'complete'; readonly items: number; readonly bytes: number }
  /** `maxItems` delivered and one more item follows: the length is not known and is at least `items + 1`. */
  | { readonly kind: 'item-limit'; readonly items: number; readonly bytes: number };

export interface OpenOptions {
  readonly signal?: AbortSignal; // slice B
  /** Default 262_144. Slice B. */
  readonly yieldEveryBytes?: number;
  /** Default 5_000. Slice B. */
  readonly yieldEveryItems?: number;
  /** Lets the event loop run. Default `() => new Promise((r) => setTimeout(r, 0))`. Slice B. */
  readonly yieldNow?: () => Promise<void>;
}
export interface JsonStream {
  /** From the first significant byte: `[` array, `{` object, anything else other, nothing but blanks empty. */
  readonly shape: 'array' | 'object' | 'other' | 'empty';
  /** Delivers the items one by one; `return()` (a `break`) cancels the source. Needs shape 'array'. */
  array(limits: ArrayLimits): AsyncGenerator<unknown, ArrayEnd, undefined>;
  /** Buffers the rest of the body, at most `maxBytes`, and parses it. For an envelope (slice B). */
  value(maxBytes: number): Promise<unknown>;
  /** Cancels the source if nothing consumed it. Safe to call twice (slice B). */
  close(): Promise<void>;
}
/** Reads up to the first significant byte (blanks may span chunks), then stops pulling. */
export function openJson(source: AsyncIterable<Uint8Array>, options?: OpenOptions): Promise<JsonStream>;

### How the pieces behave (each rule is covered by an AC)

- **A scanner, then the platform's own `JSON.parse`.** The scanner walks the bytes of one top-level array and finds where each item starts and ends: a state machine over `"` (in string), `\` (escape inside a string), `[` `{` (deeper), `]` `}` (shallower) and `,` (item boundary at depth 0). The structural bytes are ASCII and never occur inside a multi-byte UTF-8 sequence, so scanning bytes is exact and no text is decoded for the bytes that are skipped. Each finished item is cut out (copied only when it crosses a chunk boundary), decoded with a fatal `TextDecoder('utf-8')` and parsed with `JSON.parse`. A bad byte sequence or bad JSON in an item is `malformed`. Between items the scanner checks the separators: an empty item (`[1,,2]`, `[1,]`) is `malformed` because `JSON.parse('')` throws and the empty slice is not allowed; two items without a comma (`[1 2]`) are one slice that does not parse; bytes after the closing bracket that are not blank are `trailing-data`; the source ending before the closing bracket is `truncated`. The scanner counts brackets without pairing their kinds, so a mismatch such as `{"a":[1}` leaves the depth wrong: the slice then does not parse (`malformed`), or the body ends first (`truncated`), or the item reaches `maxItemBytes` (`too-large`). Whichever comes first, the read fails closed and delivers nothing past that item.
- **Bounds.** At most `maxBytes` bytes are taken from the source in total; a body larger than that is `too-large` (the scanner stops at that byte, so no item that ends past it is delivered). One item may not exceed `maxItemBytes` (`too-large`) and its nesting may not exceed `maxDepth` (`too-deep`, counted before `JSON.parse` runs, so a deeply nested body never reaches the recursive parser). What the reader holds at any moment is the current chunk, the item being assembled (at most `maxItemBytes`) and nothing else: it never holds the whole array.
- **Stop at the item limit, and say what is not known.** After the `maxItems`th item the reader looks one separator ahead: `]` ends the array with `complete` and the exact length (an array of exactly `maxItems` items is complete, not cut); `,` followed by another item start means at least one more item exists, and the reader returns `item-limit`, stops pulling and cancels the source. It does not read the rest and does not count it, so after an `item-limit` the length of the array is not known. A `,` followed by `]` is `malformed`.
- **Early stop cancels the HTTP body.** The generator's `finally` calls the source's `return()`. Through `scheduleMgmtRead` that releases the scheduler slot and the adapter's generator destroys the response, which closes the socket. No `AbortSignal` is needed for that; the signal is for the caller's cancellation and the deadline.
- **Abort and silence.** The pull loop races the source's `next()` against the abort, so a body that stops sending is ended by the signal and not only when the next chunk arrives. The service passes the same signal to `mgmt.stream`, so the request itself is aborted too (the scheduler's task signal reaches the adapter's `req.destroy()`).
- **Chunked work (I-5).** The scanner works on one chunk synchronously and the loop yields to the event loop after every `yieldEveryBytes` (256 KiB) scanned or `yieldEveryItems` (5,000) delivered, whichever comes first. The cost of scanning is linear in the body; it is not measured yet (AC-15 measures it).
- **Shapes (slice B).** `openJson` reads up to the first non-blank byte and reports the shape, and the caller chooses: `array()` for `[`; `value(maxBytes)` for `{` (the paged envelope: at most 500 items, so it is buffered, bounded by `maxBindingsEnvelopeBytes`) or anything else. `array()` on a body that is not an array is `not-an-array` and delivers nothing.
- **The glue (`readBoundedList`, slice C).** It opens a timer for `deadlineMs` with the injected `Timers`, links it with the caller's signal (`AbortSignal.any`), calls `mgmt.stream` with that signal, sniffs the shape and reads either the items or the envelope. It collects the items in a local array and returns them only when the read ended well (`complete` or `item-limit`); on any error nothing is returned. `JsonStreamError` and the adapter's errors are turned into `AppError` with a fixed `detail`: "The answer of the broker was not a complete list." (`not-an-array`, `malformed`, `truncated`, `trailing-data`), "The answer of the broker was larger than the limit." (`too-large`, `too-deep`), "The bindings of the vhost could not be read in time." (the deadline). An adapter error that already carries a known error code keeps its code and gets the existing fixed text ("The bindings of the vhost could not be read."). The shutdown abort keeps `ENGINE_SHUTTING_DOWN`.
- **The bindings store (slice C).** `read(cid, vhost)` calls `readBoundedList` with `{ page: 1, page_size: 500 }` (the same query as today) in the `interactive` lane. Each item is checked with the existing binding item schema; one that fails is a fail-closed `malformed` (the whole read is refused, as a bad page is today). An `array` result becomes rows up to the cap: `complete` gives `expected` = the length and `dropped` = 0 (the length cannot exceed the cap by more than the cut); `item-limit` gives `truncated`, `dropped` = 1 as a minimum, `expected` absent and `countExact: false`. An `envelope` result goes through the existing envelope schema and the existing paging loop (a page number up to `page_count`, early stop at the cap when `total_count` says what is left, `expected` and `dropped` exact), with each further page a streamed GET of at most `maxBindingsEnvelopeBytes`. A failed read installs nothing; a resident vhost is served `stale` (as today); a vhost never read raises the Problem. At most `maxBindingReadsPerConnection` streams are open for one connection; the others wait for a free place (the single flight per vhost stays), and `stop()` aborts the waiting and the open ones.
- **What the answer says.** A cut read keeps `state: 'live'` and `complete: true` of the version (what was read is all that is resident), `truncated: true`, `dropped` the minimum, `expected` absent and a fixed `reason`: "The broker sent every binding of the vhost in one answer, without paging; the read stopped at the limit and the number left out is not known." An exact unpaged answer keeps the existing text. The numbers are never presented as a count when they are a minimum (Q-5).

## Out of scope

- Any change to `libs/engine/ports` (`MgmtStreamRequest`, a `maxBytes` or a `deadlineMs`) or to the adapter's behaviour (a byte ceiling or a body deadline in `stream`). The exact optional change is written under Q-3; the reader and its caller enforce both limits without it.
- The scheduler's `holdMs` watchdog releasing a slot without aborting the body (Q-4 records it; this reader stays under it with its own deadline).
- A contract change: no new field in `FreshnessSchema`; the minimum count is carried by `truncated`, `dropped` and the fixed `reason` (Q-5). `contracts:api-docs-check` must stay clean without a regeneration.
- Other lists. The reader is generic and lives in a shared project, but this WP adopts it for bindings only (Q-8): `/api/vhosts` in the sweeper stays a `get`, and consumers (OQ-433), policies, permissions and the per-queue and per-exchange binding lists have no engine reader yet. A reader added later for one of them uses `readBoundedList` and does not use `get` for a list that is a bare array.
- Counting what the cap left out (reading the rest of the body without keeping it, up to a budget). Q-5 describes the alternative and its cost.
- A byte bound on the resident rows (OQ-686 (3)), the answer-at-once `loading` window for the first bindings query (OQ-686 (1)), per-queue or per-exchange binding reads as a way to read a big vhost in pieces, a persisted cache.
- Moving `readBoundedList` into `@app/kernel` for reuse by other services (Q-8: when a second consumer exists).
- Registering the module in `coreModules` (M0-48 Q-17) and any UI.

## Risks / questions

Every question below is also a row in `docs/open-questions.md`, section "Spec questions: M0-48l" (Q-n is OQ-(709+n); OQ-700 to OQ-709 are reserved for M0-53). None is decided here: each has a default that this spec uses so it can be implemented, and the row says what the maintainer must answer.

- **Q-1 Where the reader lives.** Default: a new `type:pure`, `runtime:isomorphic` project `json-stream` (`libs/shared/json-stream`). A service may import it, the adapter's specs may import it, and a later service (consumers, M2-F02) may reuse it. Alternatives: `internal/` of `svc-explorer` (no new project, no reuse; the adapter spec could not import it), `@app/domain-model` (wrong subject), `@app/kernel` (`type:kernel` is not allowed in the adapter's specs).
- **Q-2 Hand-written or a dependency.** Default: hand-written scan-and-`JSON.parse`-each-item (about 300 lines with tests, no dependency, every limit under our control). A dependency would also need the limits, the abort race, the yield and the fixed-text errors wrapped around it, so the saving is the scanner only. If a maintainer prefers `@streamparser/json` 0.0.26 (MIT, no dependencies, published 2026-08-21, older than the 3-day gate; pre-1.0, so the API may change; its source and advisories were not reviewed here), the exact protected-path changes are: (1) `tools/supply-chain/deps-allowlist.json`: `"@streamparser/json": { "reason": "Incremental JSON parser behind @app/json-stream (bounded reads of bare-array management lists).", "ref": "M0-48l" }`; (2) `pnpm-workspace.yaml` catalog: `'@streamparser/json': 0.0.26` (exact, referenced as `catalog:`); (3) `eslint.config.mjs` confinement: `{ names: ['@streamparser/json'], only: ['libs/shared/json-stream'] }`; (4) no release-age exclusion is needed; (5) CODEOWNERS approval of the change. `stream-json` 3.7.0 is not proposed: it depends on `stream-chain` and Node streams, which does not fit an isomorphic pure project. An agent applies none of these.
- **Q-3 Port and adapter: no change needed; one optional hardening.** `stream` is shaped like `get` (facts table), so the service needs nothing from `@app/ports`. What `stream` lacks is a byte ceiling and a body deadline; the reader and the glue enforce both. If a maintainer wants the adapter to enforce them too (defence in depth for any future stream reader), the exact change is: in `libs/engine/ports/src/mgmt.ts` add to `MgmtStreamRequest` `maxBytes?: number` and `deadlineMs?: number`; in `adapter-mgmt-http/src/client.ts` `stream` count bytes in the `chunks` generator and throw `MgmtHttpError('response-too-large', ...)` past `maxBytes` (and destroy the response), and start the body deadline when the headers arrive (`startExchange` with `deadlineCoversBody` true and `timeoutMs = deadlineMs`); the default stays unlimited so `svc-capabilities` is unchanged. `libs/engine/ports` is `trust:critical`, so that change would make the WP trust-critical (the issue says the maintainer decides the label then). Same family as the proposal in OQ-688 (`maxBodyBytes` on `MgmtGetRequest`), which this WP makes unnecessary for bindings.
- **Q-4 `holdMs` releases the slot without aborting the body.** `holdSlot`'s watchdog (120 s) frees the slot and counts `holdTimeouts`; the response keeps flowing. Default: not changed here; the reader's deadline (90 s) is below it, AC-11 proves that, and the other `stream` user reads at most 64 KiB. A change in `@app/kernel` (abort the task signal when the watchdog fires) is a separate issue if a maintainer wants it for every stream user.
- **Q-5 The total is unknown after a cut.** Default: stop at the cap, do not read or count the rest; `truncated: true`, `dropped` is a minimum (1: the reader saw that one more follows), `expected` absent, `countExact: false` internally, and the fixed `reason` says the number left out is not known. This follows OQ-688 (a reason text, not a new field). Alternatives: (a) a new optional `FreshnessSchema` field such as `droppedIsMinimum`, which changes `@app/contracts` and the API documents; (b) keep scanning without keeping items up to a byte budget (for example 32 MiB, about 150,000 more bindings) so the count is exact when the body ends inside the budget and a minimum otherwise, at the cost of that much more transfer and of holding the slot longer. The issue text says "counting the rest"; this default does not, because an early stop is what bounds the work.
- **Q-6 Byte ceiling before the cap.** Default: a body over `maxBindingsBodyBytes` (256 MiB) or an item over `maxBindingItemBytes` (256 KiB) fails the read closed (`too-large`), as `response-too-large` does today, and serves the last good rows `stale` if any. 500,000 bindings of the recorded shape are about 107 MB, so the ceiling is reached only by unusually large bindings. Alternative: treat the byte ceiling like the item cap (keep what was read, mark `truncated`), which needs a rule for a cut inside an item. Confirm the three numbers (256 MiB, 256 KiB, 8 MiB for an envelope page) and the deadline (90 s).
- **Q-7 Sniffing the shape.** Default: the first significant byte decides (`[` bare array, `{` envelope), so the same code reads RabbitMQ and LavinMQ and no product or version is named. Alternatives: key on `profile.product` (code branching on broker behaviour, I-3) or add a registry capability for "bindings list pages" (data, but a change in `libs/shared/semantics` and a lab recording to back it). A broker that answers a new shape is `not-an-array`/`malformed` and fails closed.
- **Q-8 Other bare-array lists.** Default: the reader is generic and shared, but only bindings adopts it now. `/api/vhosts` in the sweeper stays a `get` (bounded by the 16 MiB body limit, thousands of vhosts, and capped by `maxVhostsPerSweep`); consumers, policies, permissions and per-queue bindings have no engine reader yet (OQ-433), and the first one added uses `readBoundedList`. `readBoundedList` starts in `svc-explorer/src/internal` (a service cannot import another service) and moves to `@app/kernel` when a second service needs it. Alternative: put it in the kernel now.
- **Q-9 Label and CODEOWNERS.** Default: `json-stream` is not tagged `trust:critical` and the adapter gets a spec file only, so the WP is not trust-critical by the issue's rule; `svc-explorer` stays covered by its CODEOWNERS line. The reader parses untrusted broker bytes, so a maintainer may want `--trustCritical` on the new project; CODEOWNERS is a protected path, so the line (`/libs/shared/json-stream/ @RafaelJCamara`) is proposed here and applied by a maintainer.
- **Q-10 Lane and slots.** Default: the `interactive` lane (a person waits for the first window), at most 2 streams open per connection (`maxBindingReadsPerConnection`), each holding one of the 4 `interactive` slots until read, cut or timed out. Alternatives: the `background` lane (one at a time, but slower and queued behind sweeps), a limit of 1, or no limit beyond the scheduler's. The wait for a free place is bounded by the number of vhosts a user can open, and the queue is the store's single flight per vhost.
- **Q-11 The p99 assertion.** Default: AC-15 asserts p99 at most 20 ms on the CI Linux runner and prints the maximum; AC-7 is the deterministic gate (yield counts). If AC-15 proves flaky on shared runners it becomes a printed measurement in the M0-48 perf harness and AC-7 stays. The yield sizes (256 KiB, 5,000 items) are starting values until measured (like OQ-684).
- **Q-12 What this closes.** It makes the `maxBodyBytes`-on-`MgmtGetRequest` proposal of OQ-688 unnecessary for bindings and schedules the streaming reader that OQ-688 names. Default: slice C adds a pointer to the OQ-688 and OQ-686 rows; a maintainer closes OQ-688 when slice C lands. OQ-686 (1) (the first query awaits the whole read) now covers a read of up to about 100 MB; the answer-at-once `loading` window stays the alternative there.
- **Q-13 Size.** About 1,100 changed lines by estimate (1,740-2,180 at this repository's usual overshoot) against 800 (AGENTS.md section 5). Default: four child issues (A to D) with the hard budgets and cuts above; `oversize-approved` is not asked for. Same family as OQ-654.
- Related and not decided here: OQ-125 (not touched), OQ-433 (which lists are bare arrays), OQ-686 (3) (resident rows have no byte bound: this WP bounds what is held while reading, not what stays resident), OQ-688.
- **Protected paths:** none edited by default. A maintainer applies, only if answered that way: the CODEOWNERS line of Q-9, the dependency changes of Q-2, the port and adapter change of Q-3. Nothing in `testing/lab-evidence/**` or a workflow is needed.
- **Size:** about 1,100 changed lines in four slices (table above). If C overshoots, AC-12 leaves first; if A overshoots, `maxDepth`.
- **trust:critical:** no by default (Q-9). The review checks: no path keeps part of a failed read, no error carries input or broker text, every buffer has a bound and a counted or declared drop, the slot and the socket are released on every ending, a minimum is never shown as a count, and the shape is never decided from a product name.
