## Goal

A maintainer opens the served app and, in the page, adds a broker connection (name, management address, AMQP address, user name, a write-only secret, environment class), tests its management API and its AMQP endpoint on their own, sees the capability card of the broker, sees the environment chrome, edits and deletes the connection, unlocks a production connection with an audited confirmation, switches between connections, and opens the explorer for one from the tree and the switcher. Today the only way to add a connection to a running engine is `curl` (`docs/runbooks/run-locally.md`); this WP removes that.

Serves: CON-01 and CON-02 (UI side of M0-44 and M0-45/M0-46), DC-37 (separate HTTP and AMQP credentials), DC-31 (gates rendered as sent), DC-15 (honest wording), I-10 (secrets are write-only after entry), I-2 (every command through the engine's executor: the UI only calls actions), blueprint 5.9 (prod lock), 10 (UI rules).

## Rules

**R1 Routes and the library.** A new lazy library `libs/ui/feature-connections` (`type:ui-feature`, `runtime:browser`, alias `@app/feature-connections`, Transloco scope `connections`), made with the `ui-feature` generator and reshaped as `feature-explorer` was. The app mounts it with `loadChildren: () => import('@app/feature-connections').then((m) => m.connectionsRoutes)` at `/connections` (outside `c/:cid`, which needs a connection): `''` the list, `new` the create form, `:id` the connection (detail), `:id/edit` the edit form. An id that is not a plain route token is the not-found view. The app never imports the library statically.

**R2 The directory.** `ConnectionDirectory` (root service of `ui-data`): `connections.list` in windows of 100, at most 200 profiles kept, `items`, `status` (`idle | loading | ready | error`), `error` as received, `truncated`, `refresh()`, `more()`. The list page, the switcher and the detail page read it; every successful create, update or delete calls `refresh()`. It holds no secret (the contract has none).

**R3 Secrets are write-only (I-10).** A secret is typed in a `type=password` input with `autocomplete="new-password"`, held in the form component's own state only, built into the request at submit time, and never written to a signal of a store, a URL, a route state, storage, a log, an attribute or an error message. The pasted URI is treated as a secret as well (a password input). After a saved profile loads, the secret fields are empty and show "set" or "not set" with the date from `secret.isSet` and `updatedAt`; an empty secret field means keep (it is not sent). To remove a secret the person sets the authentication to "none". The form never echoes an input value into the page text, a title or a live region. A failed save keeps what was typed in the inputs (so a typo in the name does not cost the password) until the person leaves the page.

**R4 Testing.** A draft test sends the form's current values (`draft`); a saved test sends `{cid}`. The two tests are separate buttons and each shows its own result in a polite live region: success (product, version, cluster, user, tags, time; for AMQP the target and the open features), a failure by code (a heading from the page's own table by code, the engine's `message` as sent, and a one-line hint), an unknown code shown as the code, a Problem (validation, transport) as sent. Running one test never changes the other's result. A button is busy while its call runs and cannot be pressed again. A successful HTTP test that reports AMQP ports offers to fill the AMQP port (a UI-only convenience).

**R5 The prod lock and the unlock dialog.** `ArmingStore` (root service of `ui-data`) remembers what `ops.arm` answered: per connection, `armedUntil` (the answer's `expiresAt`) and a clock-driven `armed(cid)` signal that turns false at expiry (clock injectable); `arm(cid)` and `disarm(cid)` call the actions and keep the answer or the Problem; `noteLocked(cid)` records that the engine refused with the lock. The lock gate of a mutating control is a `GateDecision` built from two engine facts: the profile's `envClass` (an unset or unknown class is `prod`) and the store's `armed(cid)`. A `prod` connection that is not armed gives `{enabled: false, reason, source: 'prod-lock', fix: {actionId: 'ops.arm', input: {connectionId}}}`; anything else gives `{enabled: true}`. Every mutating control of the feature (Save, Delete) and the planned peek control use it through `<app-gated>`. This is a display of the engine's rule from engine-sent facts, named in the issue's AC; the engine stays the authority and still refuses (R6). The unlock dialog names the connection and its class, says that changes that name it are allowed for 15 minutes and that the unlock is recorded in the audit log, and has Cancel (focused first) and Unlock. Unlock calls `ops.arm` once; on success the dialog closes, focus returns to the control that opened it, and the lock line reads "Unlocked until HH:MM"; a Problem stays in the dialog as sent. "Lock again" calls `ops.disarm`. `apps/web` provides `LOCK_STATE` from the store for the active connection, so the status bar shows armed and locked.

**R6 The engine's refusal is shown as sent.** A rejected update or delete (an `EngineProblemError`) shows `title`, `detail`, `code` and, for a gate, the gate's `reason` and `source`, as received, in an alert region. If the Problem is `GATE_BLOCKED` with `gate.fix.actionId === 'ops.arm'` and a `connectionId` equal to the connection on screen, the alert also offers "Unlock this connection" (opens the dialog) and the store is told `noteLocked`. Nothing is retried on its own. For a `dev`-class profile the gate is open (the UI has no engine fact that says it is not), the engine locks it anyway today (OQ-785), and this is the path the person sees.

**R7 The capability card and the probe.** The detail page reads `profile.get` on open: a profile that parses shows the card; `NOT_FOUND` says "not probed yet"; any other failure says the capabilities are not known. A "Check capabilities" button runs `probe.run` and shows the twelve steps (status and the engine's safe `detail`) and then the card. The card has one row per gate, as sent (open only for `enabled: true`, a degraded gate with its reason, the engine's reason and source as sent, a source is a link only when it is an absolute https URL without credentials), plus the verification banner and the facts the profile carries (product, version, era with its "conservative" mark, statistics mode). Unknown never reads as available. The card computes no authorisation.

**R8 Environment chrome.** `<app-env-chrome>` shows the class on the list rows, the detail page (with the name as detail) and the form (live, following the selected class, so choosing `prod` turns the strip to prod before saving). The class text is a key per class. An unknown class reads `prod`.

**R9 The switcher.** In the sidebar of the shell (`apps/web`), above the tree: a native `<select>` of the directory's profiles (name and class), the active one selected, plus a link "Manage connections". Choosing another profile navigates with `resolveSwitchTarget(currentUrl, toCid, exists)`: the page-level addresses (`explorer`, `explorer/<kind>` with its query) carry over to the new connection; any other address under the old connection is asked of `ADDRESS_EXISTS` (a token whose default says no, because the object pages do not exist yet, M1-42); when it says no the explorer root of the new connection opens and the switcher shows a dismissible notice ("`<address>` does not exist on `<name>`. The explorer root is shown."). The notice never names more than the address.

**R10 Delete.** Delete opens a confirm dialog that names the connection, says the stored credentials are removed and cannot be recovered, and has Cancel (focused first) and Delete. It calls `connections.delete {cid}`; on success the directory refreshes and the list opens; a Problem stays in the dialog as sent (R6 applies).

**R11 Accessibility and words.** Every control has a visible label; a field error is tied to its field with `aria-describedby` and a summary region with `role="alert"` follows a failed submit; dialogs are `role="dialog" aria-modal="true"` with a label, Escape cancels, Tab is kept inside, focus returns to the opener; results are in `aria-live="polite"` regions; no information by colour alone. Every visible string is a Transloco key of the `connections` scope (`@app/ui-no-raw-template-text`); no string says "read-only", "non-destructive", "without side effects" or "safe peek" (DC-15). Engine text (names, reasons, messages) is rendered as text only.

**R12 What is proved where.** The pages and stores run in jsdom specs against the real `EngineApi` over a fake engine (like `feature-explorer`); the calls the UI makes are replayed against the real router over the real actions with the services' in-memory fakes (`libs/testkit`); one browser run against `pnpm nx run engine:serve` (and a lab broker when Docker exists) is recorded in the commit body and the README. The Playwright and axe spec (`@connections`) waits for M0-60.

## Out of scope

- TLS trust configuration (custom CA, mTLS, insecure override), SSH/SOCKS tunnels, OAuth and other auth providers: M1-53. The form has the per-endpoint "use TLS" flag the engine stores today; an untrusted certificate fails the test with the engine's `*_TLS_UNTRUSTED` code and a hint, and nothing here changes the trust store.
- Bundles import and export UI (`bundles.*`), colours, team visibility, profile duplication, URI parsing in the UI.
- Reading the arming state from the engine (no action returns it, OQ-530) and anything that changes how the guardrail classes a connection (OQ-283, OQ-785): kernel, guardrails and contracts are not touched.
- Object pages (a queue's own page, M1-42): the switcher's "does the object exist" check is a seam proved against a fake.
- `apps/e2e-web`, Playwright, axe (M0-60); a dev-gallery page.
- A shared capability card library (follow-up issue, Q-5).

## Risks / questions

Every question is a row in `docs/open-questions.md`, section "Spec questions: M0-52".

- **Q-1 Where the connections page lives.** Default: `/connections`, outside `c/:cid`, reached from the switcher link and from the no-connection view. Alternative: inside the shell with a sidebar entry (needs the shell to render without a connection).
- **Q-2 The default class of the create form.** Default: `dev` (a lab broker is the first use). The engine's own reading of an unset class is `prod`; a person who wants `prod` selects it and the chrome turns.
- **Q-3 One login for both endpoints.** Default: the create form has "use the same user name and password for AMQP" on; the edit form has it off. Alternative: always two logins (DC-37 separate credentials).
- **Q-4 Arming state is the UI's memory.** Default: a reload reads "locked". Alternative: an engine query for the state (OQ-530, a contract change).
- **Q-5 The duplicate capability card.** Default: a second card in this feature, a follow-up issue to extract one into a shared lib.
- **Q-6 The lock gate from the class and the arming answer.** Default as R5; it mirrors the engine's rule for display. If the maintainer prefers the UI never to pre-compute, the alternative is to enable every control and rely on the refusal path (R6) alone, which fails AC-1 of the issue.
- **Q-7 The switcher's object check.** Default: a seam (`ADDRESS_EXISTS`) that says no until the object pages exist, so any non-page address falls back to the explorer root with the notice.
- **Q-8 No human-only action is needed.** The new `ui-data` files and the feature library add no dependency. The one chunk or initial-bundle number that would need a limit change is reported if it appears.
