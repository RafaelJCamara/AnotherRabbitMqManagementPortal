# M0-54 feature-explorer grids, saved views and cluster overview (EXP-02/03 UI)

**Issue:** #50 · **Milestone:** M0 · **Wave:** M0-W3 · **Size:** M by label; about 2,290 changed lines by estimate, ten slices with hard budgets (see "Slices" and Q-1) · **Owner area:** ui (the issue also carries `area:engine`) · **trust:critical:** no

Status: spec for approval. Nothing is implemented. Checked against the worktree at `a23c84c`. The issue depends on #49 (M0-53, `ui-grid`), #44 (M0-48, `svc-explorer`) and #47 (M0-51, the shell); all three have landed their code. What each of them does and does not give is in "What the code gives and what it does not". Two things the issue's verification names do not exist: `pnpm nx e2e e2e-web --grep=@explorer` (M0-60) and `pnpm nx run perf:explorer-ui-20k`.

## Goal

The explorer screens of the web app, in a new lazy feature library `libs/ui/feature-explorer`: one grid each for queues, exchanges, connections and bindings, filtering by name text and facets, sorting, a column chooser and saved views; and the cluster overview page with its totals, rates, nodes, alarms and capability card (why-disabled reasons). The grids read windows of 200 rows through `inventory.query`, follow the rows on screen through the `explorer.window` topic, and say, in words, whenever what they show is loading, stale, partial or truncated. The explorer only reads the inventory; it reads no message and calls no broker-changing action. The only commands it sends are the two that keep a person's own saved views (`views.create`, `views.delete`).

Serves: EXP-03 (entity grids and saved views) and EXP-02 (cluster overview), the UI side of M0-48; DC-15 (honest wording), DC-32 (statistics-off aware: totals without rates, rates labelled unavailable), DC-31 (gates rendered as sent), DC-52 (the grid adapter is used, never AG Grid directly); ADR-021 (CSP, Trusted Types, no `innerHTML`), ADR-034 (docs policy); invariants I-6 and I-7 (bounded: no list-all, 200-row blocks, 25 blocks), I-10 (no secrets: none reach this UI), I-11 (only `ui-grid` imports AG Grid) and I-13 (no silent loss: partial, stale, truncated, dropped and unfollowed rows are shown). Blueprint 3.2 (resource map), 10 (grids: infinite row model, deltas for visible keys only, `refreshInfiniteCache` at most every 5 s), `scale-first` 10.

## Rules

These are the behaviours the acceptance criteria prove. They are written so that a test can fail them.

**R1 The window source** (`createInventoryWindowSource` in `@app/explorer-model`; slice B). One source object is one query: `{cid, kind, filter, sort}`; a changed filter or kind is a new source (the grid then aborts the old one, purges and rebinds). `window({offset, limit, sort}, signal)` becomes `inventory.query {cid, kind, filter, sort: first sort only, window: {offset, limit, version?}}`; the grid's offsets are multiples of 200 and its limits at most 200, and the source refuses anything else before sending. The answer becomes `{rows, total: matched}` (the filtered count, not the index total, and never null: the engine always knows). The row id is `row.key`. A rejected call or a Problem fails the block as a whole (the grid already shows and retries it). `bindings` sources are built only with exactly one vhost.

**R2 Version pin** (slice B). The first answer of a scroll fixes `pin = answer.version`; later blocks of the same sort send `window.version = pin`, so a scroll sees one consistent list (M0-48 AC-7). A different sort, a new source or a call of `refreshed()` (the grid reloaded its cache) clears the pin; an answer that belongs to an older epoch than the request that started it never sets the pin. An answer with `freshness.versionChanged: true` (the pin is gone) is shown as a notice and asks for one cache reload (at most every 5 s, by the grid).

**R3 Following the rows on screen** (slice C). The grid reports the ids it shows to `watch(ids)` (after its own 100 ms debounce; displayed rows only, a few dozen). The source then:
1. keeps the followed set; if the reported set is the same as the last reported set, or a subset of the followed set, nothing is sent; otherwise it unsubscribes and subscribes with `keys` = the reported ids in screen order (a topic param is fixed when `sub` is sent, OQ-657);
2. keeps the keys of one `sub` inside `SUB_KEYS_BYTES_MAX = 48 KiB` of key text (each key counted as its length plus 3), and at most 500 keys (Q-6). Ids left out are counted as `unfollowed` and the page says so ("live updates paused for N rows"); the earliest ids on screen are kept;
3. turns an item with a row into an `upsert` change of `{...row, key: item.key}` (the topic omits the key); an item with the key `~version` is never a row; a `remove` in `removes` becomes a `remove` change;
4. on a **snapshot** (the first, or after a `gap`), reconciles: every followed key that is not in the snapshot has left the inventory, so a `remove` change is emitted for it; and if the marker's version is newer than the pin, one `refresh` change is emitted (with no pin yet nothing is compared; Q-7). On a **delta** with a marker newer than the pin, one `refresh` change is emitted. The grid reloads at most every 5 s however many `refresh` changes arrive;
5. on `reset` (the engine started a new session, its versions restart) clears the pin and emits one `refresh` change; on `gap` waits for the snapshot that follows and counts it; on `status` shows the topic's health; on an error that ends the topic (an `EngineProblemError`, a `TransportError`) shows it, stops following, and leaves the grid working from windows: the person can still reload (I-13);
6. unsubscribes when the source is destroyed.
The source counts windows, resubscribes, markers seen, refresh changes, snapshots reconciled, gaps, resets and unfollowed ids, and exposes them as a state object with a listener (the page wraps it in a signal), so the page and the tests can read them.

**R4 What the page says about freshness** (slice D). One banner region above the grid, a polite live region, built from the last answer's `freshness` and never from the rows:
- `loading`: "Loading the inventory: {loaded} of about {expected} loaded. Rows and counts are incomplete." (without "about {expected}" when absent). While it is loading with no row yet, the page shows this and never only "no rows".
- `stale`: "Showing the last good read from {sweptAt}." plus the engine's `reason`.
- `unavailable`: "The inventory is not being read." plus the `reason`.
- `truncated` or `dropped > 0`: "{dropped} rows were left out of the index because of its limit." For `bindings`, when the `reason` says the count is not known, "at least {dropped}".
- `complete: false` in any state: "This list is incomplete." `complete` is never displayed as true unless the engine said so.
- `versionChanged`: a one-time notice that the list changed while scrolling and was reloaded.
- `hazards`: each id with a sentence from the page's own table (`explorer.hazard.<id>`); an id the table does not know is shown as the id with a generic sentence, never hidden (Q-22).
- The engine's `reason` is always shown as sent (fixed text, English), in addition to the page's own sentence.
- A live-updates line: following N rows, paused for M unfollowed rows, ended (with the Problem), or "not followed" for bindings.
- `live` and complete: only "Updated {sweptAt}".

**R5 Filters** (slice E). The filter is the contract's, nothing more: `text` (case-insensitive substring of the name; for bindings of source, destination and routing key, as the engine matches), `vhosts`, `types`, `states`, `hasConsumers`, `minMessages`, each applied by the engine. **No regex** (OQ-666) and **no client-side filter over loaded rows**, which would filter only the blocks that happen to be loaded. Which facets exist per kind:

| Kind | text | vhosts | types | states | hasConsumers | minMessages |
| --- | --- | --- | --- | --- | --- | --- |
| queues | yes | yes | yes (queue type) | yes | yes | yes |
| exchanges | yes | yes | yes (exchange type) | no | no | no |
| connections | yes | yes | yes (protocol) | yes | no | no |
| bindings | yes | exactly one, required | no | no | no | no |

The engine matches a facet that does not apply to a kind against nothing, so the UI offers only the facets above and never sends the others. A change of the text applies after `FILTER_DEBOUNCE_MS = 200` of no typing, or at once on Enter; any other change applies at once. Facet values are exact and case-sensitive, as the engine matches them. The caps are the contract's (text 200 characters, 100 vhosts, 16 types, 16 states) and the UI's own cap of 25 vhost chips (so a saved view stays inside 16,384 characters, Q-12). Every active filter is a removable chip with an accessible name. A filter that matches nothing says "No rows match" with the chips listed.

**R6 Sort** (slice E). One column, ascending or descending, only on a column the engine accepts for the kind (the lists in rule R7). A header sort that adds a second column keeps the first, drops the second and says so (Q-10). The sort is part of the column state (so of a view).

**R7 Columns.** Column ids are the engine's column names, so a `GridSort.columnId` is an `InventorySort.column`. Cells are text; a field the broker did not send reads "not reported", never `0`, `false` or blank. Numbers use `Intl.NumberFormat`. There are no per-queue rate columns (OQ-661: per-queue rates never).

| Kind | Shown by default | Hidden by default | Sortable (all columns listed) |
| --- | --- | --- | --- |
| queues | name, vhost, type, state, messagesReady, messagesUnacknowledged, messages, consumers, policy | node, durable, autoDelete, exclusive, operatorPolicy, deliveryLimit | all fifteen |
| exchanges | name, vhost, type, durable, autoDelete, internal | none | all six |
| connections | name, vhost, user, node, state, protocol, channels, peerHost, ssl | none | all nine |
| bindings | source, destination, destinationType, routingKey | vhost, propertiesKey, argumentsKey, argumentsTruncated | source, destination, destinationType, routingKey, vhost |

`argumentsKey` is the canonical form cut at 512 characters; when `argumentsTruncated` is true the cell says it was cut.

**R8 Saved views** (slice F). A view is `{version: 1, kind, filter, columns}` stored as the `definition` of `views.create` with `kind` equal to the grid kind (`queues`, `exchanges`, `connections`, `bindings`; the contract's `kind` is any `[a-z][a-z0-9-]{0,39}`). `columns` is the grid's `GridColumnState` (order, visibility, widths, pinning, sort). The views control lists the person's views of the current kind (`views.list {kind, limit: 200}`; if a `nextCursor` comes back the page says that only the first 200 are shown), applies one, saves the current state under a name, and deletes one after an inline confirmation. A view is never tied to a connection, so it is offered on every connection. Applying a view (the portability rule is Q-14) goes through `parseViewDefinition`, which never throws, drops what it does not understand and reports each drop. Saving serialises the state, refuses a definition over 16,384 characters before sending, and shows the engine's Problem as sent when the engine refuses (a prod-lock 422, a budget, a validation); the current filters and columns stay applied. Replacing a view creates the new one first and deletes the old one second (a failure between the two leaves a duplicate, never a loss). The Save and Delete controls are `<app-gated>` with a gate that comes from `allowedActions`: closed, with a stated reason, when the action is not in the list or the list is unknown (Q-13).

**R9 Overview** (slice G). One request on open (`overview.get`) and one on each press of Refresh; no polling, because every call costs up to three interactive-lane broker requests (I-8) and there is no overview topic (Q-19). Refresh is disabled for `OVERVIEW_MIN_REFRESH_MS = 10,000` after a call and says why. The page shows:
- **Totals**: queues, exchanges, connections, channels, consumers as numbers; a total the broker did not report reads "not reported". Messages (total, ready, unacknowledged) with their source in words ("reported by the broker" or "summed from the last queue read") and the time they describe (`asOf`); when `complete` is false, "partial: some queues did not report a count".
- **Rates**: `available` with publish and deliver per second; `unavailable` with its reason as a sentence (statistics are off; the broker does not report rates). "From Prometheus" is never shown (no reader exists). Never a zero the broker did not send.
- **Nodes**: an accessible table (name, running or stopped, being drained), at most 100.
- **Alarms**: `active` is an alert region naming each node and its resource (memory, disk, other); `none` says no alarm is reported; `unknown` says the alarm state could not be read, with the engine's reason, and is never worded as "none".
- The inventory's freshness line (R4 wording), and product, version and cluster name when present.
- Errors: a failed call shows the engine's Problem as sent and keeps the last good answer, marked as from an earlier read.

**R10 Capability card** (slice H). From `profile.get`, parsed with `BrokerProfileSchema`: if the profile is absent, fails to parse or the call fails, the card says the capabilities are unknown (never "available"). Otherwise one row per entry of `gates`, in id order: the feature's name (a key for the eight known ids, the id itself for an unknown one), its state in words (available; available with limits; not available), and for a closed or degraded gate its `reason` and `source` as sent. A source is a link only where `parseSourceLink` of `ui-design` says so (absolute `https:` without credentials), and opens with `rel="noopener noreferrer"`. A gate is open only for `enabled === true`; any other value or shape is closed. The card makes no call and has no control that needs a gate: the rows are display rows built with the rules of `<app-gated>`, because `<app-gated>` always draws a button and these features have no destination yet (Q-21). It never computes authorisation.

**R11 Routes, tree and tab.** Under the shell's `c/:cid`, the child `explorer` mounts the feature's lazy `explorerRoutes`: `explorer` (overview), `explorer/queues`, `explorer/exchanges`, `explorer/connections`, `explorer/bindings?vhost=<name>`; an unknown child falls through to the shell's not-found view. `?view=<id>` selects a saved view. The feature reads the connection id from a token it owns (`EXPLORER_CONNECTION`), provided on the mounting route by `apps/web` from `ActiveConnection`; a null id shows no content and makes no call. The explorer tree source is a static list in `apps/web` (overview and the four kinds, translated labels, `url: /c/<cid>/explorer[/<kind>]`, no counts, no vhost level, no engine call); activating a node opens a tab through the existing `WorkspaceTabs`. A tab remembers its address only: kind, vhost, view id. Filter edits, column changes and the selection are not persisted per tab (Q-15). A vhost whose encoded address is over the shell's 512-character tab limit cannot be opened as a tab; the shell's own refusal notice is shown (the feature does not work around it).

**R12 Strings.** One Transloco scope, `explorer`, registered by the feature's route providers with a bundled-JSON loader (`import()`), English only. Every visible string, `aria-label`, `title` and placeholder is a key; engine data (names, reasons, sources, node names) is rendered as text. The file is the scope root (`{"nav": ..., "kinds": ...}`), so keys read `explorer.nav.*` (Q-17). No string uses "read-only", "non-destructive", "without side effects" or "safe peek" (Q-28).

**R13 Accessibility.** The grid keeps AG Grid's own ARIA grid roles. The filter bar is `role="search"` with a labelled input; the chips are a list whose items have a remove button named for the chip; facet pickers are disclosure panels with labelled checkboxes (no listbox library, Q-27); the views control is a disclosure (button with `aria-expanded`, panel with real buttons), the same pattern as the column chooser (OQ-706 (1)); the freshness and live lines are polite live regions that do not repeat on every block; focus returns to the views button after a view is applied and to the chip's neighbour after a chip is removed; the overview has labelled regions (alarms, totals, rates, nodes, capability card), the nodes are a real `<table>`, and an active alarm is `role="alert"`. State is never colour alone.

**R14 Bounded.** The grid holds at most 25 blocks of 200. A `sub` follows at most 500 keys and 48 KiB of key text. `views.list` asks for 200. The tree draws at most 500 rows (the shell's rule). The overview holds at most 100 nodes. Nothing in the feature holds a list of the whole inventory.

**R15 What is proved where.**
- *Node/Vitest (no DOM), in `@app/explorer-model`:* the window source (R1 to R3), the view parse and serialise (R8), the column and filter model (R5 to R7). Deterministic; counts and shapes, no time. It is a `type:pure`, `runtime:isomorphic` project because `perf` and `testkit` are `runtime:node` and the lint rules do not let them import a `runtime:browser` project (Q-29).
- *jsdom component specs (`test-components`):* the pages with the real `DataGrid` over a fake `ExplorerData` (20,000 rows) or a `FakeEngine`; roles, names, focus, live-region text, requests sent. No layout, so no scroll position, no paint, no frame time.
- *Node perf harness (`perf:explorer-ui-20k`, slice J):* the real window source (from `@app/explorer-model`) and the real `inventory.query` action over a 20,000-row index: engine time plus adapter time per interaction. Excludes transport and rendering, and says so in its output.
- *Real browser (planned):* interaction time from input to painted rows, and everything that depends on layout or on the real CSP. Needs the browser driver (M0-53's `grid-100k` harness, not landed), `apps/e2e-web` (M0-60) and issue #277. Not provable in this WP's slices (Q-3, Q-24, Q-25).

**Other risks.**
- The grid reports displayed rows only, so the followed set is a few dozen; the 500-key and 48 KiB limits bind only in odd cases (very tall windows, compact density), but they are the difference between one error and a closed connection (OQ-683), so they are tested.
- A first sweep of a large broker is `loading` for seconds to tens of seconds; the page shows it and the topic's marker refreshes the list as kinds are installed. The bindings kind reads a whole vhost on first use (up to 90 s) and has no topic: its page shows a loading state and a manual Reload.
- Mounting AG Grid in the app for the first time can show things jsdom cannot (the style nonce effect, a Trusted Types refusal, row virtualisation): these belong to the browser proofs that Q-3 and Q-24 defer. No claim is made for them here.
- `apps/web` hosts the tree source and the route; a bug there is a shell bug, not an explorer bug. Slice I gets a fresh-session `/review-wp` for the unsafe-address cases of AC-24 (a vhost in a tab address, an unknown child, a null connection).
- The generated project's plain Vitest cannot compile signal-input components; slice A adds `test-components` as `ui-grid` and `ui-design` have it. If the generator's output has changed by then, slice A stops and asks.

**trust:critical:** no. The review checks: no gate is computed (only rendered as sent, closed on anything unexpected), no `innerHTML`, no direct `fetch`, no broker text beyond the engine's own fixed `reason`, bounded buffers and subscriptions, every engine failure visible, and the strings.
