# M0-68 Release workflow and opt-in updates for the image and docs (PLAT-10)

**Issue:** #58 · **Milestone:** M0 · **Wave:** M0-W4 · **Size:** L · **Owner area:** ci, release (lane: platform) · **trust:critical:** yes

Status: **draft spec, written by an agent, not approved, not started. Do not implement before a maintainer approves it** (the issue is trust-critical; the work-in-progress cap of AGENTS.md section 12 is 2 and `docs/plan/status.md` lists three trust-critical WPs in flight). Checked against `origin/main` at `a1b20d5`. Assumptions are rows OQ-1492 to OQ-1499 in `docs/open-questions.md`.

## Goal

One gated pipeline from a release-please tag to an immutable GitHub release for Web 1.0: the conformance gate, the build (engine bundle, web build, container image), the SBOM and checksums with attestations, a draft release and an immutable publish, then the docs publication. Update checks stay off: the Web 1.0 artefacts contain no updater at all, and the desktop updater (first-run opt-in, enterprise disable) belongs to M2. Serves PLAT-10, DC-58, DC-59, ADR-026, ADR-035, amendments A-12, A-22, A-26 and invariants I-12 and I-14.

## Files & interfaces

Slices A and B are agent work; slice C is applied by a maintainer; D is docs.

**Create (slice A)** a new Nx project `release-ci` in `tools/release-ci` (tags `type:tooling`, `runtime:node`, `trust:critical`; make it with the `library` generator, then `pnpm install`), plain Node, no new dependency:

- `gate.ts`: `evaluateGate(input): GateVerdict`. Input is the tag, its commit, whether the commit is on the default branch, and the check runs of that commit as the API returns them. A pure function; the workflow step fetches the data with `gh api` and passes it in.
- `checksums.ts`: `buildSha256Sums(files)` and `verifySha256Sums(text, files)` (sorted names, two-space format of `sha256sum`).
- `plan.ts`: `releaseAssets(version)`: the exact list of asset names a Web 1.0 release must hold (see AC-4), and `checkAssets(listed, expected)`.
- `release-hardening.ts` and `release-hardening-selftest.ts` (in `tools/supply-chain`, next to `workflow-hardening.ts`): rules for `release.yml` (AC-6).
- `README.md`, tests (`*.spec.ts`, Vitest) and fixtures of API responses.

**Modify (slice B)**

- `.github/workflows/image.yml`: add `workflow_call` (inputs `tag`, `publish`; output `digest`), keep every existing trigger and check.

**Propose, do not apply (slice C; protected paths)**

- `.github/workflows/release.yml` (new): the pipeline below. The agent pastes the full text into the issue.
- `.github/workflows/release-please.yml`: one added step that starts `release.yml` when a release is created.
- `release-please-config.json` (not protected, an agent may apply it, but the change has no effect until `release.yml` exists): `"draft": true`.

**Modify (slice D)**: `docs/runbooks/release.md` (new runbook: how to cut, dry-run, roll back, how updates reach users), `AGENTS.md` section 7 rows, `docs/open-questions.md`, `docs/plan/status.md`.

**The pipeline** (`release.yml`, `permissions: {}` at the top; each job lists its own):

| # | Job | Does | Permissions it may hold |
| --- | --- | --- | --- |
| 1 | `resolve` | Validates the `tag` input against `^v[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z.]+)?$`, checks the tag exists, points at a commit on the default branch, and equals the version in `.release-please-manifest.json`. | `contents: read` |
| 2 | `gate` | Fetches the check runs of the commit (`ci`, `conformance`, `supply-chain` and the other required names) and runs `evaluateGate`. Refuses a missing, pending, failed, or cancelled check; "unverified" cells are not failures (M0-42 Q-4). | `contents: read`, `checks: read` |
| 3 | `build` | Builds the engine bundle and the web build from the tag (frozen lockfile), packs them as `engine-<version>.tgz` and `web-<version>.tgz`. | `contents: read` |
| 4 | `image` | Calls `image.yml` with the tag (`publish` follows `RELEASE_PUBLISH`); gets the digest of the signed manifest list. | `contents: read`, `packages: write`, `id-token: write` (inside `image.yml` only) |
| 5 | `sbom` | Exports the image's SBOM and provenance (`docker buildx imagetools inspect --format`) and writes `image-<version>.sbom.spdx.json`. | `contents: read`, `packages: read` |
| 6 | `checksums` | `SHA256SUMS` over every asset; `actions/attest-build-provenance` for the assets and the sums. | `contents: read`, `id-token: write`, `attestations: write` |
| 7 | `draft` | Uploads every asset to the draft release release-please created and fails if the list differs from `releaseAssets`. | `contents: write` |
| 8 | `publish` | Only when `RELEASE_PUBLISH` is `true` and `dry_run` is false: `gh release edit --draft=false`; then fails unless the release is immutable. On a dry run: deletes nothing it did not create, publishes nothing, prints what it would do. | `contents: write` |
| 9 | `verify` | From a clean runner: downloads the published assets, checks `SHA256SUMS`, `gh attestation verify`, `cosign verify` of the image digest against `image.yml`'s identity. | `contents: read`, `packages: read` |
| 10 | `docs` | Publishes the docs site and the compatibility matrix (the M0-62 target), after the release is public. | per M0-62 |

```text
workflow_dispatch inputs:  tag (required)   dry_run (boolean, default true)
concurrency:               release (never cancelled)
```

## Acceptance criteria

The issue's criteria are AC-I1 and AC-I2. "Where": **unit** (runs without a runner), **static** (reads the workflow text), **fork run** (needs a real run on a fork with a tag, as the issue says), **maintainer** (a repository setting).

| ID | Given | When | Then | Where | Test or command |
| --- | --- | --- | --- | --- | --- |
| AC-1 | the gate input of a tag | a required check is missing, pending, failed or cancelled; the tag is not on the default branch; or every check passed | the verdict is "refuse" with the first failing name in the first four cases and "go" in the last; an unrelated failing check does not refuse; the verdict never depends on check order | unit | `tools/release-ci/src/gate.spec.ts`: "AC-1 ..." |
| AC-2 | files and a `SHA256SUMS` text | the sums are built, then one byte, one name, or one line is changed | `verifySha256Sums` accepts the original and rejects each change, a missing file and an extra file; names are sorted and use the two-space format | unit | `checksums.spec.ts`: "AC-2 ..." |

## Risks / questions

- OQ-1492: the repository is public although A-22 says private until ADR-029. `RELEASE_PUBLISH` (and `IMAGE_NAME` from M0-64) keep publishing a maintainer's switch.
- OQ-1493: how a tag starts the pipeline (release-please with `GITHUB_TOKEN` starts nothing). Working default: `release-please.yml` runs `gh workflow run release.yml -f tag=...` after a created release; a GitHub App token would remove the step (OQ-01).
- OQ-1494: which check names the gate requires (`ci` jobs, `conformance`, `supply-chain`, `zizmor`, `dco`?) and whether it re-runs them or reads the run on the tagged commit. Working default: read the check runs of the commit; require `conformance` and the jobs of `ci`.
- OQ-1495: the stage "notices/SBOM" is the image SBOM and the licence files until #176 lands; is that enough for a Web 1.0 alpha (DC-50)?
- OQ-1496: `"draft": true` in `release-please-config.json` changes how release-please reports releases (it creates the tag with the draft, and a draft is not visible to anonymous users). Needs a dry run on a fork before the config change lands.
- OQ-1497: attestations of the tarballs: `actions/attest-build-provenance` (needs `attestations: write`, public repo or a paid plan) or cosign `sign-blob`? Working default: the GitHub action, same identity model as the image.
- OQ-1498: size. About 1,300 changed lines with tests and docs across A, B and D; `oversize-approved` is not asked for because the slices are separate commits.
- OQ-1499: the trust-critical cap (2) is already reached (M1-14, M1-23, M1-13 per `docs/plan/status.md`). Slice A should not start before one of them is done or a maintainer lifts the cap.
- Protected paths: this WP needs `.github/workflows/release.yml` and a change to `.github/workflows/release-please.yml`; both are proposed text for a maintainer. No dependency is added.
- Needs a fork: AC-5, AC-8 and the signing identity of `verify` (`cosign verify` pins the repository name of the fork).
