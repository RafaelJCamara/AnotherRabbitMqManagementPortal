# M0-75 RabbitMQ 4.4 readiness and new-release runbook

**Issue:** #66 · **Milestone:** M0 · **Wave:** M0-W3 · **Size:** M by label, about 2,600 to 3,200 changed lines by estimate (over the 800 limit; six slices proposed, see Slices and question Q-8) · **Owner area:** conformance, semantics (lane: evidence) · **trust:critical:** yes

## Goal

Make the product ready for RabbitMQ 4.4 before it is generally available, by applying amendment A-23 and following `docs/runbooks/new-broker-release.md`: a `resolveEra` rule that answers "4.4" only when every node qualifies, draft era-4.4 cells derived from the v4.4.x source, a 4.4 entry in the broker lab so the conformance matrix runs nightly against it, and a written procedure for promoting 4.4 to Tier 1 within 14 days of GA. Nothing in this work package claims 4.4 behaviour that a source citation or recorded lab evidence does not support, and nothing makes 4.4 "verified" (I-14).

Serves: DC-01 and DC-02 (data-driven, conservative era), DC-60 (supported window, 4.4 readiness, 14-day SLA), blueprint 5.2 (era and verification), amendment A-23, invariants I-3 (version behaviour is registry data), I-14 (evidence comes from CI and a human, never from an agent). Builds on M0-37 (three-way harness, `semantics-evidence`, coverage gate), M0-14 (broker lab), M0-71 (CI evidence recorder), M0-42 (nightly workflow and its `alpha` job), M0-46 (era in the profile) and M0-12 (cells). It does not need M0-76 (the platform upgrade lane); see Q-10.

## What is true today (from the repository, 2026-10-20)

Each line below was read in the repository at `origin/main` 0ee4dee. External facts (what RabbitMQ has published) are not asserted here; they are the questions Q-1 to Q-3.

1. **No 4.4 in the lab.** `testing/broker-lab/versions.json` pins five official images (3.13.7, 4.0.9, 4.1.8, 4.2.9, 4.3.6), each `x.y.z` with a `sha256` digest and a `support` string (`tier-1` for 4.2.9 and 4.3.6). It has no 4.4 entry and no `alpha` entry type. The `Dockerfile` builds `FROM rabbitmq:${VERSION}-management@${DIGEST}`, so the lab can only start an image that exists as an official tag. OQ-81 (where alpha images come from) is open.
2. **The fact sheet (2026-10-16, `docs/research/fact-sheet.md` section a) lists no 4.4 release.** Its 4.4 / 5.0 row says: "none: `4.4.0-alpha.<sha>` (v4.4.x branch) and `5.0.0-alpha.<sha>` (main) from rabbitmq/server-packages". It also says the quorum-queue machine version is "9 on main"; it says nothing about the v4.4.x branch. The flag name `rabbitmq_4.4.0` appears only in amendment A-23, the plan and the runbook ("for example"); no cited source file in the repository shows that it exists (compare 0.12, which cites `rabbit_core_ff.erl@v4.3.6` for `rabbitmq_4.3.0`).
3. **`resolveEra` already has a 4.4 era, resolved by version number alone.** `libs/shared/semantics/src/era.ts`: `Era` is `'3.13' | '4.0-4.2' | '4.3' | '4.4'`; `eraOfVersion` returns 4.4 for `major.minor >= 4.4` (a pre-release counts, so `4.4.0-alpha.x` is 4.4); the rule is "4.3, or 4.4 when every node is 4.4 or later", under the 4.3 evidence (flag `rabbitmq_4.3.0` enabled, no Machine Version below 8). `EraInputs` has no `rabbitmq_4.4.0` flag and no Machine Version 9 rule (OQ-103). A pre-release is never `verified` (`verificationOf`).
4. **Machine Versions are never supplied.** `libs/engine/svc-capabilities/src/era.ts` passes `qqMachineVersions: []` and adds the reason "quorum-queue Machine Versions were not probed" for 4.3 and 4.4. `apps/conformance/src/assert/lab-versions.ts`, `tools/semantics-evidence/src/dump-cells.ts` and `libs/shared/semantics/src/era.spec.ts` build `EraInputs` by hand (`ff43Enabled: true`); a new required field breaks all of them at compile time, which is wanted. Fact sheet 0.13 and U-02: the status endpoint shows the per-node code version, not proof of the effective Raft machine version.
5. **No era-4.4 cells.** The registry has 68 era-4.3 cells (12 settle matrix, 18 counters, 2 DLX carry-over, 36 delayed retry) and none for 4.4 (OQ-394). `peek-caps.data.ts` has four 4.4 rows (classic and quorum, user and admin); `hazards.data.ts` has ranges that end at `<4.4.0` or are open ended (`>=4.3.0`). A lookup for a 4.4 key throws `SemanticsGapError` and the caller fails closed. All cells are `code-derived`; **`testing/lab-evidence/` does not exist yet**, so no cell on any version has recorded evidence. `pnpm nx run conformance:coverage` reports 137 cells, 229 recorded results, 0 confirmed, 229 unverified, 12 conformance ids without a scenario.
6. **The nightly's alpha leg cannot run end to end today.** `conformance-nightly.yml` has an `alpha` job (`continue-on-error: true`, `if: has_alpha == 'true'`); `tools/conformance-ci/src/nightly-plan-cli.ts` reads `ALPHA_VERSIONS`, which the workflow never sets, so the job is skipped and the report says "not available" (OQ-494). Even with the variable set, `planNightly` accepts a pre-release version but the code behind `conformance:test --versions=<v>` does not: `libs/testkit/src/lab/versions.ts`, `tools/conformance-ci/src/lab-versions.ts`, `apps/conformance/src/driver/lab-endpoint.ts` (the pin lookup and the container-name pattern) and the evidence regexes (`record/bundle.ts`, `record/evidence.ts`, `record/evidence-format.ts`) all require `^\d+\.\d+\.\d+$`, and the pin lookup reads only `versions.json` `brokers`.
7. **Without a recorded baseline a run is `unverified`, not green.** `three-way.ts`: a live run with no valid CI-recorded evidence gives the live leg `no-baseline` and the verdict `unverified` (shown, skipped, never a pass). Evidence is recorded only by `conformance-record.yml` (manual dispatch on the default branch, inputs `cells`, `versions`, `dry_run`) and approved by a human (A-20, I-14). So a nightly against 4.4 can show that the scenarios execute; it cannot show agreement until a human has approved evidence for 4.4.
8. **The runbook is six lines** (`docs/runbooks/new-broker-release.md`): it names the diff files, the lab, the cells, `resolveEra`, "unverified-minor" mode and the 14-day promotion, but has no alpha rule, no issue checklist, no commands and no owner for the clock. `docs/plan/work-packages-design.md` has no M0-75 entry (its last entry is M0-69), so the issue, A-23 and the runbook are the scope source.
9. **Docs and ownership.** `apps/docs/src/content/docs/matrix.md` lists Tier 1 as 4.2.9 and 4.3.6 and says no conformance run has been published. `CODEOWNERS` covers `/libs/shared/semantics/`, `/apps/conformance/`, `/tools/semantics-evidence/`, `/.github/workflows/` and `/tools/supply-chain/`; it has no line for `/testing/broker-lab/` (OQ-86, OQ-458) or `/tools/conformance-ci/` (OQ-492). The platform upgrade lane (M0-76) detects platform majors only; nothing detects a new broker release.

## Out of scope

- Writing, editing or approving anything under `testing/lab-evidence/**`, and flipping any cell status (I-14, A-20). Evidence is recorded by `conformance-record.yml` after a maintainer dispatches it, and approved by a human (slice F).
- Evidence for an alpha build. The evidence format and the recorder accept `x.y.z` only; alpha builds run in the nightly and are never recorded (Q-6).
- Promoting 4.4 to Tier 1, setting `support` to `tier-1`, or marking any version `verified` (a maintainer step after green recorded evidence; Q-9).
- Detecting new broker releases automatically (a follow-up modelled on `tools/platform-lane`), golden fixtures for 4.4 (`record-golden`, M0-25), probe and adapter behaviour on 4.4 (`adapter-mgmt-http`, the management hash-password endpoint change noted in the research), and a review of the other version-ranged tables (hazards, capabilities, warnings, tap rules, provider presets) for 4.4. Each becomes an issue (Q-10); the runbook lists them as checklist items.
- New conformance ids or new scenarios. The 4.4 cells reuse the existing ids (CF-SETTLE, CF-CARRY, CF-DOWN, CF-DR, CF-STAMP); the 12 ids that have no scenario today stay with M0-38 to M0-41.
- 5.0 alphas and 4.3.7 alphas (they use the same lane once OQ-81 is settled).
- A divergence report that compares a live 4.4 run with the 4.3 registry cells (Q-6).

**Other risks.**

- Trust-critical: yes (label, and the tags of `semantics`, `broker-lab`, `conformance-ci`). It needs an adversarial second review (skill `security-review`) on slices A, C and D, and a human CODEOWNERS approval. Review runs in a fresh session with `/review-wp`.
- Size: the estimate above is about 2,600 to 3,200 lines; 68 cells at about 22 lines each are most of it. Splitting by data file keeps each slice under 600 (Q-8).
- The 4.4 source has to be read from outside the repository; the implementer must cite exact tags or commits and must not assert 4.4 behaviour without them. If the v4.4.x branch moves between slices, the citations are re-checked at each slice.
- `resolveEra` for a 4.4 cluster stays conservative for a long time because Machine Versions are never probed (U-02); the flag is the only positive 4.4 evidence the engine will have. Profiles will read 4.3 for real 4.4 clusters until the flag is readable, which is the safe direction.
- Exposure window: 4.4 already resolves to era 4.4 today with no cells (OQ-103), so every 4.4 lookup is a gap and fails closed. Slice A should land before D so the era is at least as conservative as the cells.
- `peek-caps.data.ts` already has 4.4 rows and `doomed.ts` already treats 4.4 like 4.3; both predate any 4.4 source. Slice D re-checks them against the v4.4.x source and raises an issue if they differ (Q-10).
- Uncertainty U-02 (effective Machine Version over HTTP) is a dependency of the Q-4 default, not of this WP's landing.
