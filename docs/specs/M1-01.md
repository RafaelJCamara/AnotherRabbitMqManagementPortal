# M1-01 Effective-config resolver and k.3 tables (POL-01 core, DC-30)

**Issue:** #86 · **Milestone:** M1 · **Wave:** M1-W1 · **Size:** M · **Owner area:** semantics · **trust:critical:** yes

Working spec written in agile mode (the approval stop is waived by the maintainer's standing instruction). Every default below is logged as an additive row in `docs/open-questions.md` (OQ-960 onward, see "Risks / questions").

## Goal

A pure resolver that says, per policy key, which value a queue really has: operator policy merged with user policy, then resolved against the queue argument by the rule of the queue type and broker version, with provenance for every input and warnings for every ignored, overridden or unsupported key. The rules are data in the semantics registry (I-3), cited from the fact sheet (section k.3, b.5) and the semantics matrix; where the registry has no row the answer is "unknown", never a default. Serves POL-01 and DC-30; consumed later by M1-03 (DLX-source limits), M1-20 and M1-50 (effective-config view, hypothetical names) and M1-36 (peek planner's delivery limit).

**Interfaces**

```ts
// @app/semantics (new)
interface EffectiveConfigLookup {
  /** Step 1. Throws SemanticsGapError when no merge rule names the key (and both values are not boolean). */
  merge(key: string, bothBoolean: boolean): MergeOutcome; // { kind: 'min'|'max'|'negative-rule'|'operator', citations, conformance }
  /** Step 2. Throws SemanticsGapError: no row, version unreadable, rows overlap, or the row is 'undetermined'. */
  resolution(queueType: QueueType, key: string, version: SemVer | null): ResolutionOutcome;
  keyForArgument(argument: string): string | null; // 'x-max-length' -> 'max-length'
  warning(id: WarningId): WarningRef; // W-EC-* ids
}
registry.effectiveConfig: EffectiveConfigLookup;

// @app/effective-config (new)
type PolicyValue = number | string | boolean;
interface PolicyInput { name: string; definition: Readonly<Record<string, PolicyValue>> }
interface ResolveInput {
  queueType: QueueType; version: SemVer | null;
  args: Readonly<Record<string, PolicyValue>>;   // x-arguments of the queue
  userPolicy: PolicyInput | null; operatorPolicy: PolicyInput | null;
}
interface EffectiveEntry {
  key: string; argument: string | null;
  status: 'effective' | 'default' | 'unset' | 'unknown' | 'invalid';
  value: PolicyValue | null;                      // null unless effective or default
  rule: string | null;                            // 'min(arg, policy)', 'policy', 'negative-rule(user, operator)', ...
  basis: 'source-read' | 'extrapolated' | null;   // how far the registry row was read from the broker source
  provenance: ProvenanceEntry[];                  // every input, which one decided
  warnings: EffectiveWarning[];                   // { id: 'W-EC-...', textKey, params, citations }
}
interface EffectiveConfig { entries: Record<string, EffectiveEntry>; mergedPolicy: {...; notEffective: true}; unrecognisedArguments: string[] }
function resolveEffective(input: ResolveInput, lookup?: EffectiveConfigLookup): EffectiveConfig;
function mergeOperator(user, operator, lookup?): MergedPolicy;
function resolveHypothetical(input: HypotheticalInput, lookup?): HypotheticalResult;
```

## Out of scope

- Reading `effective_policy_definition` or any management-API field: the adapter and `svc-topology` (M1-20) map API objects to `ResolveInput`; this library never sees an API object.
- The `effective-config` action and its HTTP route (M1-20), the UI (M1-50), policy editing (M2-04), the DLX-source analysis (M1-03).
- Lab evidence for any row, flipping a status, `testing/lab-evidence/**` (human only; the recordings needed are listed in OQ-968).
- Keys the k.3 tables do not name (for example `max-priority`, `ha-*`, `queue-mode`, `max-in-memory-*` resolution): they are `unknown`, with a reason, until a row exists.
- Broker 4.4 rows (no source has been read for 4.4).
- Mixed-version clusters: the caller passes the lowest node version.

- Sources disagree on `delayed-retry-min/max` (k.3 table: `min(policy, argument)` for both; fact sheet b.5: `max()` for min and `min()` for max). Both keys are `undetermined`: the answer is unknown until a lab recording (OQ-962).

- No row for 4.4; the 4.4 source has not been read (OQ-963).
- Regular expressions: the broker matches policy patterns with Erlang `re` (PCRE); the library evaluates only a conservative subset with JavaScript `RegExp` and treats the rest as uncertain (OQ-966). A security reviewer should read `hypothetical.ts` first.
