# M1-04 Death-history normaliser (DLQ-02)

**Issue:** #89 · **Milestone:** M1 · **Wave:** M1-W1 · **Size:** S · **Owner area:** dlq · **trust:critical:** no (one capability row is added to the trust-critical `semantics` data; see Risks)

## Goal

One pure library that turns the death headers of a message, as a client sees them, into one bounded, provenance-tagged timeline: `x-death` (AMQP 0-9-1 table, seconds), `x-opt-deaths` (AMQP 1.0 annotation, milliseconds), `x-first-death-*` and `x-last-death-*`, the delivery counters, and an explicit trust verdict for a client-published `x-death` on 4.0+. It is the shared input of the DLQ centre (DLQ-02), the replay planner (DC-28: "newest rejected/delivery_limit entry") and the `x-death` decoder page. Serves DC-28, DC-15 (wording), I-3, I-6, I-13; blueprint 5.2 and `docs/research/tap-streams-ops.md` T3.

## Files & interfaces

Nx project `deaths` (`libs/shared/deaths`, alias `@app/deaths`), tags `type:pure`, `runtime:isomorphic`. It imports no third-party package and only types from `@app/semantics`.

**Create**

- `libs/shared/deaths/src/limits.ts`: the bounds (entries, routing keys, string bytes, timestamp range).
- `libs/shared/deaths/src/types.ts`: the input and output types.
- `libs/shared/deaths/src/read.ts`: tolerant, bounded readers over plain, typed (`{t, v}`) and `Map` values.
- `libs/shared/deaths/src/entry.ts`: one death record from one table, by form.
- `libs/shared/deaths/src/x-death.ts`, `x-opt-deaths.ts`: the two forms (key names, time unit) over `entry.ts`.
- `libs/shared/deaths/src/first-last.ts`: `x-first-death-*` / `x-last-death-*` and their cross-check.
- `libs/shared/deaths/src/trust.ts`: the verdict on a client-published `x-death`.
- `libs/shared/deaths/src/counters.ts`: `x-delivery-count`, `x-acquired-count`, the 1.0 `delivery-count`.
- `libs/shared/deaths/src/normalize.ts`, `context.ts`, `index.ts` and the specs.
- `docs/specs/M1-04.md` (this file).

**Interfaces**

```ts
// The second argument is the broker context, not a bare era: the rule is data (I-3).
export interface DeathContext {
  /** registry.capability('clientDeathHeaderInterpreted', profile); null when unknown (fail closed). */
  readonly clientDeathInterpreted: boolean | null;
}
export function deathContext(
  capability: (id: string, profile: CapabilityProfile) => boolean,
  profile: CapabilityProfile,
): DeathContext; // a throwing lookup (SemanticsGapError) gives null

export type DeathMessage =
  | { protocol: 'amqp091'; headers?: unknown; clientPublished?: boolean }
  | {
      protocol: 'amqp10';
      messageAnnotations?: unknown;
      applicationProperties?: unknown;
      header?: unknown;
      clientPublished?: boolean;
    };

export function readDeathEntries(message: DeathMessage): EntriesResult; // slice B
export function normalizeDeaths(
  message: DeathMessage,
  context: DeathContext,
): DeathHistory; // slice C

// DeathHistory: { protocol, state: 'none'|'present'|'unreadable',
//   entries: DeathEntry[] /* newest first, ms */, orderBasis: 'last-time'|'broker-order',
//   first, last: DeathSummary|null, totalDeaths: number|null,
//   counters: { deliveryCount, acquiredCount }, trust: { trusted, state, reasons },
//   trusted: boolean, flags: HistoryFlag[], truncation: {...counted...}, provenance: string[] }
```

Values may arrive as plain JS (amqplib: a timestamp is `{ '!': 'timestamp', value }` in seconds), as the engine's typed form `TypedHeaderValue` (`{ t, v }`, the shape of `Delivery.headers`), or as `Map`s (AMQP 1.0 clients); all three are read the same way. The message body is not part of the input type, so no payload can reach the output.

## Out of scope

- Framework decoders (MassTransit, Spring, ...) and delay-infrastructure classification: M1-xx decoders (`/new-decoder`). Only a fixed list of republish markers is read, as trust evidence.
- Replay destination resolution (M1-34), the DLQ view and the death timeline UI (M1-xx `feature-dlq`, `libs/ui/payload`), the `apps/utilities` page.
- Lab recordings of real `x-death` shapes (needs `conformance:record`; OQ-1042) and any `lab-verified` status.
- A new registry table or cell type; a broker-version comparison in code.

## Risks / questions

- OQ-1040: the second argument is a context, not a bare `era`, so the version rule stays in the registry (I-3). The issue's `normalizeDeaths(msg, era)` is a sketch.
- OQ-1041: size over the 800-line guide; no `oversize-approved` label requested because slices are within 600.
- OQ-1042: no real `x-death` / `x-opt-deaths` message was ever recorded in `testing/fixtures` or the lab; every shape here is from the docs, the release notes and the broker source (`docs/research/tap-streams-ops.md` T3). Lab recordings needed (proposed ids, not created): CF-DEATH-01 (0-9-1 consumer sees `x-death`, `x-first/last-death-*`, time in seconds, newest first), CF-DEATH-02 (1.0 consumer sees `x-opt-deaths` with first-time and last-time in ms), CF-DEATH-03 (a client-published `x-death` on 3.13 is merged into the history, on 4.x it is delivered verbatim until the next dead-lettering), CF-DEATH-04 (conversion of a 1.0-published `x-opt-deaths` for a 0-9-1 consumer).
- OQ-1043: on 4.x no wire marker proves a copied `x-death` was copied. The verdict is evidence-based (hint, replay stamp, republish marker, missing `x-first-death-*`, mismatch); a consistent, unmarked record is `broker-shaped` and trusted, and says so.
- OQ-1044: the republish markers (`x-redrive-count`, `x-redriven-from`, `x-redriven-at`, `x-original-exchange`, `x-original-routingKey`, `x-exception-message`, `x-exception-stacktrace`) are a fixed list from the research, not a decoder; decoders may extend the evidence later.
- OQ-1047, OQ-1048: coverage cannot be measured (no provider), and the 0-9-1 order before `message_containers_deaths_v2` is unverified.
- OQ-1045: the capability row is a data change in the trust-critical `semantics` project; CODEOWNERS sign-off is for the maintainer. No status or evidence is touched.
- Estimated changed lines: about 1,500 with tests.
