# M1-26 Metrics engine: Prometheus adapter, ScrapePlanner, fallback, forecast (MON-01, MON-05 core)

**Issue:** #111 · **Milestone:** M1 · **Wave:** M1-W2 · **Size:** L (split into five slices of at most 600 changed lines each, A to E; the issue is labelled `needs-split`) · **Owner area:** engine, metrics · **trust:critical:** no (slice D touches the composition root `apps/engine`, which needs the usual CODEOWNERS review there; the new libraries carry no `trust:critical` tag)

Working spec written under the maintainer's agile mode (no approval stop). Questions that were decided by default are rows OQ-862 to OQ-871, OQ-889 and OQ-890 in `docs/open-questions.md`; each has a working default in use.

## Goal

Prometheus-first, demand-driven metrics scraped per node, with management sampling as the fallback, a bounded hot time-series store and a pure forecast, all in the engine (no UI: M1-54 builds the charts on `metrics.live` and `metrics.query`). Serves MON-01 and MON-05 (core), DC-32, DC-33, ADR-024, blueprint section 8 (metrics architecture) and invariants I-3, I-5, I-6, I-8, I-9, I-10, I-12, I-13.

## What the code gives and what it does not

| Fact | Where | Consequence |
| --- | --- | --- |
| `PromScrapePort.scrape(request, signal)` returns the body as chunks; `schedulePromScrape` holds a background slot until the body is read. No adapter implements it. | `libs/engine/ports/src/mgmt.ts`, `kernel/src/scheduler/scheduled-ports.ts` | `adapter-prometheus` is new: the HTTP client over Dialer sockets (like `adapter-mgmt-http`) and the exposition-format parser. |
| The BrokerProfile already carries `prometheus: { endpoints[{node,url,source}], perObjectAllowed, queueFilter, minIntervalSec }`, `lbFronted` and `nodes`. Provider ports (Amazon MQ 16001-16003), the `queue=` capability (`prometheusQueueFilter`) and the interval come from the registry. | `domain-model/src/broker-profile.ts`, `svc-capabilities` (step 11) | The planner reads the profile only: no version comparison and no provider switch in the metrics code (I-3). |
| Golden Prometheus pages of the five lab versions (stats on and off) and LavinMQ exist. | `testing/fixtures/prometheus/**` | The parser and the metric catalogue are proved against real output; nothing is hand-recorded. |
| The `prom-scrape` Dialer purpose is registered as `planned`. | `libs/engine/net-dialer/src/purposes.ts` | It becomes `active` in slice B (the generated outbound-calls page follows). |
| Every action of the contract registry must be served by the engine, every topic must have a source. | `apps/engine/src/compose-services.spec.ts` (AC-1, AC-2) | The contracts and the wiring land in the same slice (D). |
| A worker thread for the parse above 1 MiB (blueprint 1.4) needs a second entry in the engine bundle. | `apps/engine` build | Not built: the parser yields to the loop at a fixed byte and line count (I-5), which `perf:metrics-100k` proves with counts. OQ below. |

**Interfaces**

```ts
// @app/forecast (pure)
export interface Point { readonly t: number; readonly v: number } // epoch ms, value
export function counterRate(points: readonly Point[]): Point[]; // per second, reset-aware
export function ewma(points: readonly Point[], halfLifeMs: number): number | undefined;
export type LimitForecast = // also named DrainForecast for the drain ETA
  | { state: 'ok'; etaMs: number; band: { lowMs: number; highMs: number | null }; ratePerSec: number; r2: number; windowMs: number; points: number }
  | { state: 'reached' }                                        // an empty queue, for the drain ETA
  | { state: 'moving-away'; ratePerSec: number; r2: number; reason: 'flat' | 'away' | 'beyond-horizon' }
  | { state: 'no-reliable-forecast'; r2: number; windowMs: number; points: number }
  | { state: 'insufficient-data'; points: number; spanMs: number; needed: { points: number; spanMs: number } };
export function drainEta(points: readonly Point[], options?: ForecastOptions): LimitForecast;
export function timeToLimit(points: readonly Point[], limit: number, direction: 'falling' | 'rising', options?: ForecastOptions): LimitForecast;

// @app/adapter-prometheus
export function createPromScrapeClient(options: { dialer; targets: PromTargetResolver; requestTimeoutMs?; maxSocketsPerConnection? }): { scrape: PromScrapePort; invalidate; close };
export function parseExposition(chunks: AsyncIterable<Uint8Array>, sink: (sample: PromSample) => void, options?: ParseOptions): Promise<ParseSummary>;

// @app/svc-metrics
export function createMetricsModule(deps: MetricsModuleDeps): MetricsModule; // actions, topicSources, stop()
export function planScrape(input: PlanInput): ScrapePlan; // pure
```

## Out of scope

- Charts and the UI (M1-54), the persisted store with 48 h raw points and rollups (M4-04), alerts (M4-05), the external PromQL datasource and Grafana links (MON-01 later part), forecasts of memory and disk alarms beyond the generic `timeToLimit`, "consumers needed", z-score anomalies and the "why is this queue growing" tree (later MON work packages).
- A worker thread for parsing (OQ below), the chunked delta-encoded store tiers (blueprint section 8: only when a team-scale perf test demands them).
- Golden recordings of `queue=` on 4.3.6 and of Amazon MQ pages: they need a lab and a provider account (human-only list in the report).
- Any change to the guardrails, the authorizer, `apps/engine/src/entry`, `apps/web` or `libs/ui`.

## Acceptance criteria

| ID | Given | When | Then | Test (name quotes the AC id) |
| --- | --- | --- | --- | --- |
| AC-1 | A backlog that falls linearly with small noise | `drainEta` runs | `ok` with an ETA, a band with `lowMs <= etaMs <= highMs`, `r2 >= 0.95`; the ETA is within 10 % of the true one | `forecast/src/drain-eta.spec.ts`: "AC-1 a steady decline has a drain ETA with a confidence band" |
| AC-2 | A noisy or bending series with R2 below 0.95 | `drainEta` runs | `no-reliable-forecast` with the R2, never an ETA | "AC-2 R2 below 0.95 is no reliable forecast" |
| AC-3 | Too few points or too short a span; a flat or growing backlog; a series that changed slope | `drainEta` runs | `insufficient-data` with what is needed; `not-draining`; the adaptive window uses the recent slope. The output has no NaN or Infinity and an ordered band (property test) | "AC-3 insufficient data, not draining, adaptive window, finite outputs" |
| AC-4 | A counter with a reset and a gap | `counterRate` and `ewma` run | Per-second rates, the reset interval skipped (never a negative rate) | "AC-4 counters are turned into rates across a reset" |
| AC-5 | The golden Prometheus pages of the five lab versions (both statistics modes) and LavinMQ | The parser reads each, in one chunk and in many different chunkings (including a split inside a multibyte character) | The samples equal an independent line count; the same samples for every chunking; label escapes, spaces after commas, `NaN`/`+Inf`, timestamps and `# HELP`/`# TYPE` lines are handled | `adapter-prometheus/src/parser.spec.ts`, `golden/golden.spec.ts`: "AC-5 ..." |
| AC-6 | A line longer than `maxLineBytes`, a body longer than `maxBodyBytes`, more samples than `maxSamples` | The parser reads them | The long line is skipped and counted; the body ends with `response-too-large`; the sample cap ends with a counted truncation; memory stays bounded (the line buffer never exceeds its cap) | "AC-6 oversized lines, bodies and sample counts are bounded and counted" |
| AC-7 | A 20 MiB synthetic body that is always ready | The parser reads it | It gives the loop a turn at least every 64 KiB and 2,000 lines (counted with an injected yield, also inside one huge chunk; no wall-clock percentile is asserted) | "AC-7 the parser yields to the event loop" |
| AC-8 | A loopback server and the real client | A scrape runs | The request is a GET of the exact path and query, sockets come from the Dialer, credentials go as `Authorization` only when the resolver gave them, a 401/403/404/5xx maps to its code, a redirect is refused, an abort closes the socket | `adapter-prometheus/src/client.spec.ts`: "AC-8 ..." |
| AC-9 | A canary secret as the login | Every failure path runs | The secret is in no error, no URL and no log line (I-10) | "AC-9 a login never reaches an error" |
| AC-10 | An Amazon MQ profile (endpoints 16001, 16002, 16003) with queue demand | `planScrape` runs | One target per endpoint, interval >= 60 s, aggregated `/metrics` only (no per-object request), the connection login for provider endpoints, none for a listener or default endpoint | `svc-metrics/src/internal/scrape-planner.spec.ts`: "AC-10 ..." |
| AC-11 | An LB-fronted profile | `planScrape` runs | Per-node targets when every running node has an endpoint, else the plan is marked `partial` with the reason and the uncovered nodes | "AC-11 ..." |
| AC-12 | A 4.3 profile with queue demand, and a profile without `queueFilter` | `planScrape` runs | Aggregated `/metrics` always; `/metrics/detailed?family=queue_coarse_metrics&family=queue_consumer_count&vhost=...` only on demand and only where `perObjectAllowed`; `queue=<regex>` only with `queueFilter`, chunks of at most 2,000 characters, at most 8 requests; the interval is at least 10 times the last scrape duration, clamped | "AC-12 ..." |
| AC-13 | No endpoint, a blocked provider, or an endpoint that failed three times | `planScrape` runs | The source is `management` with the overview and node reads only (per-object reads only where `perObjectAllowed`); the fallback is labelled and its derived rates are marked approximate | "AC-13 ..." |
| AC-14 | Series fed past the item, byte and queue-series caps | The store ingests | Every ring stays within its bounds, drops are counted and reported, pinned queues and the top backlogs stay, cluster and node series are never evicted | `store-hot.spec.ts`: "AC-14 ..." |
| AC-15 | A fake scrape port, a fake management port and a manual clock | The collector runs with demand | It scrapes through the scheduled port only, stores the points, falls back to management after three failures, returns to Prometheus after the cool-down, makes no request without demand, stops on idle and on `stop()` | `collector.spec.ts`: "AC-15 ..." |
| AC-16 | The real router over the in-memory service | `metrics.query` and `metrics.forecast` are called | A bounded window of points (never more than `maxPoints`), the source and its partial/approximate/stale flags, the forecast states of AC-1..3; an unknown or invisible connection answers 404 | `actions/*.spec.ts`: "AC-16 ..." |
| AC-17 | A live client | It subscribes to `metrics.live` | A snapshot of the latest values, then only changed keys (`latest`); an invisible connection ends with NOT_FOUND; stop ends every subscription | `window-source.spec.ts`: "AC-17 ..." |
| AC-18 | The composed engine | Its served actions and topics are compared with the registry | `metrics.query`, `metrics.forecast` and `metrics.live` are served; a quit drain stops the collector (no request after it) | `apps/engine/src/compose-services.spec.ts`: "AC-18 ..." |
| AC-19 | A synthetic 400,000-series Prometheus body and 100,000 queues of demand | `perf:metrics-100k` runs | The parse yields by count (a turn every 64 KiB and 2,000 lines) and holds nothing (heap growth under 96 MiB for 29 MiB of text), the demand is capped at 50 queues, queues nobody asked for are skipped by the parser, and the store stays under its caps and counts its drops (stored and refused add up to every series). Wall times and the loop delay are printed, not asserted | `apps/perf/src/metrics-100k/metrics-100k.perf.ts` (`pnpm nx run perf:metrics-100k`): "AC-19 ..." |

What is only proved against fakes: the whole scrape path (the scheduled port, the resolver, the dialer) runs over a loopback HTTP server, not over a real RabbitMQ listener, and the collector runs over a fake scrape port and a manual clock; the golden pages prove the parser and the catalogue against real output, not the cadence. A lab run (`queue=` on 4.3.6, a real node loss, an Amazon MQ account) is not done here (see the report's human-only list).
