# svc-explorer

Windowed inventory, overview and the explorer.window topic, served from an engine-resident bounded index.

Tags: `type:service`, `runtime:node`, `trust:critical`.

Status: work package M0-48 ([spec](../../../docs/specs/M0-48.md)), slices A to E, F, G, H and I of nine. Slice F ships no engine code: the golden replay, the lab run and the perf harness described under "Proof of scale" below. Slice A shipped the module skeleton, the shared contract types, the `inventory.query` contract, the ports and their fakes. Slice B shipped the bounded index and the sweeper. Slice C makes `inventory.query` real: it reads windows from the index. Slice D ships `overview.get`. Slice E ships the `explorer.window` topic source. Slice G ships `search.query`. Slice H ships the `bindings` kind. Slice I ships the `connections` kind. The sweep cadence and the idle stop (AC-5) are in the sweeper. The module is not yet registered in `coreModules`, and its topic source is not yet registered with the hub (OQ-669).

## Public API

- `createExplorerModule(deps)`: returns the `ExplorerModule` (`actions`, `topics`, `topicSources` with the `explorer.window` source, `jobs`, `stop()`) the composition root registers. It owns the one sweeper the actions and the topic read through; `stop()` ends every topic subscription (with `ENGINE_SHUTTING_DOWN`) and every sweep.
- `ExplorerModuleDeps`, `ExplorerLimits`, `DEFAULT_EXPLORER_LIMITS` (`src/deps.ts`): the ports the module needs (the scheduled `MgmtReadPort`, the cached profile read, the connection read, clock and timers) and the bounds of the index and its sweeps.
- `createInventoryQueryAction(deps)`: the `inventory.query` action. It checks that the caller may see the connection (the same `NOT_FOUND` for an invisible and an unknown one), reads the cached profile (`NOT_FOUND`, run the probe first), touches the sweeper (the first query starts the sweeps) and answers a window from the index with no request to the broker. Every answer carries its freshness: `loading` with `loaded` and `expected` while the first read runs (never `complete`), `live`, `stale` (the last read failed or was partial, rows from the last good version) or `unavailable`; the profile's hazard ids that explain a missing column are copied into `freshness.hazards`. A pinned `window.version` is served from the retained previous version and says `versionChanged` when it is gone. Stats-off rows carry exactly what the broker sent: a missing field is absent, never zero.
- `createOverviewGetAction(deps)`: the `overview.get` action (slice D). It checks visibility as `inventory.query` does, touches the sweeper, and makes at most three `interactive`-lane reads (`/api/overview`, `/api/nodes`, and `/api/health/checks/alarms` only when the nodes do not settle the alarms); it never lists a queue, an exchange or a connection. Message totals are the broker's `queue_totals` when it reports them (`broker-overview`), else the sum over the queue sweep (`queue-sweep`, with `asOf` and `complete`), else absent. Rates are `available` only where the broker reports them, else `unavailable` (`statistics-off` or `not-reported`), never zero. Alarms: the per-node flags of `/api/nodes` name a node and a resource; without them the alarm check's `ok` is `none` and anything else, a failure included, is `unknown` with a fixed reason, never `none`. The node flag names are assumed from the broker's HTTP API (no recording holds an alarm, OQ-660).
- `createSearchQueryAction(deps)`: the `search.query` action (slice G). It checks visibility and reads the cached profile as `inventory.query` does, touches the sweeper and answers from the index with no request to the broker: the best 50 names (`SEARCH_RESULT_MAX`) of the queues and exchanges (or of the `kinds` asked for), each with `kind`, `key`, `vhost`, `name` and a `rank` (`exact`, `prefix` or `substring`, case-insensitive), the exact count of names that matched (`matched`) and `truncated` when more matched than are shown. Order: rank, then the shorter name, then the key, then the kind. The text is 1 to 200 characters (an empty one is `VALIDATION_FAILED`) and is a plain text, never a pattern (OQ-666); the character-bitmask prefilter and the fzf-style scorer are not built (OQ-675). One pass over the rows keeps a sorted shortlist of 50, so the answer holds no list of all matches. `freshness` merges the kinds searched: the worst state (a search is never `live` while one of its kinds is loading), `complete` only when every kind is, `loaded` and `expected` summed. A cold connection is answered at once from what is installed, labelled `loading`. Measured at 20,012 names (AC-25): p95 a few milliseconds per search through the executor, against the 50 ms target.
- `createWindowSource(deps)` (`src/internal/window-source.ts`, slice E): the `TopicSource` of `explorer.window`. A grid names the keys on screen (`params.keys`, at most 500, with `cid` and `kind`); a change of what is visible is an `unsub` plus a `sub` (OQ-657). The snapshot is read synchronously from the index for those keys, plus a `~version` item (OQ-658). It then follows the sweeper's installs and publishes only: an upsert for a visible key whose row changed, `remove(key)` for a visible key that left the inventory, and one `~version` item when rows were added or removed (none when only counts changed). An item is `{ key, version, row }` with the row as `inventory.query` returns it but without its `key`. The hub owns coalescing to the latest per key, the 2 Hz pace, the ring (1,000 items, 1 MiB) and `gap` then `snapshot` on overflow. The hub asks synchronously but visibility is an async read, so a subscription is admitted first: until then the snapshot is empty and nothing is followed (an unknown connection never gets an index, a sweep or a listener); an invisible and an unknown connection end the subscription with the same `NOT_FOUND`; permission (`broker.read`), param validation and the 64-subscription limit are the hub's. After admission the current rows of the visible keys are published, which the outbox absorbs if the first snapshot has not been taken yet and sends as a delta if it has. Visibility is checked once, at subscription (a connection made private later is not re-checked until the client resubscribes). Measured worst case (AC-19): 500 keys with 255-character names and vhosts and typical other fields are 793,812 bytes of snapshot, 76 % of the 1 MiB frame; with every optional string at 255 characters a snapshot passes the frame and the hub ends the subscription with `BUDGET_EXCEEDED` (never silence). A `sub` naming 500 such keys is about 340 KB, over the hub's default 64 KiB client frame: the carrier must raise `maxClientFrameBytes` (OQ-683); the numbers are OQ-684.
- `kind: 'bindings'` of `inventory.query` (slice H, `src/internal/bindings.ts`): bindings are never listed whole (I-7), so a query names exactly one vhost in `filter.vhosts` (otherwise `VALIDATION_FAILED`, with no request to the broker). The vhost is read on first use, paged at 500 in the `interactive` lane (a person is waiting), and kept resident; bindings are not part of the background sweep. RabbitMQ ignores the paging on this endpoint and answers a bare array with the whole vhost (all five recorded versions); the store reads that as one answer, applies the cap after it (rows past the cap are counted in `dropped`, `truncated` is true, `expected` is the array length) and sets the fixed `freshness.reason` "sent in one answer, without paging". Only a paged answer (LavinMQ) stops early at the cap. A big bare answer is bounded only by the adapter's body limit (OQ-688). The resident rows of a connection are bounded by `ExplorerLimits.maxBindingsResident` (500,000): rows past it are dropped and counted (`freshness.dropped`, `truncated`), and a vhost that no longer fits is evicted, least recently used first, and counted (`BindingsStore.stats`). A resident vhost older than `bindingsMaxAgeMs` is read again; if that fails the rows are served as `stale`. Filter, sort and window work as for the other kinds (text on source, destination and routing key; sortable by `source`, `destination`, `destinationType`, `routingKey`, `vhost`). The row carries the arguments only as `argumentsKey` (canonical, cut at 512 characters and flagged). `explorer.window` follows the swept kinds only. Decisions are OQ-686; the correction for the recorded bare-array answer is OQ-688.
- `kind: 'connections'` of `inventory.query` (slice I): the sweep lists `/api/connections` once per sweep (all vhosts), paged at 500 with `disable_stats` and without `enable_queue_totals`, and the index holds the rows like the other swept kinds (`explorer.window` follows them too). A row is `key`, `name` and what the broker sent of `vhost`, `user`, `node`, `state`, `protocol`, `channels`, `peerHost` and `ssl`: statistics off drops the static information below 4.2.6 (registry capability `connectionStaticInfoWithStatsOff`), and the row then has only the fields the broker sent, never a default. A connection with no vhost is keyed under the empty vhost, has no `vhost`, and no `vhosts` filter matches it. Facets: `types` is the protocol, `states` the state, text matches the name; every row column but `key` can be sorted; `hasConsumers` and `minMessages` match nothing, as for exchanges. The registry has no hazard id for the dropped connection information, so `freshness.hazards` stays empty for this kind (OQ-691). `search.query` does not search connections.
- `createExplorerFakeDeps({ connectionCount, bindingsPerVhost, bindingsAnswer, queueCount, vhostCount, exchangesPerVhost, ownerId, seeded, profile, mgmt, limits })` (`src/testing.ts`): fakes for those ports, including a scripted broker that serves N queues across vhosts through a paged `/api/queues` (page ceiling 500), N connections through a paged `/api/connections` and records every request, a statistics-off single node on `/api/overview`, `/api/nodes` and the alarm check, a cached profile (`seeded: false` removes it), and a sweeper on manual time, for specs, the architecture manifest and the HTTP specs.
- The contract schemas live in `@app/contracts` (`registry/explorer-types.ts`, `registry/inventory-query.ts`, `registry/overview-get.ts`, `registry/search-query.ts`, `registry/explorer-window-topic.ts`).

## Internals (src/internal/)

- `index.ts`: `createInventoryIndex`, the per-connection index. Bounded by rows and estimated bytes across kinds; rows past the cap are dropped in sweep order and counted (`stats.dropped`, `IndexVersion.dropped` and `truncated`). Every install is a new version; the previous one stays readable for a pinned window. `window` filters, sorts (a cached permutation per version, kind and column, at most 4 kept; the key breaks ties) and slices. `setStale` marks a version whose latest sweep did not finish (I-13).
- `sweeper.ts`: `createSweeper`, the only code that lists the broker. One sweep per connection at a time (a second `sweepNow` joins it); per vhost and kind (the connections are one global list), pages of 500 with `disable_stats` (and `enable_queue_totals` on queues only), always in the `background` lane. `status(cid)` says whether a sweep is running and the broker's own object count per kind (`total_count` of the first page of each vhost), which is what `freshness.expected` shows. A kind that already has a version is installed only when every kind was read, and then all kinds as one new version (so a pinned scroll survives a whole sweep); a failed, aborted or partial sweep leaves the last good version in place, marked stale, and the outcome carries a fixed-text Problem (no broker text, I-10). Cadence: the first `touch` (demand) starts a sweep at once; the next starts `clamp(sweepMinIntervalMs, sweepMaxIntervalMs, sweepCostFactor x server time)` after the last one ended (30 s, 15 min, 50 x the sum of the request durations the injected Clock measured, so 0.4 s, 4 s and 20 s of server time wait 30 s, 200 s and 900 s); a failed sweep waits by the same formula, never sooner. When a wait ends and no `touch` came for `idleStopMs` (10 minutes) the connection's sweeps stop with no timer left, and a later `touch` starts them again at once; `stop()` cancels the timer and aborts the request in flight (OQ-687). A first read installs each kind as it finishes, so a partial first sweep shows what is loaded and says it is incomplete.
- `freshness.ts`, `visible.ts`, `profile.ts` (slice C): the freshness every answer carries (fixed reasons only, I-10), the connection visibility check (a copy of the one in `svc-capabilities`: a service imports no service), and the cached profile read.
- `overview.ts` (slice D): the service's own zod schemas for `/api/overview`, `/api/nodes` and the alarm check, and the pure steps from them to the `overview.get` output (totals, rates, nodes, alarms). `index.ts` gained `queueTotals()`, a single pass over the queues that counts the queues lacking a count instead of summing them as zero.
- `window-source.ts` (slice E): see `createWindowSource` above. `index.ts` gained `current()`, the version the index is at now.
- `search.ts` (slice G): `searchNames`, the ranked top-50 over the rows of the searched kinds, and `mergeFreshness`. `index.ts` gained `rows(kind)`, the read-only rows of the current version, and `folded(kind)`, the case-folded names in the same order: built on the first search of a version, kept with it, counted in `stats.bytes` and never more than one extra copy of the names, so the search folds nothing per query. Once the shortlist of 50 is full, a match that cannot beat its last entry is turned away on numbers and one key compare. The sorted copies the windows read are kept per kind, `sortCacheEntriesPerKind` of them (default 8, `ExplorerLimits`), the oldest going first.
- `bindings.ts` (slice H): `createBindingsStore`, the per-connection resident LRU of vhosts with its bounds, counts and single-flight reads; see `kind: 'bindings'` of `inventory.query` above.
- `rows.ts`: the service's own zod schemas for the part of each management answer it reads, and the mapping to rows; a field the broker left out or sent as null is absent from the row.

## Proof of scale (slice F)

- `createSweeper` and the `Sweeper` and `SweepOutcome` types are exported from the package index for the lab run (`libs/testkit/src/it/svc-explorer.it.ts`), which needs the sweeper on the real clock and the outcome of a sweep. The module owns its own sweeper; nothing else should create one.
- AC-22, `libs/testkit/src/golden/explorer-replay.spec.ts`: the sweeper over the golden recordings (RabbitMQ 3.13.7, 4.0.9, 4.1.8, 4.2.9, 4.3.6 with statistics on and off, LavinMQ 2.10.2), served by a local HTTP server and read by the real management adapter behind a real `BrokerScheduler`. It checks what is sent on the wire: `page`, a `page_size` of at most 500, `disable_stats` and `enable_queue_totals` on RabbitMQ lists, neither flag on LavinMQ, and no request other than the vhost list, a queue and an exchange list per vhost and one connection list. No Docker.
- AC-23, `libs/testkit/src/it/svc-explorer.it.ts` (`pnpm nx run svc-explorer:it '--versions=4.2.9,4.3.6'`, needs a Docker daemon): a lab broker seeded with 20,000 queues (`IT_QUEUES=100000` for 100,000) by `src/it/seed-queues.ts` (a definitions import), swept through the adapter and the scheduler with a recording proxy in front of the broker. It asserts paging and flags as the broker received them, that the index count equals `object_totals.queues`, that windows make no request and have a p95 of at most 100 ms, and that a pinned scroll sees every queue once. It prints the figures S-13 records (`src/it/s13-alternatives.ts` adds the other ways of listing, measured and not asserted).
- AC-24, `apps/perf/src/explorer-20k/explorer-20k.perf.ts` (`pnpm nx run perf:explorer-20k`, node only, synthetic broker): window p95 and event-loop delay p99 while sweeps keep installing versions; asserted at 20,000 queues, printed at 100,000. It also prints the `search.query` p95 at 20,000 and 100,000 names.
- The record is [S-13](../../../docs/architecture/s-13-mgmt-api-cost-100k.md) and the addendum to ADR-024.

## Invariants

- Never imports another service or an adapter; cross-service needs are ports wired in the composition root (blueprint 2.2).
- Every mutation is an `implementAction` file in `src/actions/`; nothing writes through a WritePort outside one (mutation funnel). This module is read-only: it is handed a `MgmtReadPort`, never a write port (I-2, I-8).
- Engine buffers are `BoundedRing` or `BoundedQueue` (`@app/bounded-buffers-only`).
- No contract allows an unbounded input or output: a window is required, its `limit` is at most 500, filters and key lists are capped, and every output array has a maximum (I-7). The test `AC-1 explorer contracts allow no unbounded input or output` proves it.
