# svc-identity

Credential providers and the TokenManager: where a broker login comes from, its renewal and its expiry rules.

Tags: `type:service`, `runtime:node`, `trust:critical`.

## Public API

- `createIdentityModule(deps)`: returns the `EngineModule` the composition root registers.
- `IdentityModuleDeps` (`src/deps.ts`): the ports the module needs.
- `createIdentityFakeDeps()` (`src/testing.ts`): fakes for those ports, for specs, the architecture manifest and the HTTP specs.
- Credential providers (M1-23, slice A): `createPasswordProvider`, `createStaticTokenProvider`, `createTokenCommandProvider` and `createX509ExternalProvider`, each a `CredentialProvider` that returns an `IssuedCredential` or rejects with an `AppError` of fixed text. `ProviderConfigSchema` is the strict union of their non-secret settings.
- The client-credentials provider (M1-23, slice B): `createClientCredentialsProvider` asks the configured token endpoint for an access token through `TokenEndpointPort` (the `adapter-token-endpoint` project implements it), with a fixed-text Problem per failure and a bounded wait. `ProviderConfigSchema` gains the `client-credentials` kind: an `https` endpoint (plain `http` only on a loopback host), a client id, an optional scope and audience, and optional `tlsCa` (public CA certificates, PEM, at most 8) for this identity provider only; the config has no way to switch certificate verification off. The client secret stays in the profile's sealed credential.
- The TokenManager (M1-23, slice C): `createTokenManager({ providers, auth, capabilities, clock, timers, limits? })`. `credentialFor` returns the credential of a profile and protocol with a `generation`; `track` registers a live connection so its token is renewed at 75 % of the lifetime and pushed to it (`updateSecret` for AMQP 0-9-1, `putAuthToken` or a reconnect for AMQP 1.0, a reconnect for streams, nothing for HTTP); `refreshAfterUnauthorized` is one renewal after a 401, a no-op for a stale generation; `state` and `subscribe` report `valid`, `refreshing`, `failed`, `expired`, `username-changed` or `invalidated` with a fixed-text Problem (a copy for each reader). A renewal whose user name differs or is missing, or that drops the expiry, is refused and never reaches the connection; the first user name of a connection is kept apart from the entries (it survives eviction) and a first token for another user is refused. `track` takes the login `username` when the caller has it. `invalidate(connectionId, protocol?, { forgetUsername? })` drops the cached credential, the renewal timer and any renewal or push in flight (slice E calls it on a profile edit or delete, a secret rotation, a vault lock and a prod lock). The manager methods take no principal: never expose them through a route with a caller-chosen connection id. Callers share one renewal in flight; failures back off 2 s doubling to 60 s with at most 8 attempts per lifetime; a first token that just failed is not asked for again before the wait is over; one sweep timer catches deadlines a wall-clock jump left behind; entries, remembered user names, listeners, concurrent provider calls and every wait are bounded and every refusal is counted (`stats()`). `isRetryableAfter401` allows GET, HEAD and OPTIONS only. The pure rules (`refreshPoint`, `plannedRefreshAt`, `backoffDelayMs`, `renewalActionFor`, `expiryRuleFor`) are exported and tested apart from the manager.
- The size preflight (M1-23, slice D): `credentialFor` and `refreshAfterUnauthorized` now return `warnings` (`SizeWarning`: a code, a text key `identity.<code>.v1`, the measured bytes and the limit) for a token that may be too large for the broker, and report each new warning once per credential generation to the optional `onSizeWarning` sink before the value is returned. A warning never blocks, and each `SizeWarning` (and the list that holds it) is frozen, so a caller cannot change what another caller or the sink reads. `BEARER_HEADER_LARGE` is a `Bearer <token>` header (or the encoded `Basic` one) above 4,000 bytes; `PLAIN_RESPONSE_LARGE` is the AMQP login response (`0x00 user 0x00 token`) plus a stated headroom of 1,024 bytes above the pre-auth frame limit (8,192 bytes when `amqp091PreAuthFrame8192` holds, 4,096 otherwise). The registry knows a pre-auth frame rule for AMQP 0-9-1 only, and `credentialFor` and `refreshAfterUnauthorized` take `http` or `amqp` with nothing finer. So an `amqp` login is always measured as an AMQP 0-9-1 PLAIN login, whichever protocol the connection really speaks: for an AMQP 1.0 or stream connection the warning is the 0-9-1 measure applied to that token, not a measure of its own login. The pure `preflightSize` takes `amqp10` and `stream` as protocols and measures them against the smaller 4,096-byte limit, because no per-protocol limit is recorded for them, but `credentialFor` never passes them. The research notes read an 8,192-byte SASL limit for AMQP 1.0 from 4.0 (OQ-1549), so an AMQP 1.0 or stream login may get a warning it does not need, or miss one it should get, until M1-25 records the limits per protocol. A missing warning is therefore not a promise that the login fits. The numbers are source readings, not lab results (U-14), so the texts in `i18n/en/warnings.json` say a request "may" fail. `preflightSize`, `preflightCredential` and `httpAuthorization` (a token is always `Bearer`, only a password is `Basic`) are exported and pure. `httpAuthorization` throws a `VALIDATION_FAILED` Problem (fixed text) for a token that is not printable ASCII without a space, a Basic user name with a colon, or a control character in a Basic part; it returns `undefined` only for the certificate login. A sink or listener that returns a rejected promise is counted in `listenerErrors` like one that throws, and a `capabilities()` that is not an object, or a flag that is not `true`, is read as "nothing proven" (`capabilityErrors`).
- The capabilities feed (M1-23, slice D): `createRegistryCapabilities({ registry, profileFor })` answers the manager's `capabilities` callback from the three registry rules `amqp091ClosesAtCredentialExpiry` (from 4.2.6), `amqp10TokenRenewalEndpoint` (from 4.1.0) and `amqp091PreAuthFrame8192` (from 4.1.0); this project compares no version (I-3). A connection with no known profile proves nothing. A rule the registry lacks is a `SemanticsGapError`: the manager counts it (`capabilityErrors`) and takes the conservative branch (cancels its own consumers at expiry, reconnects AMQP 1.0, measures a login against the smaller frame) in the expiry timer, the push and the preflight alike.
- The provider config store (M1-23, slice E3, OQ-1455): `createProviderConfigStore(store)` wraps a `CredentialProviderStore` (the `credential_providers` table of `persistence`, or `createInMemoryCredentialProviderStore` for specs) and applies `ProviderConfigSchema` on every read and every write. `get` returns `found` with the validated config, `absent`, or `{ kind: 'invalid', reason: 'unreadable' | 'schema' }`: a stored value that is not JSON, is over 256 KiB or fails the schema (an unknown kind, an extra key, a relative command path) is one fixed refusal, with no thrown parse error, no zod issue and no part of the stored text, and the caller never holds a config the schema did not accept. `put` stores what the schema returned (defaults filled in) and refuses an input it rejects without repeating it. The config holds no secret: the password, token or client secret stays in the profile's sealed credential. Nothing in the engine writes it yet (OQ-1455: the action and form are a follow-up issue), and a connection bundle cannot create one.
- `SecretValue`: a secret that prints `[secret]` in `String`, `JSON.stringify` and `util.inspect`; `reveal()` is the one way to the value.
- `readTokenClaims`: reads `exp`, `iat` and the user name claim of a JWT. It checks no signature; the broker does.
- Ports (in `@app/ports`, `identity.ts`): `StoredLoginPort`, `CommandRunnerPort`, `TokenEndpointPort` and `ConnectionAuthPort`; the composition root implements them.

## Invariants

- Never imports another service or an adapter; cross-service needs are ports wired in the composition root (blueprint 2.2).
- Every mutation is an `implementAction` file in `src/actions/`; nothing writes through a WritePort outside one (mutation funnel).
- Secrets are write-only (I-10): a secret lives in a `SecretValue`, and no provider puts one, a user name, a command line or a command's output into an error.
- This project imports no socket library and no adapter (I-9, layering); the token request and the command run behind ports.
- Engine buffers are `BoundedRing` or `BoundedQueue` (`@app/bounded-buffers-only`). The TokenManager holds credentials in memory only, keeps at most `maxEntries` of them, and a token, a secret or the text a provider or the connection layer sent is never in its state, errors or `cause`.
- A size warning carries numbers and a text key, never the token; the sink hears the key, the connection, the protocol and the generation.
- Time and timers come from the injected `Clock` and `Timers`; nothing in this project sleeps or reads `Date.now()`.
